一次伪装成 sshd 的挖矿进程排查

原文发表于 2024-05-28 · Denis Wen

Linux / 进程与定时任务 · 历史排查记录

在 top 里看到一个名为 sshd 的进程持续占用大量 CPU。从进程实际运行的文件开始，排查到了定时任务和挖矿配置。

入口：一个名字熟悉的异常进程

最初的异常来自 CPU 占用。进程名看起来像常见的 SSH 服务，但资源使用情况引起了注意。进程显示的名字不能说明它实际执行的文件来自哪里，于是继续查看文件与进程的关系。

# 查看该进程打开的文件
lsof -p <PID>

# 查看进程实际执行的文件
ls -l /proc/<PID>/exe

继续查：是谁在重复启动它？

随后检查相关用户的定时任务：

crontab -l -u <用户名>

原文记录了两类可疑任务：一类每隔六小时尝试下载程序及配置文件，另一类每分钟尝试启动这个伪装成 sshd 的程序。程序放在临时目录中，任务通过文件锁控制重复执行。

这些任务解释了一个重要现象：即使结束当前进程，后续调度也可能再次启动它。排查需要把执行文件和启动来源联系起来。

配置文件给出的线索

原文进一步查看了配置文件，发现它包含 CPU 计算配置、RandomX 相关选项以及矿池连接信息。结合异常占用和定时任务，判断这是一个挖矿程序。

这里不保留恶意下载地址、矿池地址与原始任务命令。公开版本只保留定位过程，避免把可执行的恶意下载指令混入排查示例。

原文做到了哪里

原文最后记录了清理相关用户定时任务的操作，但没有记录完整的入侵入口调查、其他持久化项检查或恢复验证。因此，这篇文章是一段异常进程排查记录，不能据此认定系统已经完成全面清理。

原文使用的删除操作会移除该用户的整份 crontab。重新整理时保留这个范围说明：实际处置前应先保留证据，区分正常任务与恶意条目，避免把正常业务任务一并删掉。

留下来的排查顺序

  1. 从 CPU 异常确认需要调查的进程。
  2. 核对实际执行文件，避免只凭进程名判断。
  3. 查找反复拉起进程的调度来源。
  4. 结合配置与行为判断用途，并明确处置记录的边界。

这次记录提醒我：一个看起来熟悉的名字，也值得沿着文件路径和启动链路再往下追一层。
