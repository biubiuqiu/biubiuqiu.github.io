用户让 Agent 查一下昨晚失败的订单。工具返回 2 MB 明细，Agent 找出三个异常批次，替用户建了一张工单。十分钟后，用户问：“第二批和第一批是同一个原因吗？”如果把整份明细再发给模型，每次追问都要付一次阅读费。如果只留下“三个批次异常”，这次追问又答不出来。更麻烦的是，假如进程恰好死在工单创建成功之后，下一台机器怎么知道该继续分析，还是再建一次工单？

这三个问题决定了我会怎么存 transcript，也就是 Agent 与用户、模型、工具之间已经发生的交互。对于多人共用、需要跨机器恢复的服务，我会从按逻辑条目追加、小内容内联、大结果留可回读的引用开始。模型下一轮读哪些条目，单独做决定。下面用这张工单走一遍。

一行该放什么？先看一次工具调用#

假设这次查询的调用编号是 q7，建单是 t8。平台可以把一次运行记成下面六条。序号属于会话，调用编号属于一次工具交互，两者各有用途。

序号   类型                写入的内容
41     user.message        查昨晚失败的订单，异常批次建一张工单
42     tool.call     q7    query_orders，时间范围与查询条件
43     tool.result   q7    3 个异常批次，明细对象 A，版本与校验值
44     tool.call     t8    create_ticket，依据 #43，稳定幂等键 K
45     tool.result   t8    成功，外部工单号 O-318
46     assistant.message   三个批次已汇总到工单 O-318

如果从数据库里只取 44 到 46，就能给用户展示“建了哪张工单”。如果两次查询并行，即使结果按相反的顺序回来，也能用调用编号配对。流式输出的半个词、半截 JSON 参数可以发到前端；通常等一条消息或一次调用完整后，再提交一条历史。真要断线续播，可以给增量片段配短期缓冲和游标。它的保留周期可以比会话短得多。

整段会话放一个 JSON 字段，在单写者、长度有上限、总是整段读取的原型里很省事。代价取决于具体写法。假设客户端每加一条都重新上传整个数组，100 条等长消息累计要传 5,050 条消息的等价字节；分条追加只传 100 条。这是客户端传输量的算例，数据库的实际磁盘写入还取决于实现。另一种很实用的起点是本地 JSONL：同样使用 JSON 编码，每次只往末尾加记录。编码格式和更新粒度，是两项可以分别选择的设计。

同一句“继续”，三个 SDK 分别从哪里读#

Claude Agent SDK：把原生会话交还给运行时#

用 TypeScript 调用 query() 时，可以记下返回的 session_id，下次通过 options.resume 继续。默认 transcript 保存在本机 ~/.claude/projects/ 下的 JSONL 文件中。把后续请求打到另一台机器时，光传一个 ID 还缺少它指向的数据。

官方提供的 SessionStore 适配器支持 append(key, entries) 和 load(key)。它对后端提出了很具体的要求：读回来的条目要与写入值深度相等，顺序一致。换一种 JSON 序列化可以，擅自把工具结果换成一句摘要会破坏这项约定。键里还有项目标识和可选的子路径，后者可能对应子 Agent 的记录。我的做法是把原生条目按批持久化，给界面另建轻量索引。若在底层拆走 2 MB 明细，就在 load 时无损拼回；若只希望模型收到摘要，应在工具最初返回结果时就明确设计这个接口。会话恢复 · 外部存储契约与示例

LangChain / LangGraph：恢复“接下来轮到谁”#

LangChain 的 create_agent(..., checkpointer=saver) 可以接入 LangGraph 的持久化。同一个 thread_id 找回这条线程的图状态；messages 是其中一个字段，业务也能扩展自己的状态。开发时可以用 InMemorySaver，官方给出的数据库示例使用 PostgresSaver。跨线程的用户偏好则有单独的 Store。LangChain 短期记忆 · LangGraph 持久化

拿工单举例，可以让检查点带上查询产物 A 的引用、待审批的建单请求和当前图状态。审批人隔天回来，运行时要知道从哪个步骤继续。只恢复聊天窗口里的六行文字，很难可靠地推断这件事。反过来，若把原始明细也塞进经常保存的状态，检查点的读取和序列化就要处理一个大字段。我的选择是让状态只带该节点下一步要用的数据，再单独测量实际 saver 的增量写入量。

OpenAI Agents SDK：留下历史，还能改变模型读到的内容#

Python SDK 的 SQLiteSession("orders-17", "sessions.db") 就能给同一会话的多次 Runner.run 保存历史。显式指定文件路径很重要，默认的内存库随进程结束而消失。Session 有 get_items、add_items 等接口。RunConfig.session_input_callback 则允许在调用模型前组合已取回的历史与本轮输入；筛掉某些旧项，并不会把其余旧项当作新增历史再写一遍。Session 与输入合并 · SQLiteSession 的持久化参数

例如，下面两次调用可以放在两个进程里执行。示例假设应用已配置同一个 agent，并且两个进程能访问同一份数据库文件；第二次调用用相同的会话 ID 找回历史。

from agents import Runner, SQLiteSession

# 第一轮，agent 的查询工具返回摘要、批次号和明细引用
session = SQLiteSession("orders-17", "orders.db")
await Runner.run(agent, "查昨晚失败的订单", session=session)

# 下一轮，重新打开会话，不需要客户端重传整段聊天
resumed = SQLiteSession("orders-17", "orders.db")
answer = await Runner.run(agent, "第二批和第一批原因相同吗？", session=resumed)

这里有两处成本。回调里只留下十条，可以减少送给模型的 token；如果此前已经取回了一万条，数据库读取量还是一万条。SessionSettings(limit=N) 能进一步限定取回数量，但 N 按条目计数，截断点可能刚好落在工具调用与结果之间。平台需要能回补缺失的配对，或者把整组已结束的交互移出输入。

在 PostgreSQL 和对象存储之间划线#

回到企业平台。下面是我会先实现的一张逻辑表。平台生成稳定的事件 ID，同一次写入的重试沿用它。工具调用 ID 可以在一次 run 内解释，审计与排障还需要知道事件属于哪个租户、会话和 run。

transcript_item
  tenant_id, session_id, seq         会话内的已提交顺序
  event_id, run_id, kind, call_id    去重、归属与工具配对
  payload_jsonb                     消息内容，或小预览与产物描述
  artifact_key, digest, byte_size   大结果的不可变版本、校验值和大小
  schema_version, created_at        解码与保留策略

  PRIMARY KEY (tenant_id, session_id, seq)
  UNIQUE      (tenant_id, session_id, event_id)

一次追加事务里，先锁定这条会话的头记录，检查事件是否已写入，给这一批分配连续序号，再插入条目、更新头序号并提交。这样前端拿 seq > cursor 翻页，不会因一个较早分配的序号后来才提交而漏掉记录。不同会话可以各写各的。大型并行任务若卡在同一把锁上，先观察单会话等待时间，再决定要不要让子任务分流；全平台的并发用户数推不出这把锁有多热。

明细 A 先写入当前租户名下的不可变对象并确认成功，再在数据库事务里提交第 43 条及其引用。上传成功、事务失败会留下孤儿对象，可以在宽限期后扫描回收。倒过来做则可能让用户看到一条“成功”的记录，点进去却没有明细。访问产物时按当前用户重新验权，事件里存稳定的对象标识；临时下载地址在读取时生成。

算一笔账：数据库变小了，哪些字节还在？#

假设每天 10,000 次运行，每次 20 条记录，每条平均 1 KB，另有一次 2 MB 的工具返回。按十进制单位，每月按 30 天计。下面只算未压缩的逻辑内容；索引、WAL、副本、备份、对象请求费与网络费都需另测。

小记录     10,000 × 20 × 1 KB × 30  =   6 GB/月
大结果     10,000 ×  1 × 2 MB × 30  = 600 GB/月
条目数     10,000 × 20 × 30         = 600 万条/月

大结果内联，数据库承接约 606 GB/月；写到对象存储，数据库承接约 6 GB/月加引用，对象侧接住约 600 GB/月。总字节大致还在。收益是一次“打开最近会话”可以只查轻量索引和当前页，备份热库也不用反复携带大结果。如果产品承诺永久保留明细，还得单独给那 600 GB 的逐月累积付钱。

这里有两次独立决策。大结果外置发生在活跃会话里，依据单条内容大小和读取方式。整段历史归档发生在会话变冷以后，依据回访频率、保留期限和可接受的恢复等待。可以把已封存的序号区间压成 JSONL 分段，在数据库登记起止序号、对象版本和校验值。先校验归档并切换读取目录，再回收热副本。此时用户突然追问，新的记录继续追加到末尾；翻旧页才取对应的归档分段。

外置阈值值得用实际流量挑。拿一周样本，按工具统计结果大小的 P50、P95、P99，以及七天内有多少结果被完整重读。分别模拟 32 KB、128 KB、512 KB 的切点，看热库少写多少、每天多多少次对象 GET、恢复首条响应的 P95 慢多少。10 MB 的偶发报表和每轮必读的 40 KB 配置，很可能应该采用不同策略。删除一个租户的数据时，归档、摘要、缓存和仍在保留期内的备份也要有各自的到期路径。

用户问“第二批呢”，实际读哪几条#

打开聊天页，按游标读最近一页，显示建单回执和查询摘要。只有用户展开明细时才取 A。继续问原因，先取带覆盖序号的摘要、其后的完整交互和本轮问题。摘要至少保留三个批次的标识、原查询时间范围与产物引用。如果第一批和第二批的差异藏在错误码里，就到 A 中提取这两个批次的相关行，再把它们放进预算内。不能访问或已过期时，明确告诉用户依据缺失；重新查到的是新数据，要标上新的查询时间。

排查当时为什么建单，沿第 44 条回看第 43 条的原始证据和当时使用的工具版本。若产品还要回答“模型当时具体看到了什么”，应记录该次模型调用使用的条目区间、摘要版本、系统提示版本、工具定义版本和最终请求摘要值。仅有哈希可以校验，无法还原内容；需要逐字核对的场景，应在授权和保留策略允许下保存实际请求，或保存足以重建请求的不可变输入。即使输入相同，重新请求模型也不能保证得到同一答案。

我会让摘要带上 through_seq 和策略版本。线上试一种更短的摘要时，可以回到授权范围内的历史重建，再拿“第一批和第二批有何不同”这样的追问对照答案。这样压缩可以做实验；一旦用新摘要覆盖了唯一原文，就失去了验证它漏掉什么的机会。关于消息如何进入有限的模型窗口，可以接着读《Agent 的上下文管理》。

最值得做的验收：在第 44 条之后拔掉电源#

假设工单系统已创建 O-318，但运行时还没写第 45 条就退出。此时 transcript 能证明“发起过建单”，无法证明远端是否成功。新的 worker 应带着原先持久化的幂等键 K 查询或重试，让支持幂等的下游返回同一张工单，再补写结果。遇到既不能查单、又不接受幂等键的接口，就把状态记为“结果待核对”，交给人工确认。数据库的唯一键能挡住两条重复记录，挡不住远端创建两张工单。

如果今天从零开始做，我会先交付三件能验收的事：会话能按序翻页；换一台 worker 能继续追问并找回指定批次；在建单回执写入前杀掉进程，恢复后外部系统仍只有一张单。跑通以后再根据工具结果大小和冷会话回访率决定外置与归档阈值。好的存储设计最终体现在一个很平常的瞬间：用户隔天回来问“第二批呢”，系统找得到昨天的证据，也记得那张工单已经建过了。
