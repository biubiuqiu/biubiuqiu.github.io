一个不可见字符，为什么让数据同步字段错位？

原文发表于 2022-02-09 · Denis Wen

Sqoop 1.4.7 / Hive 2.1.1 · 历史实践记录

相同的同步命令，大部分表都正常，只有几张表不断报类型转换错误。最后，线索落在了一个平时看不见的字符上。

问题：相同配置，字段却发生了错位

这次记录使用的是 Sqoop 1.4.7 和 Hive 2.1.1。从 Hive 向 MySQL 同步数据时，几张特定的表出现字段错位，继而报出类型转换错误。其他表使用相同配置可以正常同步，于是排查方向转向了数据本身。

先把问题缩小到一条数据

定位问题数据花了两天。方法很朴素：手工二分。假设有一万条记录，先尝试同步其中五千条，再根据结果继续缩小范围，直到找到能复现错误的数据。

把 Hive 在 HDFS 上的数据文件取下来后，用 cat 查看，内容看起来正常。换成 vim，却发现其中夹着一个显示为 ^@ 的字符。继续对比发现，包含这个字符的记录会同步失败，不包含它的记录则正常。

这里的 ^@ 对应 NUL 字符，也就是 Unicode 的 U+0000。它与空字符串是不同的概念：字符串里实际存在一个字符，只是通常不可见。

为什么不是普通的字符串内容？

最初的疑问是：既然已经通过 --fields-terminated-by 指定了字段分隔符，NUL 为什么没有被当作普通内容，而是影响了解析结果？

为了解答这个问题，我查看了 Sqoop 1.4.7 的源码。记录解析器使用状态机处理输入，涉及四类字符：

参数解析器里的作用
--enclosed-by字段包围字符
--escaped-by转义字符
--fields-terminated-by字段分隔符
--lines-terminated-by记录分隔符

关键线索在获取字段包围字符的方法注释里。未指定时，它用 \000 表示“无”。而输入数据中的 NUL，在 Java 中可以写成 \u0000。两种写法表示的是同一个字符：

char a = '\u0000';
char b = '\000';
System.out.println(a == b); // true

原文通过读取问题文件、调试字符值，结合状态机中对包围字符和转义字符的判断，将字段错位定位到了输入字符与这些默认值的冲突上。

当时的处理办法

原文采用的处理方式是显式指定 --enclosed-by 和 --escaped-by，避免沿用与问题数据冲突的默认值。实际取值需要结合输入格式验证，不能任意挑一个字符就认为不会再发生冲突。

留下来的排查思路

这次经历里，最有用的是逐步缩小问题的过程：先对比正常与异常数据，再从显示差异找到不可见字符，最后进入解析器的状态转换逻辑。错误信息指向类型转换，原因却藏在更早的数据解析阶段。
