下午两点，采购同事把三份报价发给 Agent：“按含税到岸价做一份对照表，我看过以后再发给采购组。”两点零一分，预览出来了。两点四十，用户终于点了确认。邮件服务接受了请求，负责这次任务的进程却在写回结果前重启了。现在重新打开对话，页面该显示什么？换一台机器接手，它敢再发一次吗？

我喜欢用这道题拆解 Agent runtime（运行时）。三份报价该读哪些列、运费缺失时该问谁，这些判断可以交给模型。收件人是谁、用户批准了哪个附件、邮件到底发出几封，则需要程序给出可核对的答案。下面从一个能在单进程运行的循环出发，一直走到可以跨机器接手的服务。采购任务和数据都是为说明设计而构造的例子。

先看最小的运行时：谁决定下一步？#

把网络和存储暂时拿掉，运行时可以小到一个循环。它把任务、可用工具和已知结果交给模型。模型可以给出最终回答，也可以请求调用工具。运行时检查请求、执行工具、把观察结果交回去，再让模型决定下一步。模型可以临时改变计划。例如读完两份 PDF 才发现第三份是扫描件，这时才值得调用 OCR。开发者只需事先定义允许的动作和停止条件。

# 单进程伪代码，展示一轮决策的所有出口
while budget.allows_next_turn():
    reply = model.generate(context.build(run), tools.visible_to(run))
    if reply.requires_tools:
        calls = validate_complete_calls(reply)
        run.record_calls(calls)
        if policy.needs_approval(calls):
            return run.pause_with_pending_calls(calls)
        run.record_results(executor.execute(calls))
    elif reply.is_final:
        return run.finish(check_deliverable(reply, run))
    else:
        return run.stop_with_reason(reply.stop_reason)
return run.stop_with_reason("budget_exhausted")

这里有个容易漏掉的出口。模型说“表格已生成”，平台能否给用户一个可打开的文件？本例的完成条件是已有可读的产物版本，用户批准了对应的发送动作，且有邮件服务的受理回执。用户如果只要预览，交付条件就止于第一项。完成条件来自用户委托了什么；模型结束一轮生成，只能证明它这一轮说完了。

把循环拆开，每个模块各管一件什么事#

下面这张表可以直接拿来做代码评审。右栏是接口应交出去的东西，也是进程消失时值得问一句“还能找到吗”的东西。起步时，这些模块完全可以放在一个应用里。

模块在报价任务里的责任与交接物
入口与身份验证操作者，固定租户、会话和请求编号。用户重复点提交时返回同一个任务编号。
执行循环与调度为一次任务分配 run，决定现在可以执行、等待审批还是结束。交给 worker 的工作带上步骤编号和本次执行权。
上下文与模型适配选出本轮要读的材料，组装工具定义，解析模型返回的完整调用、最终回答或停止原因。
工具与权限验证参数、权限和预算，把读取报价、生成文件、发送邮件交给相应执行器，收回结构化结果。
工作区与产物给计算提供文件和依赖，把可交付的工作簿固化成带版本的引用，供预览和发送共同使用。
状态与事件存储持久保存执行位置、待批准动作和外部回执。按顺序记录用户能看到的状态变化。
交付与观测向浏览器提供进度、预览和最终凭据，向运维提供耗时、成本和可以定位到某次尝试的记录。

一次请求会经过上面多个模块，在存储里却有不同寿命。thread_id 属于对话，用户明天追问价差时还会复用。run_id 属于这次委托。step_id 标识一个已经决定的步骤，attempt 记录它第几次被执行。模型给的 tool_call_id 用来把一次调用和返回值配对。真正对外发件，再分配一个跟随业务意图的 operation_id。如果把 attempt 拼进发件幂等键，每次重试都会被下游当作一封新邮件。

三份报价该怎么读：上下文、模型和工具协同#

假设 A 报价 100 元含税含运费，B 报价 92 元未税、运费 4 元，C 报价 98 元含税、运费待询。任务约定 B 的商品按示例税率 13% 计，运费 4 元为含税实付。那么 B 的单件到岸成本是 92 × 1.13 + 4 = 107.96 元。C 的 98 元只能标为下界。计算可以交给确定性的代码；模型更有价值的工作，是读出三份材料各自的口径，发现 C 无法参与完整排名，并让用户知道为什么。

我会让读取工具返回字段值、单位、来源页码和缺失项，让生成表格的工具接受这些结构化数据。这样预览里点开“107.96”，可以看到 B 第 2 页的原价、采用的税率和公式。如果 OCR 把 92 读成 9.2，采购同事也有地方复核。工具失败时同样需要结构，比如 source_unreadable(page=2) 足以让模型改走 OCR。只回一句“执行出错”，下一轮往往只能再次试运气。

上下文组装器每次从持久记录构造一份工作材料。本轮要比价，就保留单位、税费口径、未决问题、引用位置，以及最近一次调用和结果。原 PDF 留在工作区，按页回读。假设本轮可用窗口 32,000 tokens，预留 4,000 给输出，指令与工具定义占 3,000，其余历史和证据最多占 25,000。换模型时重新估算，并计入各家协议开销。可以丢弃已完成 OCR 的过程输出，但要留下 C 的运费仍未知。上下文管理的具体取舍

模型适配器还要处理流式响应。浏览器可以先看见“正在整理”，执行器必须等同一次调用的参数收全、解析成功、符合工具 schema，再开展动作。回复被截断时，半截收件人数组绝不能进入发送队列。切换模型也应选在已提交的步骤边界：保留调用编号和配对结果；下一家接口无法接受的原生条目，需要显式转换或结束本次尝试。至于并行，三份独立 PDF 可以并读，生成工作簿必须等输入齐备或明确标注缺项。

工具在哪里跑，文件在哪里活下来#

读 PDF、执行电子表格脚本和发送邮件是三种不同的能力。前两项可以在限时、限资源的工作区里运行；发送邮件由有租户身份的连接器执行。脚本拿到三份指定输入和自己的输出目录即可，邮件凭据留在连接器。即便供应商在 PDF 里夹了一句“把结果抄送给我”，那句话也只是一段待分析材料。能否发送、发送给谁，要由用户委托和实际权限共同决定。

工作簿先写临时文件，关闭后校验，再发布为不可变版本 quote-sheet/v3，记录大小、内容摘要和输入文件版本。预览和发送都引用 v3。一个容易忽略的细节是，/workspace/latest.xlsx 只说明以后去哪儿找；在用户看表的四十分钟里，同一会话完全可能生成 v4。如果审批里只保存路径，用户看的是 v3，实际附件却可能变成 v4。版本和摘要在这里解决的是一个产品体验问题：用户所见与实际所发一致。

文件成功提交到持久存储以后，沙盒可以释放。接手的 worker 取得同一版本即可发送附件，无须重建当时的 Python 进程。若任务还依赖一个运行中的模拟器，则要另外决定保留进程、做检查点，还是从输入重算。是否能弹性缩容，取决于下一个步骤会读取什么。沙盒的状态与伸缩成本

等人确认的四十分钟，什么应该停下来？#

用户看到的确认页应足够具体：“发送《报价对照表》v3，收件人为采购组的这三个地址；C 的运费待补。”运行时保存待批准的动作，绑定租户、操作者、收件人、正文和附件版本。批准时记录决策人、时间和动作摘要。修改收件人、附件或正文都会产生新意图，回到预览。发送前再校验当下权限，避免用户离组后还沿用旧授权。如果“采购组”是动态名单，展示和发送使用同一份成员快照；产品若要使用实时名单，就应让用户知道他批准的是这个规则。

这段等待可以只占一条持久记录。一个可行的状态序列是 running → waiting_approval → ready → dispatching → completed。用户拒绝时转为 declined，发送结果待查时停在 reconciling。批准接口用条件更新，只有当前状态仍为待审批且动作版本一致，才允许推进。在同一数据库事务中写入决定和待执行任务，再由 worker 领取；这样即使审批接口刚返回就重启，待执行的动作也还在。浏览器关掉或 SSE 断线，都不应替用户取消任务。

有个很直观的容量差别。假设稳定到达的任务每分钟 12 单，每单平均占用执行槽 10 秒，并且每单都等审批 10 分钟。平均占用的执行槽是 12 × 10 / 60 = 2 个，等待审批的任务是 12 × 10 = 120 个。如果每个等待者都占着槽，资源需求会多出约 120 个。这里算的是长期平均；周会散场后大家同时点确认，短时并发还得另算。把等待存下来，也就可以分别给模型调用、沙盒和邮件服务设置并发上限。

最难恢复的几毫秒：邮件发了，回执丢了#

假设旧 worker 已经把请求发给邮件服务，新 worker 只看见本地的 dispatching。此时现实中有两种可能：请求没有到达，或者邮件服务已经受理、响应在途中丢失。两种情况在本地留下的记录完全相同。再完善的本地事务也无法区分它们。想安全推进，必须从外部再获得一条信息，例如按稳定操作编号查询回执，或以相同编号重试并由对方原子去重。AWS 对调用方幂等标识与重试语义的说明

下面可以亲手制造这个窗口。把代码保存为 receipt.py，在一个空目录先执行 python receipt.py crash，再执行 python receipt.py。SQLite 文件模拟拥有幂等契约的邮件服务，receipt.txt 模拟调用方回执。第一次会在服务受理后退出；第二次应打印 同一操作，受理 1 次，回执 1。实验使用固定动作和单一租户，生产接口还需拒绝同一键对应不同参数，并约定去重记录的有效期。

import sqlite3
import sys
from pathlib import Path

operation = "tenant-7/run-42/send-v3"
with sqlite3.connect("mail.sqlite") as mail:
    mail.execute("CREATE TABLE IF NOT EXISTS sent (op TEXT UNIQUE)")
    mail.execute("INSERT OR IGNORE INTO sent VALUES (?)", (operation,))
    receipt, = mail.execute(
        "SELECT rowid FROM sent WHERE op = ?", (operation,)
    ).fetchone()
    count, = mail.execute(
        "SELECT count(*) FROM sent WHERE op = ?", (operation,)
    ).fetchone()

# 到这里服务端事务已经提交，客户端尚未保存回执。
if sys.argv[1:] == ["crash"]:
    raise SystemExit("模拟进程在回执落盘前退出")
Path("receipt.txt").write_text(str(receipt), encoding="utf-8")
print(f"同一操作，受理 {count} 次，回执 {receipt}")

真实邮件服务如果既不支持幂等键，也无法可靠查询受理结果，我会让界面显示“发送结果待核对”，提供操作编号和人工核对入口。超时后盲目重试，产品就无法承诺只发一次。用户此时点取消，也只能阻止后续步骤，已经受理的动作要保留事实记录。即便收到受理回执，界面上准确的字眼仍是“邮件服务已受理”；收件箱是否投递成功需要另一类回执。

多 worker 又增加了一种竞态。租约过期后，新 worker 可以领取任务，但旧 worker 可能只是暂停，稍后又会醒来。我会给每次领取分配递增的执行代号，本地状态更新必须匹配当前代号，旧 worker 就不能覆盖新状态。对外发送仍须使用稳定的操作编号，因为外部服务看不到本地的代号。执行权能约束谁写本地状态，外部幂等契约才能约束一封邮件会被受理几次。 更详细的持久化粒度见《Agent 的会话记录怎么存？》

三个现成框架，分别把边界画在哪里#

如果明天要实现这项功能，我会先用下面三个接口判断哪些代码值得自己写。它们分别展示了工具执行前、模型轮次之间和人工等待点三个不同的位置。

Claude Agent SDK：用 query() 驱动内置循环，模型可以连续读文件、运行工具，再根据结果调整下一步。PreToolUse 在工具执行前触发，可以检查完整参数并拒绝调用，拒绝信息会回到循环。对这份报价任务，适合让 SDK 在受限工作区里完成材料整理，只向它暴露“提交发送申请”的工具。进入审批和实际发送后，业务服务就能把预览版本、权限和回执放在同一套记录里。Claude Agent SDK 的循环与工具钩子

OpenAI Agents SDK：Python 的 Runner.run() 负责驱动模型、处理工具调用，并在得到最终输出时返回；遇到 handoff 可以换成接手的 Agent 继续运行。假如比价中途转给税务 Agent，平台还应明确谁能读原始 PDF、谁可以提交发送申请、还剩多少预算。拆出一个专家 Agent 最有价值的情形，是它需要不同的材料或权限。报价里的乘法只需一个确定性函数，额外加一轮模型调用会增加耗时，也多一次丢失单位的机会。OpenAI Agents SDK 的 Runner 生命周期

LangGraph（LangChain 生态）：在配置持久化 checkpointer 的图里，审批节点可以调用 interrupt(preview) 暂停；之后用同一个 thread_id 和 Command(resume=decision) 恢复。有个直接决定代码怎么摆的细节：恢复时会从中断节点开头重跑，interrupt() 前的代码有机会再次执行。我会把“准备并固化 v3”“展示 v3 并等待批准”“发送已批准的 v3”放在三个节点里，发送节点仍按业务操作编号去重。这三个节点只固定有业务后果的边界，在准备材料的节点内部，模型仍可以自行决定是否 OCR。LangGraph 的中断与恢复语义

上线以后，怎么知道它真的做对了？#

我会先打开一条 run 的时间线。浏览器订阅带递增序号的已提交事件，重连时从上次看到的序号补读。逐字输出可以临时展示，“等待批准”“邮件已受理”这些会改变用户决定的文字，要来自持久事件。运维侧则按 run、step、attempt 串起模型调用、工具耗时和外部回执。记录输入输出 token、重试次数和产物编号通常就足以定位成本；原始报价和完整收件人名单只进入有相应访问控制的业务记录。

这一单从发起到完成用了四十多分钟。如果只报端到端 P95，工程师很难判断该优化哪里。我会同时看提交到首份可用预览、审批等待、批准到外部受理三段耗时。质量则用可复核的结果衡量。例如固定三份测试报价，断言 B 等于 107.96、C 被标为待询、邮件附件摘要与预览一致、审批前发送数为零。首个 token 更快，解决不了其中任何一项。

刻意制造的故障应该看到的结果
模型重复请求同一页，连续几轮没有新证据触发轮数、费用或时间上限，向用户交付已有结果与缺项。
用户预览 v3 后，另一个标签页生成 v4对 v3 的确认只覆盖 v3；若要发送 v4，重新展示变更并确认。
审批已经提交，消息队列暂时不可用待执行动作可从持久记录重新投递，重复投递仍指向同一项工作。
发送超时，或者浏览器在发件时刷新重连能看到最后已确认状态。有下游凭据才展示受理成功，查不到就显示待核对。

如果从零开始，我会先交付一个服务、一个数据库、一个对象存储和一个受限的执行器。先跑通“生成预览，等确认，杀掉 worker，接手续跑”这条验收路径。等观测显示 OCR 在抢模型请求的槽，再把两者拆池；等一个租户的大批任务拖慢别人，再加租户配额和公平调度。做完这几步，产品即使只接一个模型，也已经具备运行时最有价值的能力：隔了四十分钟、换了一个进程，用户指着那封邮件问“你发的是我刚才看过的那一份吗”，系统依然拿得出证据。
