午後 2 時、購買担当者がエージェントに三社の見積書を渡した。「税込みの着地原価で比較表を作って。私が確認してから購買チームに送ってね」。2 時 1 分にはプレビューができた。担当者が承認したのは 2 時 40 分。メールサービスが送信要求を受け付けた直後、結果を記録する前に担当プロセスが再起動した。会話を開き直したとき、画面には何を表示すべきだろう。別のマシンが引き継いだら、もう一度送ってよいのだろうか。

エージェントのランタイムを分解して考えるとき、私はこの例をよく使う。三社の見積書のどの列を読むか、運賃の記載がなければ誰に聞くかは、モデルに判断を任せられる。一方、誰に送るのか、ユーザーがどの添付ファイルを承認したのか、メールが実際に何通送られたのかには、プログラムが検証可能な答えを出さなければならない。一つのプロセスで動く小さなループから出発し、別のマシンで引き継げるサービスまでをたどってみよう。購買業務と数値は設計を説明するための架空の例だ。

最小のランタイムで、次の一手を決めるのは誰か#

ネットワークとストレージをいったん脇に置けば、ランタイムは一つのループにまで小さくできる。タスク、使えるツール、既に分かった結果をモデルに渡す。モデルは最終回答を出すか、ツールの実行を要求する。ランタイムはその要求を検査し、ツールを実行し、観察結果をモデルへ返して次の判断を仰ぐ。モデルは途中で計画を変えられる。二つの PDF を読んで、三つ目がスキャン画像だと気づいた段階で初めて OCR を呼べばよい。開発者が先に定義しておくのは、許可される操作と停止条件だ。

# 一つのプロセスで動く疑似コード。意思決定の一ターンにあるすべての出口を示す。
while budget.allows_next_turn():
    reply = model.generate(context.build(run), tools.visible_to(run))
    if reply.requires_tools:
        calls = validate_complete_calls(reply)
        run.record_calls(calls)
        if policy.needs_approval(calls):
            return run.pause_with_pending_calls(calls)
        run.record_results(executor.execute(calls))
    elif reply.is_final:
        return run.finish(check_deliverable(reply, run))
    else:
        return run.stop_with_reason(reply.stop_reason)
return run.stop_with_reason("budget_exhausted")

ここには見落としやすい出口がある。モデルが「表ができました」と言ったとき、本当に開けるファイルをユーザーに渡せるだろうか。この例の完了条件は、読める成果物の版が存在し、対応する送信操作をユーザーが承認し、メールサービスの受付記録があることだ。プレビューだけを頼まれた場合は最初の条件で足りる。完了条件を決めるのはユーザーの依頼内容だ。モデルの生成終了が示すのは、そのターンの発話が終わったことまでである。

ループを分解すると、各モジュールには何が残るか#

次の表はコードレビューにも使える。右の列にはインターフェースが次へ引き渡すものを挙げた。一つずつ、プロセスが消えても見つけられるかを確認したい。初期段階なら、すべて一つのアプリケーションに収めてもよい。

モジュール見積比較での役割と引き渡すもの
受付と本人確認操作者を認証し、テナント、会話、リクエスト番号を結び付ける。ユーザーが二度送信しても同じタスク番号を返す。
実行ループとスケジューリング依頼に run を割り当て、実行可能か、承認待ちか、終了かを決める。ワーカーにはステップ番号と今回の実行権を渡す。
コンテキストとモデルアダプター今回読む資料を選び、ツール定義を組み立て、モデルが返した完全な呼び出し、最終回答、停止理由を解析する。
ツールと権限引数、権限、予算を検証し、見積の読み取り、ファイル生成、メール送信をそれぞれの実行器に渡して構造化結果を受け取る。
ワークスペースと成果物計算に必要なファイルと依存関係を用意する。納品するワークブックを版付きの参照として確定し、プレビューと送信で共有する。
状態とイベントの保存実行位置、承認待ちの操作、外部の受付記録を永続化する。ユーザーに見える状態変化を順番に記録する。
結果の提供と可観測性ブラウザーには進捗、プレビュー、最終的な証跡を届ける。運用側には所要時間、費用、特定の試行までたどれる記録を渡す。

一件の要求は複数のモジュールを通るが、保存する識別子の寿命は異なる。thread_id は会話に属し、翌日に価格差を質問するときにも使う。run_id は今回の依頼に属する。step_id は実行すると決めた手順を識別し、attempt はその何回目の試行かを示す。モデルの tool_call_id はツール呼び出しと返り値を対応付ける。外部にメールを送るときは、業務上の意図に対応する operation_id を別に割り当てる。送信の冪等キーに attempt を含めると、再試行のたびに下流は新しいメールとして扱ってしまう。

三社の見積をどう読むか。コンテキスト、モデル、ツールの協働#

A 社は税・運賃込みで 100 元、B 社は税抜き 92 元に運賃 4 元、C 社は税込み 98 元で運賃は要照会とする。ここでは B の商品に例示税率 13% を適用し、運賃 4 元は税込み実支払額とする。B の一個あたりの着地原価は 92 × 1.13 + 4 = 107.96 元。C の 98 元は下限としか言えない。計算は決定的なコードに任せられる。モデルの価値が出るのは、三社それぞれの金額の前提を読み取り、C の順位をまだ確定できないこととその理由を伝えるところだ。

読み取りツールには項目値、単位、出典ページ、欠落項目を返させ、表を作るツールにはそれを構造化データとして渡したい。するとプレビューの「107.96」を開けば、B の 2 ページ目の元値、適用税率、計算式にたどれる。OCR が 92 を 9.2 と読み違えたときも担当者が照合できる。失敗にも構造が必要だ。source_unreadable(page=2) なら次に OCR を試せる。「実行エラー」とだけ返されても、次のターンはまた手探りになる。

コンテキストを組み立てる処理は、毎ターン永続記録から作業用の資料を作る。価格比較なら、単位、税と運賃の扱い、未解決の問い、参照箇所、直近の呼び出しと結果を残す。元の PDF はワークスペースに置き、必要なページだけ読み返す。使えるウィンドウが 32,000 トークン、出力用に 4,000、指示とツール定義に 3,000 を使えば、履歴と根拠に使えるのは最大 25,000。モデルを替えたら、各社のプロトコルのオーバーヘッドを含めて見積もり直す。完了した OCR の途中出力は捨てても、C の運賃が未確定という事実は残す。コンテキスト管理における具体的な取捨選択

モデルアダプターはストリーミングも扱う。ブラウザーでは先に「整理中」と表示できるが、実行器は一回分の引数がそろい、解析でき、ツールスキーマに適合してから動く。出力が途中で切れたとき、受信者配列の断片を送信キューに入れてはいけない。モデルの切り替えもコミット済みのステップ境界で行う。呼び出し番号と対応する結果を保ち、次のプロバイダーが扱えないネイティブ項目は明示的に変換するか、その試行を終了する。独立した三つの PDF は並列に読めるが、表の生成は入力がそろうか、欠落を明記できるまで待つ。

ツールが動く場所と、ファイルが生き残る場所#

PDF の読み取り、表計算用スクリプトの実行、メール送信は別々の能力だ。前の二つは時間と資源を制限したワークスペースで実行できる。メールはテナントに対応した認証主体を持つコネクターから送る。スクリプトには指定された三つの入力と自分の出力先だけを与え、認証情報はコネクターに残す。たとえ取引先が PDF に「私も CC に入れて」と書き込んでも、それは分析対象の一文にすぎない。送ってよいか、誰に送るかはユーザーの依頼と実際の権限で決まる。

ワークブックは一時ファイルに書き、閉じて検証した後、不変バージョン quote-sheet/v3 として公開する。サイズ、内容のダイジェスト、入力ファイルの版も記録し、プレビューと送信の両方が v3 を参照する。見落としやすいのは、/workspace/latest.xlsx が「後で探す場所」しか示さない点だ。担当者が表を見る四十分の間に、同じ会話で v4 ができることもある。承認時にパスだけ保存すると、見たのは v3 なのに v4 が添付されかねない。版とダイジェストは、目で確認したものと実際に送るものを一致させる仕組みである。

ファイルが永続ストレージにコミットされたら、サンドボックスは解放できる。引き継ぐワーカーは同じ版を取り出して添付すればよく、以前の Python プロセスを復元する必要はない。まだ動作中のシミュレーターが必要なら、プロセスを維持するか、チェックポイントを取るか、入力から再計算するかを別途決める。スケールダウンできるかは、次の手順が何を読むかで決まる。サンドボックスの状態とスケーリング費用

人の確認を待つ四十分、何を止められるか#

確認画面には「見積比較表 v3 を購買チームの次の三アドレスに送信します。C の運賃は未確定です」と具体的に表示する。ランタイムは承認待ちの操作を保存し、テナント、操作者、受信者、本文、添付の版を結び付ける。承認時には決定者、時刻、操作のダイジェストを記録する。受信者、添付、本文のいずれかを変えれば新しい意図なのでプレビューに戻る。送信前にはその時点の権限を再確認し、ユーザーがチームから外れた後まで古い許可を使わない。「購買チーム」が動的な名簿なら、表示と送信で同じメンバーのスナップショットを使う。常に最新の名簿を使う製品なら、そのルールを承認するのだと明示する。

待ち時間に必要な資源は永続レコード一件で済む。状態遷移の一例は running → waiting_approval → ready → dispatching → completed。却下なら declined、送信結果が不明なら reconciling にとどめる。承認 API では条件付き更新を使い、まだ承認待ちで操作の版が一致するときだけ進める。同じデータベーストランザクションに決定と実行待ちタスクを書き、ワーカーが取得する。これなら承認 API が応答した直後に再起動しても、待機中の操作は残る。ブラウザーを閉じたり SSE が切れたりしただけで、ユーザーに代わってタスクを取り消してはいけない。

容量に与える差ははっきりしている。毎分 12 件のタスクが安定して届き、一件が平均 10 秒間実行枠を使い、毎回 10 分間承認を待つとする。平均使用枠数は 12 × 10 / 60 = 2、承認待ちの平均件数は 12 × 10 = 120。待機中も枠を保持させれば約 120 枠余計に要る。これは長期平均だ。定例会議の終了直後に全員が承認を押すような瞬間的な集中は別に計算する必要がある。待機を永続化すれば、モデル呼び出し、サンドボックス、メールサービスにそれぞれ異なる同時実行上限を設けられる。

復旧が最も難しい数ミリ秒：送信は受理され、受付記録が消えた#

旧ワーカーはメールサービスに要求を送ったが、新ワーカーに見えるのはローカルの dispatching だけだ。要求は届いていないかもしれないし、サービスが受理した後、応答だけが途中で失われたかもしれない。ローカルの記録はどちらも全く同じだ。どれほど厳密なローカルトランザクションでも区別できない。安全に進めるには外部からもう一つ情報を得る。例えば、固定の操作番号で受付を照会するか、同じ番号で再試行し、先方に原子的に重複を除いてもらう。呼び出し元が指定する冪等識別子と再試行の意味を解説した AWS の記事

この隙間は手元でも作れる。次のコードを空のディレクトリに receipt.py として保存し、python receipt.py crash、続けて python receipt.py を実行する。SQLite ファイルは冪等性を保証するメールサービスの代役で、receipt.txt は呼び出し元が持つ受付記録だ。初回はサービスが受理した後に終了し、二回目には 同一操作の受付件数 1、受付番号 1 と表示されるはずだ。実験では操作を固定し、テナントも一つにしている。本番の API では同じキーで異なる引数を受け付けず、重複排除記録の有効期限も決める必要がある。

import sqlite3
import sys
from pathlib import Path

operation = "tenant-7/run-42/send-v3"
with sqlite3.connect("mail.sqlite") as mail:
    mail.execute("CREATE TABLE IF NOT EXISTS sent (op TEXT UNIQUE)")
    mail.execute("INSERT OR IGNORE INTO sent VALUES (?)", (operation,))
    receipt, = mail.execute(
        "SELECT rowid FROM sent WHERE op = ?", (operation,)
    ).fetchone()
    count, = mail.execute(
        "SELECT count(*) FROM sent WHERE op = ?", (operation,)
    ).fetchone()

# サーバー側のトランザクションは確定済み。クライアントはまだ受付番号を保存していない。
if sys.argv[1:] == ["crash"]:
    raise SystemExit("受付番号を保存する直前のプロセス終了を再現")
Path("receipt.txt").write_text(str(receipt), encoding="utf-8")
print(f"同一操作の受付件数 {count}、受付番号 {receipt}")

実際のメールサービスが冪等キーに対応せず、受付結果を確実に照会することもできないなら、画面には「送信結果を要確認」と表示し、操作番号と人が照合する手段を示す。タイムアウト後に無条件で再試行すれば、送信が一回だけだとは約束できない。この時点のキャンセルで止められるのは後続ステップまでで、既に受理された事実は記録に残す。受付番号が返ったときも、正確な表現は「メールサービスが受理しました」だ。受信箱への配達成功を示すには別種の記録が要る。

複数ワーカーではもう一つ競合が起きる。リースが切れて新ワーカーがタスクを取得しても、旧ワーカーは一時停止していただけで、後から動き始めるかもしれない。私なら取得のたびに単調増加する実行トークンを発行する。ローカルの状態更新は現在のトークンと一致するときだけ許し、古いワーカーによる上書きを防ぐ。外部サービスにはローカルのトークンが見えないので、送信には引き続き固定の操作番号を使う。実行権が制御するのは誰がローカル状態を書けるかだ。一通のメールが何回受理されるかを制御するのは外部の冪等性契約である。 永続化の粒度についてはエージェントの会話記録をどう保存するかで詳しく扱う。

既存の三つのフレームワークはどこに境界を引くか#

明日この機能を実装するなら、どこを自前で書くか決める前に次の三つのインターフェースを見る。ツール実行の直前、モデルのターンの間、人の判断を待つ箇所という、それぞれ異なる位置を扱っている。

Claude Agent SDK：query() が内蔵ループを駆動し、モデルはファイルを読み、ツールを実行し、結果に応じて次の一手を変えられる。PreToolUse はツール実行前に起動し、そろった引数を調べて呼び出しを拒否できる。拒否の情報はループに戻る。見積タスクなら、制限されたワークスペースで SDK に資料を整理させ、送信に関しては「送信申請を提出する」ツールだけを公開したい。承認と実送信を業務サービスが受け持てば、プレビューの版、権限、受付記録を同じ記録体系に収められる。Claude Agent SDK のループとツールフック

OpenAI Agents SDK：Python の Runner.run() はモデルを駆動し、ツール呼び出しを処理し、最終出力で復帰する。handoff が起きれば別のエージェントに引き継いで実行を続けられる。比価の途中で税務担当エージェントに渡すなら、誰が元の PDF を読めるか、誰が送信申請を出せるか、残り予算はいくらかをプラットフォームで明確にする。専門エージェントを分ける価値が高いのは、必要な資料や権限が異なるときだ。単価の掛け算なら決定的な関数で足りる。モデル呼び出しを増やせば時間がかかり、単位を取り違える機会も増える。OpenAI Agents SDK の Runner のライフサイクル

LangGraph（LangChain エコシステム）：永続 checkpointer を設定したグラフでは、承認ノードで interrupt(preview) を呼んで中断し、同じ thread_id と Command(resume=decision) で再開できる。コードの配置に効く注意点がある。再開時には中断したノードの先頭からやり直すので、interrupt() より前の処理がもう一度走る可能性がある。私なら「v3 を用意して確定する」「v3 を見せて承認を待つ」「承認済みの v3 を送る」を三つのノードに分ける。送信ノードでは業務上の操作番号で重複を除く。この三つで固定するのは業務上の結果を伴う境界だけだ。資料準備ノードの中ではモデルが自分で OCR の要否を判断できる。LangGraph の中断と再開の意味

本番で正しく動いたことを、どう確かめるか#

まず一件の run のタイムラインを開きたい。ブラウザーは単調に増える番号付きのコミット済みイベントを購読し、再接続時には最後に見た番号から先を読み足す。生成中のテキストは一時表示でよいが、「承認待ち」「メール受理済み」のようにユーザーの判断を変える表示には永続イベントを使う。運用側は run、step、attempt でモデル呼び出し、ツールの所要時間、外部の受付記録を結び付ける。コストの調査には通常、入出力トークン数、再試行回数、成果物番号があればよい。見積書の原本と受信者名簿の全件は、相応のアクセス制御がある業務記録にのみ保存する。

この依頼の完了には四十分以上かかった。エンドツーエンドの P95 だけを報告しても、どこを改善すればよいかは分からない。提出から利用可能な最初のプレビューまで、承認待ち、承認から外部受理までの三つの時間も測る。品質は検証できる結果で測る。例えばテスト用の見積三社を固定し、B が 107.96、C が要照会、添付のダイジェストがプレビューと一致、承認前の送信数がゼロであることを検証する。最初のトークンを速く返せても、これらの条件が満たされたことにはならない。

意図的に起こす障害確認すべき結果
モデルが何ターンも同じページを要求し、新しい根拠が増えないターン数、費用、時間の上限で止まり、分かっている結果と不足項目をユーザーに渡す。
ユーザーが v3 を見た後、別のタブで v4 が生成されるv3 の承認は v3 だけを対象にする。v4 を送るなら変更を再度示し、承認を得る。
承認はコミットされたが、メッセージキューが一時的に使えない永続記録から待機中の操作を再投入できる。重複して投入されても同じ作業を指す。
送信がタイムアウトするか、送信中にブラウザーが更新される再接続後に最後の確定状態が見える。下流の証跡があれば受理済み、確認できなければ要照合と表示する。

ゼロから作るなら、まず一つのサービス、一つのデータベース、一つのオブジェクトストレージ、制限付きの実行器で始める。「プレビューを作る、承認を待つ、ワーカーを落とす、別のワーカーで続ける」という受け入れテストを通す。計測して OCR とモデル呼び出しが枠を奪い合っていればプールを分ける。あるテナントの大量投入で他が待たされるようになったら、テナント別クォータと公平なスケジューリングを導入する。ここまでできれば、接続するモデルが一つでも、ランタイムの大切な能力が備わる。四十分が過ぎ、プロセスが替わっても、「さっき私が見た版を送ったんだよね？」という問いに、システムが証拠を示せる。
