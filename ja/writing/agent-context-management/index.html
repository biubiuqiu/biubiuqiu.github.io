前回の続き

同じモデルを使っているのに、エージェント製品を替えると、長いタスクの結果がどうして変わるのだろう。私が注目したのは、各ターンで実際に何をモデルに見せているか、そして履歴の一部を省いた後も、どうやって作業の続きを正しく引き継ぐかという違いだ。

調査範囲 · 2026-11-13

Claude Code は公式の公開文書で確認できる挙動を扱う。Pi と OpenCode は特定のコミットのソースも調べた。OpenCode の対象は V2 である。以下では確認できた事実、筆者の分析、実装案を区別する。3 製品を同一条件でベンチマークしたものではない。トークン予算の数値と疑似コードは設計例として示す。

図で考える。コンテキストは今使っている机#

履歴全体が資料室なら、現在のコンテキストは机の上だ。机がいっぱいになったら引き継ぎメモを書き、古い資料を棚に戻せる。ただし、目標、守るべき制約、いま進めている作業は机に残したい。

まず 4 つの図を動かしてから、ソースの分析を読んでほしい。図中のトークン数、メッセージ、イベント番号は説明用の例である。

① 履歴とコンテキスト② 製品を比べる③ 予算を動かす④ バックグラウンド要約

1. 履歴、コンテキスト、記憶、実行環境を区別する#

筆者の分析。「エージェントは何を覚えているか」という問いには、少なくとも 4 つの意味がある。すべてを一つの messages 配列にまとめてしまうと、再開、モデル切り替え、圧縮の際に、何を復元するのかが曖昧になる。

層保持するもの混同しやすい点
セッション履歴ユーザーメッセージ、モデルの応答、ツール呼び出しと結果などのイベント保存したイベントすべてを次のターンで送るとは限らない。
現在のコンテキスト今回のモデルリクエストに実際に含まれる入力送信を省いても元データが削除されたわけではない。
長期記憶セッションをまたいで役立つ好み、事実、情報の所在を示す手掛かり履歴のすべてが長期的に保持すべき事実になるわけではない。
実行環境ファイル、プロセス、作業ディレクトリ、外部への副作用チャットを復元してもファイルやプロセスまで戻るとは限らない。

例えば、テストログ全体を履歴に保存しつつ、今回の入力には失敗の要点と該当箇所への参照だけを含められる。「このプロジェクトのテストコマンド」はプロジェクト指示に向いているかもしれない。一方、テストで生成したファイルはワークスペースに属する。それぞれ保存期間も復元方法も異なる。

そこで私は、各ターンの入力を次のような計算結果として捉える。今回の入力 = 指示 + タスクの状態 + 選択した履歴 + 必要な証拠。Anthropic のコンテキストエンジニアリングの解説でも、有限のウィンドウに収める情報を毎ターン選び直すことが重視されている。[12]

2. 3 製品はどこで複雑さを引き受けているか#

確認できた仕組みを並べてみよう。この比較だけで製品全体の優劣は決められない。

製品と根拠圧縮と再開読み取れる範囲
Claude Code · 公式文書自動または手動の圧縮、プロジェクト指示、オンデマンド読み込み、サブタスクごとの独立したコンテキスト公開された挙動から内部アルゴリズム全体を復元することはできない。
Pi · 特定コミットのソース構造化要約、保持境界、セッションツリー、コンテキストの投影原記録とモデルに見せるメッセージは別々に扱う。
OpenCode V2 · 特定コミットのソース要約と直近の内容、任意のバックグラウンド事前計算、独自の要約とプロバイダー標準の圧縮の区別V1 の pruning の説明をそのまま V2 に当てはめることはできない。

2.1 Claude Code はメインコンテキストへの流入を先に絞る#

確認できたこと。公式文書には自動圧縮のほか、要約の重点を指定できる /compact が記載されている。入り口での制御もある。スキルの全文は必要なときに読み込み、MCP のツール定義はツール検索まで読み込みを遅らせられる。サブエージェントのツール実行過程は独自のコンテキストに残り、メインのセッションには結果の要約が返る。[1]

つまり調節手段は圧縮以外にもある。大量の検索やログ調査といった副次的な作業を独立したコンテキストに任せれば、メインタスクが途中経過を毎回持ち歩かずに済む。ただしサブタスクでもトークンは消費される。fork は親のコンテキストを引き継ぐため、空のウィンドウを無償で得る操作ではない。[4]

確認できたこと。プロジェクト指示と Auto memory はセッション間で情報を引き継ぐ別の経路である。公式文書では短い MEMORY.md を入り口とし、トピック別のファイルを必要に応じて読む。調査時点では、入り口から読み込むのは先頭 200 行または 25 KB のうち先に達した方までだった。これは索引の読み込み上限であって、記憶ディレクトリ全体の容量ではない。[2]

筆者の分析。参考になるのは役割の分担だ。常駐するルールは行動を制約し、必要時に読む知識は情報を補い、その時点の要約は作業を引き継ぐ。すべてを膨張する一つの「恒久プロンプト」に書けば、会話が肥大化する問題を起動時に移しただけになる。

公開文書だけでは、Claude Code が要約対象を選ぶ厳密なアルゴリズム、すべての内部しきい値、フォールバックの分岐までは分からない。Claude API にあるコンテキスト管理機能を、Claude Code があらゆる経路で採用しているとも断定できない。

2.2 Pi は「次のターンに見せる内容」を再構築可能なビューにする#

確認できたこと。Pi の圧縮記録には summary、firstKeptEntryId、tokensBefore などのフィールドがある。調べたスナップショットでは、既定の予約量は 16,384 トークン、直近の内容を残す目標量は 20,000 トークンだった。前者は圧縮の発動、後者は保持量に関わる。両方が同じ「要約の長さ」を指すわけではない。分割時にはツール呼び出しと結果が切り離されないよう考慮する。[5]

既定値以上に興味深いのは構造だ。session-manager.ts は id と parentId でセッションの経路を表現する。 buildContextEntries() が現在の要約と保持区間を選び、 buildSessionProjection() がコンテキストの編集を適用してモデル用のメッセージを組み立てる。ビュー上では内容の変更や特定の記録の省略が可能だが、元のエントリは残せる。[7]

筆者の分析。上位のアプリケーションでは、履歴を出来事の記録、モデル入力をその記録から生成するビューとして扱える。そうすれば分岐、再生、圧縮のたびに一つの配列を破壊的に書き換える必要がない。ただし「当時送ったもの」を再構築できても、モデルの確率的な出力を再現したり、ツールが外部に及ぼした効果を取り消したりできるわけではない。

確認できたこと。Pi の既定の要約は、目標、制約、進捗、判断、次の手順、重要な背景を軸に構成される。トークン数は直近に得られた usage の値を使い、それ以後に追加されたメッセージの分を見積もる。要約時には会話をシリアライズして専用のリクエストを作る。不完全な要約や、ツールを呼ぼうとする要約応答も検査する。[6]

筆者の分析。引き継ぎに最低限必要なのは、「直前にどのツールを呼んだか」よりも「次に何をするか、別案をなぜ採れないか」という情報であることが多い。要約の出来は、会話の網羅率より後任が下せる判断で評価したい。

2.3 OpenCode V2 は圧縮自体をスケジュールする#

確認できたこと。V2 の文書によれば、要約と直近の内容を組み合わせて作業を再開する。直近部分の保持目標は既定で約 15,000 トークンで、buffer が予約領域を管理する。V1 の tail-turn や pruning の挙動は明確に区別されている。直近部分でも、長いツール出力は短縮され、添付データは短い説明に置き換わる。[8] 設定スキーマでも auto、keep.tokens、buffer の各フィールドを使用する。[11]

確認できたこと。通常の要約リクエストでは既存の会話プレフィックスをなるべく維持し、末尾に要約の指示を追加する。プロバイダー側のプロンプトキャッシュを再利用しやすくするためだ。実験的なバックグラウンド経路では先に要約候補を作って一時保存し、圧縮が本当に必要になった段階で適用するかを決める。モデル、指示、履歴のプレフィックスなどが変わると、そのまま再利用はできない。[9]

また、自前で生成するテキスト要約とプロバイダー標準の圧縮を区別する。後者では不透明なチェックポイントが返る場合があり、別環境に持ち出せるかはプロバイダーとモデルに依存する。圧縮後のモデル切り替えは model フィールドを替えるだけで済むとは限らない。[8]

筆者の分析。バックグラウンド要約で難しいのは LLM をもう一度呼ぶことより、候補が適用時にも現在のセッションに対応することを確かめる部分だ。文章の生成が終わってから、バージョンを条件とした状態更新が始まる。

3. 設計で重視したい四つの判断#

3.1 圧縮の成否は次の行動が正しいかで測る#

決済コールバックの変更を依頼したユーザーが、「データベースのスキーマは変えないで」と明示したとしよう。その後エージェントがファイルを調べ、テストを実行し、大量のログを残す。テストの経過をどれほど詳しく要約しても、この制約を落とせば、次のターンで作業が別の方向に進みかねない。

ここからの推論。最低限残したいのは、目標、ユーザーが課した制約、確認済みの事実、未検証の仮説、完了した外部操作、現在の障害と次の一手だ。ファイルから再取得できる詳細は参照に縮められるが、ユーザーが退けた選択肢はコードを読み直しても判明しないことがある。

3.2 再取得したい証拠には安定した参照先とバージョンを付ける#

「詳細ログは省略」だけでは引き継げない。どの実行の、どのツール呼び出しの、ログのどの範囲で、どのコードバージョンに対応するのかが必要だ。これがなければ再取得のためにコマンドをやり直すことになる。その操作には費用がかかるかもしれないし、再現不能だったり、新たな副作用を生むこともある。

ワークスペース内のファイルも変わる。パスが指すのは現在の内容であり、当時観測した内容を指せるのは元のツール出力やハッシュ付きのスナップショットだ。両者を区別したうえで、どちらにもアクセスできるようにする。

3.3 プロンプトキャッシュの節約効果と意味的な記憶を分けて考える#

確認できたこと。Claude Code の文書は、圧縮後の会話層のキャッシュ変化と、システムプロンプトやプロジェクトコンテキストの層を分けて説明している。圧縮で履歴のプレフィックスが変わっても、安定した別の層は再利用できることがある。[3] OpenCode のコンテキスト組み立て処理でも、多くのリクエストが共有する安定した指示を意図的に先頭側へ置く。[10]

ここからの推論。毎ターン送信量を少し減らせば必ず安くなるとは限らない。冒頭を頻繁に書き換えると、後に続く長いプレフィックスまで再計算が必要になることがある。逆に、キャッシュヒット率が高くても記憶の質は分からない。キャッシュされた入力もウィンドウを消費し、無関係な情報を含みうる。入力規模、キャッシュの費用、タスクの品質は別々に見るべきだ。

3.4 圧縮によって新しい権限が生まれてはいけない#

ログ、ウェブページ、リポジトリ内のファイルを読むと、ツールの結果に命令口調の文章が含まれることがある。「そのページが実行可能だと主張している」を「ユーザーが実行を許可した」と要約してしまうと、情報が信頼境界を越えてしまう。

設計上の判断。ユーザーの指示、ツールによる観測、モデルの仮説はそれぞれ出所を区別する。許可の根拠となるのは元のユーザーイベントや製品の権限状態であり、要約の一文だけでは足りない。短くしても、誰が何を述べたかは残す。

4. 実装案：自分のエージェントにコンテキスト層を用意する#

以下は私自身の設計案で、3 製品の内部実装を説明するものではない。私ならまず再生可能なデータ構造を作り、その上に要約の仕組みを足す。

4.1 イベントを保存し、今回の入力は別に組み立てる#

セッションイベントは追記専用とし、大きなツール出力は永続的な成果物として保存してイベントにはその参照を持たせる。独立したコンテキストコンパイラが、現在のブランチ、タスク状態、証拠と予算からリクエストを作る。入力から省略しても、元の記録を密かに消してはならない。

// 設計例。既存製品のインターフェースを示すものではない。
SessionEvent {
  event_id, session_id, branch_id, parent_id,
  role, kind, content_ref, tool_call_id,
  provenance, created_at
}

ContextCheckpoint {
  checkpoint_id, base_event_id, source_event_ids,
  summary_ref, retained_from_event_id,
  model_key, instructions_hash, projection_version
}

このチェックポイントが記述するのは会話のコンテキストだけだ。ファイルシステムのチェックポイント、プロセスの復元、外部 API の実行記録にはそれぞれの仕組みが必要になる。原イベントも無期限に保存するのではなく、製品のデータ削除やテナント分離のルールに従う。

4.2 ツール呼び出しと結果を一組として扱う#

メッセージ数だけで機械的に打ち切ることはできない。アシスタントのツール呼び出しと対応する結果を一組として境界を決める。並列に呼べば結果も複数になりうる。結果を短縮する場合はツール ID、状態、重要な証拠と再取得方法を残し、アダプターでプロバイダーの要求するメッセージ構造を守る。

巨大な出力は先に永続化し、範囲を指定した抜粋を渡せる。コンパイラはどこを切り捨てたか把握する必要がある。モデルにも省略を明示し、抜粋を完全な結果として扱わないようにする。

4.3 予算はリクエスト全体で決める#

私は、固定の指示とツール定義、タスクの状態、直近のメッセージ、検索で得た証拠を別々に数える。出力、ツール結果の増加、見積もり誤差にも余裕を取る。モデルによっては入力、出力、総ウィンドウのそれぞれに上限があるので、アダプターで個別に確認する。

入力予算 = モデルの利用可能ウィンドウ − 今回の出力予約 − 安全余裕
削減可能な履歴の予算 = 入力予算 − 固定指示 − タスク状態 − 直近の内容 − 必要な証拠

例えば総ウィンドウを仮に 128k とし、出力と余裕分として 24k を取ると、入力の目標は最大 104k だ。固定部分に 12k、直近の内容に 24k、状態の要約に 8k、証拠に 16k を割り当てた後、その他の履歴に回せるのは約 44k になる。推奨しきい値や実測値ではない。

固定部分が大きすぎるなら、常駐するツールや指示を削る。残った短い会話をさらに要約しても根本は解決しない。ツールが一度返すだけで上限を超える場合は、結果が次のターンに入る前の段階にも制御を置く必要がある。

4.4 ツール結果の見え方を 3 段階に分ける#

状態今回の入力に含めるもの用途
FULL元の内容、または指定範囲の完全な内容現在の推論に使用中、あるいは厳密な比較が必要
REFERENCE事実の要約、出所 ID、バージョン、再取得先情報に価値はあるが、全文を常駐させる必要がない。
OMITTED今回は入力から外し、履歴は保存ポリシーに従って保持重複した出力、完了した調査の枝

まず説明可能なルールを実装したい。未解決エラー、最新の検証、未完了のツール呼び出しを保護し、大きなファイルを繰り返し読んだ結果は参照に縮める。評価データが集まってから、どれを先に除外するかの判断にモデルを加えることを検討する。

「直近 10 回のツール呼び出し」は保護ルールの一つにはなるが、方針全体の代わりにはならない。巨大なログが 10 個あれば上限を超えうる一方、もっと前の一つのユーザー制約が最重要であることもある。

4.5 バックグラウンド要約はバージョンを確かめてから適用する#

バックグラウンド要約がイベント E100 までを対象とし、生成中に E101 から E108 までが追加されたとする。切り替え後も追加分はすべて保持する。ユーザーがブランチを移ったり、目標やモデルを替えたりしていれば、要約そのものも使えるとは限らない。

snapshot = capture(branch, prefix_end, instructions_hash, model_key)
candidate = summarize(snapshot.events)

at_next_safe_boundary:
  if prefix_still_matches(snapshot) and policy_still_matches(snapshot):
    atomically_append_checkpoint(candidate, base=snapshot.prefix_end)
    keep_all_events_after(snapshot.prefix_end)
  else:
    discard_or_recompute(candidate)

「安全に切り替えられる時点」も定義しておく。この案では実行中のツールのバッチが完了するのを待ち、リクエストを組み立てる前に検査する。候補が失敗したり不完全だったりすれば前のチェックポイントを保ち、永続化が完了してからビューを替える。二つの非同期タスクが同時に messages を書き換えないよう、バージョン番号や compare-and-swap が必要だ。

4.6 復旧の試行回数に上限を設ける#

圧縮しても次のターンがウィンドウを超えるなら、まず増加の原因が固定指示、単一の添付ファイル、ツール結果のどれかを調べる。復旧回数に上限を設け、削減前後の実際の予算を確認する。「圧縮して同じ巨大な入力を再送」を繰り返すと、一度の失敗が高価なループになる。

要約が使えなくても原履歴があれば、直前の有効なチェックポイントに戻り、保持区間を選び直せる。モデルをまたぐ場合は移植可能なテキストのビューを再構築する。プロバイダー固有の不透明なチェックポイントは汎用の会話形式として使えない。

5. 本当に効果があるか、どう検証するか#

以下は今後実施したい評価案であり、製品の順位を測定した結果ではない。同じタスクを繰り返し再生できるように用意し、全履歴の投入、予算に応じた切り詰め、要約と直近の内容、証拠の参照化、状態チェックポイントを比較したい。モデル、ツール環境、タスクの入力は固定する。

テスト場面確認する点
途中でユーザーの要件が変わる新しい制約が古い判断に優先するか、以前の目標を実行し続けていないか。
3 回以上続けて圧縮する未解決の問題、却下済みの案、出所への参照が回を追うごとにずれていないか。
長いログとツールの並列実行呼び出しと結果が対応するか、失敗の情報が残るか、上限超過からの復旧回数が有限か。
ブランチ変更、モデル切り替え、再起動セッションのビュー、ワークスペースの状態、チェックポイントの対応が明確か。
ツール結果に指示が紛れ込む外部の文章をユーザーの要件や許可に格上げしていないか。
提出済み、または公開済みのタスク完了したことを忘れて、副作用のある操作を実行し直さないか。

タスク成功率、重要な制約の保持率、証拠の再取得成功率、重複したツール呼び出し、圧縮の待ち時間、タスク全体のトークン数と費用を記録する。キャッシュヒット率や要約の圧縮率は補助指標だ。強く圧縮した結果エージェントが 10 ターンも遠回りすれば、全体では損失になりうる。

さらに、圧縮前の入力、要約候補、切り替え後に実際に送ったリクエスト、次の行動という四つを保存したい。これらを突き合わせれば、要約の欠落、再取得の失敗、メッセージ構造の不備、証拠が揃ったうえでのモデルの判断ミスを切り分けられる。

6. 私ならどこから作るか#

Claude Code からは、情報が入る前の層分けと分離に目が向いた。Pi はセッションの投影を独立したデータ構造として扱う方法を示している。OpenCode V2 はキャッシュ、バックグラウンドでの事前計算、プロバイダー差、安全な切り替えを一つのライフサイクルに組み込んでいる。

ゼロから作るなら、まずイベント記録、証拠への参照、タスク状態、リクエストコンパイラを整え、その上に検証可能な要約と復旧を載せたい。システムがいつでも次の三つに答えられるようにする。今回モデルに何が見えていたか。各結論の出所はどこか。次の一手が今も妥当だと言えるのはなぜか。

長いコンテキストは圧縮の時期を遅らせてくれる。長時間のタスクを確実に進めるには、情報量が増えても目標、境界、証拠を守れることが必要だ。
