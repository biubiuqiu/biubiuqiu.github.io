ユーザーがエージェントに、昨夜失敗した注文を調べてほしいと頼んだ。ツールが返した明細は 2 MB。エージェントは異常のある三つのバッチを特定し、まとめてチケットを起票した。10 分後、ユーザーが「二つ目のバッチが失敗した原因は、一つ目と同じ？」と尋ねる。明細を丸ごとモデルに送り直せば、質問のたびに同じ資料を読む費用がかかる。「異常が三件」という要約しか残っていなければ、今度は質問に答えられない。しかも、起票に成功した直後にプロセスが落ちたとしたら、引き継いだマシンは調査を続けるべきか、もう一度起票すべきかをどう判断するのだろう。

この三つの問いから、トランスクリプトの保存方法を考えたい。ここでいうトランスクリプトとは、ユーザー、モデル、ツールとエージェントの間で実際に起きたやり取りの記録だ。複数ユーザーが利用し、別のマシンでも再開できるサービスなら、私なら論理的な項目ごとに追記し、小さい内容はその場に保存し、大きな結果には後から読める参照を残す。次のターンでどの項目をモデルに見せるかは、別に決める。先ほどのチケットを例に追ってみよう。

一行には何を入れるか。ツール呼び出しから考える#

注文検索の呼び出し ID を q7、起票を t8 とする。プラットフォームは一回の実行を次の六項目として記録できる。通番はセッション内の順序を、呼び出し ID は一回のツール操作を識別する。

通番   種別                記録する内容
41     user.message        昨夜失敗した注文を調べ、異常のあるバッチを一件のチケットにまとめて
42     tool.call     q7    query_orders、対象の時間帯と検索条件
43     tool.result   q7    異常は 3 バッチ、明細オブジェクト A、その版とチェックサム
44     tool.call     t8    create_ticket、根拠は #43、固定の冪等キー K
45     tool.result   t8    成功、外部チケット番号 O-318
46     assistant.message   3 バッチをチケット O-318 にまとめました

44〜46 番だけ取得すれば、どのチケットを作ったかを画面に表示できる。検索が並列で二つ走り、結果が逆順で届いても、呼び出し ID で対応付けられる。生成途中の単語や JSON 引数の断片はフロントエンドに流してよい。永続的な履歴には通常、メッセージや呼び出しが完成してから一項目を確定する。切断箇所からストリームを再生する必要があるなら、差分用の短期バッファとカーソルを用意すればよい。その保存期間はセッションよりずっと短くできる。

会話全体を一つの JSON フィールドに入れる方法は、書き手が一つで長さに上限があり、毎回全件を読む試作では手軽だ。コストは書き方による。等しい長さのメッセージを追加するたびにクライアントが配列全体を再送すると、100 件までに送る量は合計 5,050 件分。個別に追記すれば 100 件分で済む。これはクライアントの転送量の例で、実際のディスク書き込み量はデータベースの実装次第だ。ローカルの JSONL も実用的な出発点になる。同じ JSON 表現を使いながら、末尾に一件ずつ追記できる。符号化形式と更新の粒度は別々に選べる。

「続けて」と言われたとき、三つの SDK はどこを読むか#

Claude Agent SDK：ネイティブのセッションをランタイムに返す#

TypeScript で query() を呼ぶ場合、返された session_id を保存しておき、次回 options.resume に渡せる。既定のトランスクリプトはローカルの ~/.claude/projects/ 以下にある JSONL ファイルに保存される。次のリクエストを別のマシンへ送るなら、ID に加えて、その参照先のデータも必要になる。

公式の SessionStore アダプターは append(key, entries) と load(key) を備える。バックエンドに求める条件は明確だ。取り出した項目が書き込んだ値と深い等価性を満たし、順序も一致すること。JSON のシリアライズ方法を変えるのはよいが、ツールの返り値を一文の要約にすり替えるとこの契約が崩れる。キーにはプロジェクト識別子と任意のサブパスも含まれ、サブパスがサブエージェントの記録を指すこともある。私ならネイティブの項目をバッチで永続化し、画面用に軽量な索引を別に持つ。保存時に 2 MB の明細を切り離すなら、load で元どおりに復元する。モデルに要約だけを渡したい場合は、最初からツールの戻り値をそう設計する。セッションの再開 · 外部ストレージの契約と実装例

LangChain / LangGraph：次に誰が処理するのかを復元する#

LangChain の create_agent(..., checkpointer=saver) は LangGraph の永続化機構を利用できる。同じ thread_id を指定すると、そのスレッドのグラフ状態を取得できる。messages はその中の一フィールドで、アプリ独自の状態も追加できる。開発には InMemorySaver が使え、公式のデータベース例では PostgresSaver を使う。スレッドをまたぐユーザー設定などには別の Store がある。LangChain の短期記憶 · LangGraph の永続化

起票の例なら、検索で得た成果物 A の参照、承認待ちの起票要求、現在のグラフ状態をチェックポイントに保持できる。承認者が翌日戻ってきても、ランタイムはどの手順から再開するかを知っていなければならない。チャットに表示された六行だけからそれを安定して推定するのは難しい。一方、頻繁に保存する状態に生の明細を入れると、チェックポイントを読むたび、シリアライズするたびに大きなフィールドを扱うことになる。私ならノードの次の処理に必要なデータだけを状態に入れ、実際の saver が増分で何バイト書いたかを別途測る。

OpenAI Agents SDK：履歴を残しながら、モデルが読む内容を選ぶ#

Python SDK では SQLiteSession("orders-17", "sessions.db") を使えば、同一セッションで複数回実行した Runner.run の履歴が残る。ファイルパスは明示したい。既定のメモリ上のデータベースはプロセス終了時に消えるからだ。Session には get_items、add_items などがある。RunConfig.session_input_callback を使うと、モデル呼び出し前に取得済みの履歴と今回の入力を組み合わせられる。古い項目の一部を除外しても、残した古い項目が新規履歴として再度追記されることはない。Session と入力の結合 · SQLiteSession の永続化パラメーター

次の二回の呼び出しは別々のプロセスで実行できる。両方に同じ agent が設定され、同じデータベースファイルにアクセスできることが前提だ。二回目は同じセッション ID で履歴を取り出す。

from agents import Runner, SQLiteSession

# 最初のターン。検索ツールは要約、バッチ ID、明細への参照を返す。
session = SQLiteSession("orders-17", "orders.db")
await Runner.run(agent, "昨夜失敗した注文を調べて", session=session)

# 次のターンでセッションを開き直す。クライアントから会話全体を再送する必要はない。
resumed = SQLiteSession("orders-17", "orders.db")
answer = await Runner.run(agent, "二つ目のバッチの失敗原因は一つ目と同じ？", session=resumed)

ここには二つのコストがある。コールバックで十項目だけ残せば、モデルに送るトークンは減る。しかし既に一万項目を取得していれば、データベースの読み出しは一万項目のままだ。SessionSettings(limit=N) なら取得件数そのものも制限できる。ただし N は個々の項目を数えるため、ツール呼び出しと結果の間で切れることがある。欠けた相方を補うか、完了した呼び出しと結果を組ごと入力から外せるようにする。

PostgreSQL とオブジェクトストレージの境界#

企業向けプラットフォームに戻ろう。私ならまず次の論理テーブルを実装する。イベント ID はプラットフォームが生成し、同じ書き込みを再試行するときは同じ ID を使う。ツール呼び出し ID は一回の run の中で解釈できるが、監査と障害調査には、どのテナント、セッション、run に属するかも必要だ。

transcript_item
  tenant_id, session_id, seq         セッション内でコミットした順序
  event_id, run_id, kind, call_id    重複排除、所属、呼び出しと結果の対応
  payload_jsonb                     メッセージ本文、または短いプレビューと成果物の情報
  artifact_key, digest, byte_size   大きな結果の不変バージョン、チェックサム、サイズ
  schema_version, created_at        復号と保持方針

  PRIMARY KEY (tenant_id, session_id, seq)
  UNIQUE      (tenant_id, session_id, event_id)

追記トランザクションでは、まずセッションの最新通番を持つ行をロックし、イベントが既に書かれていないか調べる。バッチに連続した通番を割り当て、項目を挿入し、最新通番を更新してコミットする。これならフロントエンドが seq > cursor で次のページを読んでも、先に番号を確保した項目が後からコミットされて取りこぼすことがない。異なるセッションは独立して書ける。大規模な並列タスクが同じロックで詰まるなら、サブタスクごとに分散する前にセッション単位の待ち時間を測る。全体の同時ユーザー数だけでは、そのロックの混雑度は分からない。

明細 A はそのテナントに属する不変のオブジェクトとして先に保存し、成功を確認する。その後、データベースのトランザクションで 43 番と参照をコミットする。アップロード後にトランザクションが失敗すると孤立オブジェクトが残るが、猶予期間を置いてから回収できる。順序を逆にすると、成功と表示された記録を開いても明細が存在しない事態になる。成果物を読む際は現在のユーザーで権限を検証し直す。イベントには安定したオブジェクト識別子を保存し、一時ダウンロード URL は読むときに発行する。

データベースが小さくなった後、データはどこにあるか#

一日 10,000 回実行し、一回につき平均 1 KB の記録が 20 件、さらに 2 MB のツール結果が一件あるとする。単位は十進法、一か月は 30 日として、非圧縮の論理データ量を計算する。索引、WAL、レプリカ、バックアップ、オブジェクトのリクエスト料金、通信費は別途測定する。

小さな記録   10,000 × 20 × 1 KB × 30  =   6 GB/月
大きな結果   10,000 ×  1 × 2 MB × 30  = 600 GB/月
項目数       10,000 × 20 × 30         = 600 万件/月

大きな結果をインラインに置くと、データベースは月約 606 GB を受け持つ。外に出すとデータベースは月約 6 GB と参照、オブジェクトストレージは月約 600 GB を受け持つ。総量はほぼ同じだ。利点は、直近の会話を開くときに軽量な索引と該当ページを読むだけで済み、ホットデータベースのバックアップに毎回大きな結果まで含めずに済むことだ。明細の永久保存を約束すれば、毎月 600 GB ずつ積み上がる分の費用はやはり発生する。

ここには独立した二つの判断がある。大きな結果の外部化は、活動中のセッションで項目の大きさと読まれ方を見て行う。履歴全体のアーカイブは、セッションが使われなくなってから、再訪頻度、保持期間、許容できる復元待ち時間を見て行う。確定した通番範囲を JSONL のセグメントにまとめて圧縮し、開始・終了番号、オブジェクトの版、チェックサムをデータベースに登録できる。アーカイブを検証して読み出し先を切り替えた後、ホット側のコピーを回収する。このタイミングでユーザーが質問を再開しても、新規項目は末尾に追記できる。過去のページを開いたときだけ該当セグメントを取得すればよい。

外部化の閾値は実トラフィックで選ぶ価値がある。一週間分をサンプルに、ツール別の結果サイズの P50、P95、P99 と、七日以内に全文が再読された割合を出す。32 KB、128 KB、512 KB で分けた場合をそれぞれ試算し、ホット側の書き込み削減量、一日あたりのオブジェクト GET 増加数、再開後の初回応答の P95 がどれだけ遅くなるかを比べる。たまに生成する 10 MB のレポートと毎回読む 40 KB の設定には別の方針が適しているかもしれない。テナントのデータを消すときは、アーカイブ、要約、キャッシュ、保持期間内のバックアップについても、期限を迎えたら消える経路が必要だ。

「二つ目のバッチは？」に答えるとき、何を読むか#

チャット画面を開くときは、カーソルで直近の一ページを取得し、起票の受領結果と検索の要約を表示する。明細 A はユーザーが展開したときだけ読む。原因を続けて聞かれたときは、どの通番までを対象にしたかが分かる要約、それ以降の完全なやり取り、今回の質問を取得する。要約には最低限、三つのバッチの識別子、元の検索時間帯、成果物への参照を残す。一つ目と二つ目の違いがエラーコードに現れるなら、A からその二つの該当行を取り出して予算内に収める。権限がない場合や期限切れの場合は、根拠が得られないと伝える。検索し直した結果は新しいデータなので、新しい検索時刻を明記する。

当時なぜ起票したかを調べるときは、44 番から 43 番の原資料と当時のツールの版にさかのぼる。「モデルが実際に何を見たか」まで説明する必要があるなら、そのモデル呼び出しに含めた項目範囲、要約の版、システムプロンプトの版、ツール定義の版、最終リクエストのダイジェストを記録する。ハッシュで検証はできても内容は復元できない。一字一句照合する必要がある場合は、権限と保持方針の範囲で実際のリクエスト、または再構築に十分な不変の入力を保存する。入力が同一でも、モデルに再度問い合わせて同一の答えが返る保証はない。

要約には through_seq と方針のバージョンを付けたい。本番で短い要約を試すときも、許可された履歴から作り直し、「一つ目と二つ目のバッチの違いは？」という追加質問で回答を比較できる。こうして圧縮方式を検証できる。唯一の原文を新しい要約で上書きすると、何を取りこぼしたかを確かめる機会も失う。限られたウィンドウにメッセージをどう収めるかは、エージェントのコンテキスト管理を参照してほしい。

最も試す価値のある受け入れテスト：44 番の直後に電源を切る#

外部システムには O-318 が作成されたものの、ランタイムが 45 番を書き込む前に終了したとする。トランスクリプトから分かるのは起票を要求した事実までで、外部の成否は分からない。新しいワーカーは保存済みの冪等キー K で照会または再試行し、冪等性に対応する下流から同じチケットを受け取り、欠けた結果を補う。チケットを照会できず冪等キーも使えない API なら、状態を「結果要確認」として人の判断に引き継ぐ。データベースの一意制約でローカルの重複記録は防げても、外部にチケットが二件できることまでは防げない。

ゼロから始めるなら、最初に三つの受け入れ条件を満たしたい。セッションを順番どおりページングできること。別のワーカーに切り替えても質問を続け、指定したバッチを取り出せること。起票の受領結果を記録する前にプロセスを落としても、復旧後に外部チケットが一件だけであること。その後にツール結果のサイズと休眠セッションの再訪率を見て、外部化とアーカイブの閾値を決める。保存設計の良さが表れるのは、ごく普通の場面だ。翌日戻ったユーザーが「二つ目のバッチは？」と聞いたとき、昨日の根拠を取り出せて、既にチケットを起票したことも覚えている。
