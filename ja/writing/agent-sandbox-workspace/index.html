モデルは分析用のコードを書ける。では、そのコードはどこで動くのか。生成したファイルはどこに置かれ、次のステップでも見つけられるのか。質問に答える段階からタスクを完遂する段階へ進むには、長いコンテキストに加えて、計算し、結果を保存し、仮説を検証できる作業環境が必要になる。

本稿の範囲 · 2026-11-14

タスクの実行を出発点に、公式文書を参照しながらサンドボックスを支える OS の仕組みを考える。図、ファイル名、インターフェースは説明用の例であり、実装案は特定製品の内部構造を示すものではない。各隔離技術の性能や安全性を比較する実験は行っていない。

1. モデルが提案した手順をどこで実行するか#

たとえば、ユーザーが注文 CSV をアップロードし、金額を集計してレポートを作り、結果を確認してほしいと頼んだとする。モデルは列を理解し、集計条件を決め、Python を書ける。実データを使った集計結果にたどり着くには、さらにコードを実行する必要がある。

モデル推論そのものも計算資源を使う。ここでいう計算環境とは、モデルがツール経由で使う外部の実行環境である。CPU がプログラムを実行し、メモリが処理中のデータを保持し、ファイルシステムが入力と成果物を保存し、OS がプロセスを管理する。モデルは通常ツールで実行を依頼し、Python は別のプロセスとして動く。

エージェントに操作できるコンピューターを一台渡すと考えればよい。スクリプトを置き、実行し、エラーを読み、修正して再実行し、実在するファイルを届けられる。サンドボックスに残る成果物、ログ、終了ステータスが次の判断の根拠になる。

制約付きの作業環境

ファイル、プロセス、依存関係、資源、アクセス境界。

1.1 すべてのデータをモデルに計算させない理由#

走査、並べ替え、集計、形式変換の手順が明確なら、モデルが規則を書き、プログラムが各行に適用する方が適している。大きなファイルの合計を求めるだけなら、全行をモデルのコンテキストに通す必要はない。

Anthropic のコード実行に関する記事でも、実行環境でデータを絞り込んで変換し、必要な結果だけをモデルに返す方法を紹介している。操作間の中間状態はファイルに保持できる。[1] つまり、作業環境はコンテキストの外にも広がっている。モデルには集計、サンプル、失敗情報を渡し、入力全体と成果物は別の場所に置ける。

実行できたことは正しさの証明にはならない。金額を文字列として連結するのか数値として足すのか、返金を控除するのか、単位は何か。すべてタスクの定義とコードに依存する。集計条件を決めてから、実行して結果を確かめる。

1.2 固定のツールを百個用意するだけではいけないのか#

注文照会や予定の登録など、境界が明確な業務には固定ツールが向く。一方、作業環境では、新しい形式を解析し、フィルタースクリプトを書き、既存ライブラリで文書を変換し、結果を別のツールに渡すといった手順をその場で組み合わせられる。要望が増えるたびに新しい API を待つ必要がない。

すべてのエージェントに専用サンドボックスが必要なわけではない。許可済みの業務 API を選んで組み合わせるだけなら、実行はツールサーバーで完結する。動的なコード、大きなファイル、複数ステップにまたがる成果物、常駐プロセスを扱うとき、専用環境が生きてくる。MCP などのプロトコルが定めるのは接続と呼び出しの取り決めであり、実行するマシンは別に必要だ。

2. 依頼から納品できるファイルまでを追う#

この例では、モデルが全行を暗算する必要はない。それでもデータを理解し、適切なプログラムを提案し、実行結果に応じて調整する必要がある。エラーも新しい観測結果だ。正常終了後も、ファイルの存在、行数、集計条件を確認する。

# カレントディレクトリに orders.csv があり、金額は整数の人民元とする
import csv
from pathlib import Path

with open("orders.csv", newline="", encoding="utf-8") as f:
    rows = list(csv.DictReader(f))

total = sum(int(row["amount"]) for row in rows)
Path("summary.csv").write_text(
    f"order_count,total_amount\n{len(rows)},{total}\n",
    encoding="utf-8",
)
print({"order_count": len(rows), "total_amount": total})

このデータで期待する結果は3件、500元。実データに小数金額、欠損値、重複注文、複数通貨が含まれるなら、それぞれの処理規則と検証が要る。例には本番用の検証を含めていない。生成したファイルはまだ作業環境にあり、ダウンロードや成果物 API を通してユーザーに届ける必要がある。

3. この「コンピューター」は何を提供するのか#

ディレクトリにはファイルを置ける。しかし、プロセスの実行場所、依存関係の供給元、接続できるネットワーク、資源の制限主体はディレクトリだけでは決まらない。作業環境を五つの機能に分けてみよう。

3.1 ファイルシステムで中間状態を会話の外に置く#

入力 CSV、分析スクリプト、グラフ、テストログにそれぞれパスを割り当てる。次のツール呼び出しは必要なファイルを読み、全内容をプロンプトに戻さずに続行できる。あるプログラムが CSV を出力し、別のプログラムがグラフにするなど、ファイルはプログラム間の受け渡しにも使える。

同じパスでも中身は変わる。会話の要約にあるファイルが、すでに削除、上書き、移動されていることもある。復元後は以前の記述を信じ込まず、実際の状態を確認する。

3.2 プロセスによって実行中の作業を追跡できる#

Python の実行、ブラウザーの起動、コンパイル、テスト待ちにはプロセスが関わる。PID、終了コード、標準出力、標準エラー、子プロセス、実行時間がある。長いコマンドの終了前にモデルが次の推論に進むこともあるため、ランタイムはタスク ID で追跡する。

モデルと実行プロセスは別のマシンに置ける。ランタイムは管理された接続でコマンドを送り、出力を集めて返す。ブラウザー、GPU、大規模計算には個別の実行サービスを使ってもよい。全機能を一つのサンドボックスに入れる必要はない。

3.3 依存関係と資源から実行条件を見積もる#

スクリプトには Python やライブラリが、ページの表示にはブラウザーが、動画処理にはコーデックが要る。ベースイメージが再利用できるソフトウェアを提供し、プロジェクトのファイルと設定を加えて作業環境になる。依存関係はバージョン、取得元、キャッシュも含めて設計し、ネットワーク経由のインストールが失敗する場合に備える。

CPU、メモリ、ディスク容量、プロセス数、実行時間で仕事の規模が決まる。無限ループにホスト全体を占有させてはいけない。プログラムが起動できても、データセット全体を読み込むメモリが足りるとは限らない。

4. 作業環境にサンドボックスという境界を設ける理由#

ここまでで、作業環境が役立つ理由が分かった。では、生成したプログラムがパスを誤ったり、資源を使いすぎたり、信頼できない内容を読み込んだりしたとき、影響はどこまで広がるだろう。

専用計算環境とセキュリティ上の隔離境界は別の性質だ。通常のディレクトリとシェルでも作業はできるが、それだけで確実に隔離できるわけではない。サンドボックスではランタイムと OS が、見える資源、実行できる操作、影響の範囲を制限する。

制約付き実行環境／概念図

エージェントが生成したプログラム許可された作業ディレクトリを読み書き制限された計算資源を利用許可された外部サービスに接続
OS または実行サービスがポリシーに従って境界を検査
他ユーザーのデータホスト上の機密ディレクトリ許可されていないネットワークと認証情報
これらの保護には明示的な設定と検証が必要だ。図に線を引いただけではアクセスを遮断できない。

4.1 各仕組みが受け持つ役割#

仕組み主な制約そこからは保証できないこと
Namespacesプロセス、マウント、ネットワークなどの見え方と名前の範囲namespace に入れば任意のコードを安全に実行できること
CgroupsCPU、メモリ、プロセスなどの使用量計測と制限メモリ制限でファイル読み取りやネットワーク接続まで制限できること
Capabilities / Seccomp / LSM権限、許可するシステムコール、アクセス範囲の縮小システムコールのフィルター一つでサンドボックスが完結すること
ファイル・ネットワークポリシーマウント範囲、読み書き権限、外部接続先、出口ファイルを隔離すればネットワークも自動的に隔離できること

Docker の文書は namespace と資源制御の役割を区別している。Linux の文書も、seccomp によるシステムコールのフィルタリングだけでは完全なサンドボックスにならないと明記している。[2][3] 技術名を一つ選んで終わりにせず、マウント、権限、ネットワークポリシーまで設計する必要がある。

「ほかのディレクトリにアクセスしない」というプロンプトは行動指針だ。OS がアクセスを拒否して初めて実行上の境界になる。モデルが承認しても下位層は権限違反を拒否できる。また、ネットワーク要求を送れることと、リモートの業務データを変更する権限は別だ。

4.2 コンテナ、gVisor、microVM では境界を置く場所が違う#

通常の Linux コンテナではプロセスがホストのカーネルを共有する。gVisor はユーザー空間に Linux 型のアプリケーションカーネルを実装し、 runsc を通してコンテナツールと連携する。[4] Firecracker は KVM 上で microVM を動かし、ワークロードはゲストカーネルを使う。[5]

通常のコンテナ

タスクのプロセス共有するホストカーネル

gVisor

タスクのプロセスユーザー空間のアプリケーションカーネルホストカーネル

MicroVM

タスクのプロセス＋ゲストカーネル仮想化境界／VMMホストカーネル＋KVM

図は論理階層の比較であり、システムコールの全経路を示すものではない。選定では互換性、ワークロード、起動・運用コスト、テナント間の信頼関係も考える。一律の性能順位は導けない。microVM にも出口制御は必要で、Firecracker はネットワークフィルタリングをホスト側に委ねている。[5]

ローカルのコーディング支援では既存の開発ディレクトリでコマンドを制限できる。一方、クラウドのエージェントには新しいリモート環境を用意できる。Claude Code の sandboxed Bash 文書が説明するのはファイルとネットワークの制約で、呼び出しごとに仮想マシンを新設するという意味ではない。[6]

5. どの状態が残るのかを明示する#

会話、ファイル、プロセスは三種類の異なる状態だ。会話履歴があってもファイルが残った証拠にはならない。ファイルが残っていても、実行中の Python プロセス、メモリ上の変数、ブラウザー接続は失われているかもしれない。

Kubernetes の文書では、Pod と寿命をともにする一時ボリュームと、個々の Pod より長く残る永続ボリュームを区別している。[7] 作業環境の回収方針とストレージの方針は合わせて設計する。

重要なファイルを永続化し、アイドル時は計算資源を解放し、次回はストレージを再マウントしてプロセスを新しく起動する方式がある。別の方式では checkpoint/restore で実行状態も保存する。gVisor はこれに対応するが、復元にはファイルシステムの整合性、ネットワーク接続、環境の互換性も関係する。任意のマシンであらゆる状態をそのまま再現できるわけではない。[8]

私の見方。一時停止、プロセスのスナップショット、ファイル永続化、オブジェクトストレージへのアーカイブ、バックアップは用途が異なる。終了時のアップロードはアーカイブには使えるが、その前に突然停止した場合の書き込みは守れない。どこまでデータ損失を防ぐかを約束するには、書き込み確認の時点、永続化経路、想定障害、復旧目標を明確にする。終了フックだけでは足りない。

6. ユーザーごとに一つか、セッションごとに一つか#

これはプロダクトと資源管理の選択であり、モデルが決める構造ではない。サンドボックス、コンテナ、Pod、作業ディレクトリの間に必然的な一対一対応はない。一つのスケジューリング単位に複数の隔離インスタンスを収容できる。それを採用するかは隔離機構とプラットフォーム設計次第だ。

割り当て方式利点設計上の課題
呼び出しごとの一時環境片付けが簡単で、独立した小規模計算に向くステップ間で状態を明示的に受け渡す。依存関係の準備が重複しうる
セッションごとの作業環境タスクの状態が明確で、セッション同士を分けやすいインスタンスが増え、依存関係とファイル共有の設計が必要
ユーザーごとの作業環境個人ファイルと依存関係を再利用できる同時セッションがファイル、ポート、依存バージョン、バックグラウンドプロセスを取り合う

実装案。長期的なファイル所有権を短命な実行インスタンスから切り離す。ユーザーに永続的なファイル領域を持たせ、タスクには制約付きの作業ディレクトリか独立した実行インスタンスを割り当てる。セッションごとのサブディレクトリは整理には役立つが、ディレクトリ間のアクセス制限はランタイムと OS が実施する必要がある。

7. 作業環境にツール呼び出しをつなぐ#

自分で実装するなら、モデルには安定したツールの意味を提示し、実機の特定はランタイムに任せる。たとえば次のようになる。

{
  "workspace_id": "ws-demo",
  "operation": "exec",
  "command": ["python", "analyze.py"],
  "cwd": "/workspace",
  "timeout_ms": 30000,
  "request_id": "run-demo-1"
}

これは独自インターフェースの例だ。認証済みの主体を、その主体がアクセス可能な作業環境に結び付ける。クライアントから渡された ID だけではアクセスを認めない。request_id も呼び出しを関連付ける識別子にすぎない。サーバーが重複排除と副作用の記録を規定して初めて、冪等性に使える。

実行サービスは環境が準備できたか、コマンドが継続中か、終了コード、出力の切り詰め、成果物の場所、キャンセル後に子プロセスを片付けたかを答える。後続操作を正しい環境へ送るルーティングも要る。複数の実行者が引き継ぎ得るなら、リースなどの並行制御で二重実行を防ぐ。

目標の解釈、モデルへの要求、コンテキスト選択、タスクの進行は外部ランタイムに置ける。サンドボックスは配信された計算とその状態を受け持つ。明確なインターフェースでつなぐことで個別に増減でき、障害がモデル、配信、実行のどこにあったかも追いやすい。

私ならこう検証する。入力を読み、スクリプトを書き、実行し、修正し、成果物を渡すまでを一つのタスクで試す。途中で計算インスタンスを停止し、保持すると約束したファイルが残っているか確かめる。出力超過、メモリ不足、タイムアウト、同時書き込みを起こし、実際の状態が返るか確認する。コンテナが起動したかを見るだけより、使える作業環境かどうかがよく分かる。

エージェントにサンドボックスが必要だというとき、私が指しているのは、提案した手順を計算、ファイル、検証可能な結果に変えられ、操作の影響が明確な境界で制約される環境である。計算でできることが増え、保存した状態で複数のステップがつながり、観測で誤りを直せる。隔離によってそれらの能力を範囲を決めて提供できる。
