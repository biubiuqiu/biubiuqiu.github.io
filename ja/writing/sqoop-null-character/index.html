Sqoop 1.4.7／Hive 2.1.1 · 過去の実践記録

Denis Wen1,009 文字更新 2026-11-13
前回の続き

同じコマンドで同期しても、大半のテーブルは正常で、一部のテーブルだけが繰り返し型変換エラーになった。手掛かりは、普段は目に見えない1文字だった。

同じ設定なのに値が別の列に入る#

当時の環境はSqoop 1.4.7とHive 2.1.1だった。HiveからMySQLへデータを同期すると、特定のテーブルで値が別の列にずれ、型変換エラーが起きた。同じ設定で正常に同期できるテーブルもあったため、入力データ自体を調べることにした。

問題を1行のデータに絞る#

問題の行を特定するのに2日かかった。使ったのは手作業による二分探索だ。たとえば1万件あるなら、まず5千件を同期し、その成否を見て対象をさらに半分にする。これを繰り返し、エラーを再現する行にたどり着いた。

HDFSからHiveのデータファイルを取り出してcatで見ると、普通の内容に見える。ところがvimで開くと、途中に^@と表示される文字があった。比較を続けると、この文字を含む行は失敗し、含まない行は正常に同期できることが分かった。

この^@はNUL文字で、UnicodeではU+0000に当たる。空文字列は長さがゼロだが、ここには通常は見えない文字が1つ、実際に入っている。

なぜ通常の文字として扱われなかったのか#

フィールドの区切り文字は--fields-terminated-byで指定済みだ。それでもNULが通常の文字として通過せず、解析に影響するのはなぜだろうか。

そこでSqoop 1.4.7のソースコードを読んだ。レコードパーサーは状態機械で入力を処理しており、次の4種類の文字を区別する。

オプションパーサーでの役割
--enclosed-byフィールドの囲み文字
--escaped-byエスケープ文字
--fields-terminated-byフィールドの区切り文字
--lines-terminated-byレコードの区切り文字

手掛かりは、囲み文字を取得するメソッドのコメントにあった。指定がないときは\000で「なし」を表す。一方、入力に含まれるNULはJavaで\u0000と書ける。どちらの表記も同じ文字を表している。

char a = '\u0000';
char b = '\000';
System.out.println(a == b); // true

問題のファイルを読み込み、デバッガで文字の値を確認しながら、状態機械が囲み文字やエスケープ文字を判定する箇所を追った。列ずれは、入力に実在する文字とパーサーの既定値の衝突によるものだった。

当時採った対処#

--enclosed-byと--escaped-byを明示し、入力データと衝突する既定値を避けた。どの文字を使うかは入力形式に照らして検証する必要がある。適当に別の文字を選ぶと、今度はその文字がデータと衝突する可能性がある。

この調査から残った考え方#

役に立ったのは、段階ごとに原因の範囲を狭めたことだった。正常な行と失敗する行を突き合わせ、表示の違いから不可視文字を見つけ、パーサーの状態遷移にたどり着く。エラーが表に出たのは型変換の段階でも、列がずれたのはその前の解析段階だった。
