Last read

In top, a process named sshd was consistently consuming a large share of the CPU. Starting with the file the process was actually running led me to its scheduled jobs and, eventually, a mining configuration.

A familiar process name with unusual CPU usage#

The first clue was CPU usage. The name looked like the standard SSH service, but its resource consumption warranted a closer look. A process’s display name says little about where its executable came from, so I checked the files associated with its PID.

# List the files opened by this process
lsof -p <PID>

# Find the executable the process is actually running
ls -l /proc/<PID>/exe

What kept starting it?#

Next, I inspected the cron jobs for the user in question.

crontab -l -u <username>

The original investigation found two suspicious jobs. One attempted to download a program and its configuration every six hours. The other tried to start the program masquerading as sshd every minute. The program lived in a temporary directory, and the job used a file lock to prevent overlapping executions.

This explained why killing the running process might only provide brief relief. The scheduler could start it again. Finding the executable and finding what launched it were both necessary.

What the configuration revealed#

The configuration included CPU computation settings, RandomX options, and mining pool connection information. Taken together with the high resource usage and the cron jobs, these details identified the program as a cryptominer.

I have omitted the malicious download URL, mining pool addresses, and original cron commands. The public account documents the investigation without reproducing a working malicious download command.

Where the investigation stopped#

The original account ends with removal of the affected user’s scheduled jobs. It contains no complete investigation of the initial entry point, review of other persistence mechanisms, or verification of recovery. The evidence identifies an abnormal process but cannot establish that the host was fully cleaned.

The removal operation in the original account deleted the user’s entire crontab. That scope matters. In an actual incident, preserve the evidence first and distinguish legitimate jobs from malicious entries before removing anything.

The sequence I kept#

  1. Use the CPU anomaly to identify the process that needs investigation.
  2. Resolve its actual executable instead of relying on its name.
  3. Find the scheduler or other source repeatedly starting it.
  4. Use configuration and behavior together to infer its purpose, and document how far remediation was verified.

What stayed with me was how much a familiar name can conceal. Following the executable path and the launch chain one step further was what made this case understandable.
