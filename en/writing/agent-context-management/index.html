Why does the same model perform differently on long tasks when you switch agent products? What interests me is what each product actually lets the model see on each turn, and how it ensures the agent can pick up a task after some of its history has been left out.

Scope of this investigation · 2026-11-13

For Claude Code, I describe behavior documented by Anthropic. For Pi and OpenCode I also read the source at the commits listed below, using V2 for OpenCode. I distinguish verified findings, analysis, and a proposed implementation. I did not benchmark the three products under common conditions. The budgets and pseudocode are design examples.

Picture context as the papers on your desk#

The full history is a filing room. The current context is your desk. When your desk fills up, you can write a handover note and put old material back on the shelves. The goal, constraints, and work in progress still need to be within reach.

Try the four diagrams before reading the source analysis. The token counts, messages, and event IDs in the figures are illustrative.

1. History, context, memory, and the execution environment#

My analysis. Asking what an agent remembers raises at least four distinct questions. Combining everything into a single messages array makes it hard to reason about resuming, switching models, and compacting history.

LayerWhat it holdsAn assumption to avoid
Session historyEvents such as user messages, model responses, tool calls, and resultsEvery stored event goes into the next request.
Current contextThe input actually included in the current model requestOmitting something from a request deletes the original.
Long-term memoryPreferences, facts, and pointers that remain useful across sessionsEverything in the history should become a lasting fact.
Execution environmentFiles, processes, working directories, and external side effectsRestoring the chat also restores files and processes.

For instance, history can retain the complete test log while the current request carries only the failure and a reference to the relevant passage. The project’s test command may belong in project instructions. Files produced by the test belong to the workspace. Each has a different lifetime and recovery procedure.

I treat the input for a turn as a computed result: current input = instructions + task state + selected history + necessary evidence. Anthropic’s account of context engineering also emphasizes selecting useful information for a finite window on every turn.[12]

2. Where does each product handle the complexity?#

Here are the mechanisms I could verify. Comparing these mechanisms does not establish an overall ranking.

Product and evidenceCompaction and continuationScope and limitations
Claude Code · official documentationAutomatic or manual compaction, project instructions, on-demand loading, and separate context for delegated tasksPublic behavior reveals only part of the internal algorithm.
Pi · pinned source snapshotStructured summaries, retention boundaries, a session tree, and context projectionsOriginal records and model-visible messages are handled separately.
OpenCode V2 · pinned source snapshotSummary plus recent content, optional background precomputation, and separate handling of provider-native compactionV1 pruning behavior does not carry over directly to V2.

2.1 Claude Code limits what enters the main context#

Verified. The official documentation describes automatic compaction and directing the focus of /compact. Claude Code also controls what enters the context. Full skill instructions load on demand, and tool search can defer loading MCP tool definitions. A subagent keeps its tool activity in its own context and returns a summary to the main session.[1]

Compaction is one of several controls. Delegating a large search or log investigation to a separate context saves the main task from repeatedly carrying all the intermediate output. The subtask still consumes tokens. A fork inherits the parent context, so starting it has a cost.[4]

Verified. Project instructions and Auto memory provide a separate path across sessions. The documentation describes a short MEMORY.md index and topic files read on demand. At the time of this investigation, the index loader read the first 200 lines or 25 KB, whichever came first. That limit applies to loading the index. The memory directory can hold more.[2]

My analysis. The layering is worth borrowing. Persistent rules constrain decisions, on-demand knowledge fills gaps, and a working summary supports the handover. Putting all three into a growing permanent prompt simply moves the cost of an expanding conversation to startup.

These documents do not reveal Claude Code’s exact summary-selection algorithm, every internal threshold, or every fallback. The presence of a context-management feature in the Claude API alone cannot establish how Claude Code implements each path.

2.2 Pi builds a reproducible view of the next turn#

Verified. Pi’s compaction record includes summary and firstKeptEntryId and tokensBefore among other fields. In the snapshot I read, the default reserve was 16,384 tokens and the target for retained recent history was 20,000 tokens. The reserve affects when compaction triggers. The retention target affects what survives. A cut must also preserve the integrity of tool calls and their results.[5]

The structure is more interesting than the defaults. session-manager.ts uses id and parentId to represent a path through the session. buildContextEntries() selects the applicable summary and retained range. buildSessionProjection() then applies context edits to produce the model messages. An edit can change or omit an entry in this view while leaving the original entry in storage.[7]

My analysis. An application can treat history as its factual record and model input as a view computed from that record. Branching, replay, and compaction can share a history without destructively rewriting an array. Reconstructing the exact input still cannot reproduce a model’s stochastic output or undo a tool’s external effects.

Verified. Pi’s default summary organizes goals, constraints, progress, decisions, next steps, and essential context. Its token estimate uses the most recent available usage report and estimates the messages added since then. Pi serializes the conversation into a dedicated summary request and checks for incomplete summaries or responses that try to call tools.[6]

My analysis. Knowing what to do next and why an alternative was ruled out can be enough to resume a task. A catalogue of recent tool calls may leave both questions unanswered. I would judge a summary by the decisions someone can make after reading it.

2.3 OpenCode V2 schedules compaction itself#

Verified. The V2 documentation describes resuming with a summary plus recent content. The default retention target for recent content is around 15,000 tokens. buffer controls the reserved space. The documentation distinguishes V1 tail-turn and pruning behavior. Even retained recent content may be shortened: long tool output is trimmed and attachment data becomes a brief description.[8] The configuration schema uses auto and keep.tokens and buffer as its fields.[11]

Verified. The normal summary request reuses as much of the conversation prefix as possible and appends the summarization instructions. This gives the provider’s prompt cache a chance to hit. An experimental background path generates and stages a summary early. Only when compaction becomes necessary does the runtime decide whether to adopt it. Changes to the model, instructions, or history prefix can invalidate the candidate.[9]

OpenCode distinguishes its own textual summaries from provider-native compaction. The latter may produce an opaque checkpoint whose portability depends on the provider and model. A model switch after compaction can require more than changing the model field.[8]

My analysis. The hard part of background summarization is determining whether a finished candidate still applies to the current session. Installing it is a conditional, versioned state update that happens after the LLM request completes.

3. Four design decisions that matter#

3.1 Judge compaction by the next correct action#

Suppose a user asks an agent to modify a payment callback and explicitly says, “Leave the database schema alone.” The agent reads files and runs tests, accumulating a large log. A summary can describe the testing process in detail and still steer the next turn off course if it drops that one constraint.

My inference. A summary should preserve at least the goal, user constraints, verified facts, unconfirmed hypotheses, completed external actions, blockers, and the next step. Details available in a file can shrink to a reference. Rereading the code may never reveal an alternative the user already ruled out.

3.2 Give retrievable evidence a stable address and version#

“Detailed logs omitted” leaves a successor with little to act on. Give it the run, tool-call ID, range within the log, and corresponding code version. Without these, recovering the evidence can mean rerunning an expensive or unrepeatable command, possibly with new side effects.

Workspace files change, too. A path addresses what the file contains now. The original tool result or a content-hashed snapshot addresses what was observed then. Make both available and keep their meanings distinct.

3.3 Measure prompt-cache savings separately from memory#

Verified. The Claude Code documentation describes how compaction changes the conversation-layer cache separately from the system prompt and project-context layers. Although compaction changes the history prefix, other stable layers may still be reusable.[3] OpenCode’s context builder also deliberately places stable instructions shared across more requests near the front.[10]

My inference. Sending slightly less on every turn need not cost less. Rewriting early content can force a large subsequent prefix to be recomputed. A high cache-hit rate says little about what the agent remembers: cached input still takes up window space and may contain irrelevant material. Track input size, cache cost, and task quality separately.

3.4 Compaction cannot grant permission#

When an agent reads logs, web pages, or repository files, tool results can contain instructions. A summary that turns “a web page claims this action is allowed” into “the user approved this action” has crossed a trust boundary.

My design choice. Record distinct provenance for user instructions, tool observations, and model hypotheses. Authorization needs an original user event or product permission state to support it. Preserve that distinction even when shortening the content.

4. A proposed context layer for an agent#

The following is my own design proposal, independent of the internals of the three products. I would start with replayable data structures and add summarization afterward.

4.1 Retain events and compile the current input separately#

Append session events, store large tool outputs as durable artifacts, and put references in the events. A separate context compiler builds a request from the active branch, task state, evidence, and budget. It can omit material from a request without destroying the source record.

// Illustrative design; these are not existing product interfaces.
SessionEvent {
  event_id, session_id, branch_id, parent_id,
  role, kind, content_ref, tool_call_id,
  provenance, created_at
}

ContextCheckpoint {
  checkpoint_id, base_event_id, source_event_ids,
  summary_ref, retained_from_event_id,
  model_key, instructions_hash, projection_version
}

This checkpoint describes session context only. Filesystem checkpoints, process recovery, and execution records for external APIs need their own mechanisms. Event retention must also honor the product’s deletion and tenant-isolation policies.

4.2 Treat a tool exchange as one unit#

Cutting after an arbitrary number of messages is unsafe. A boundary must account for an assistant tool call and its matching result together. Parallel calls may have several results. If results must be shortened, keep the tool identifiers, status, key evidence, and retrieval instructions. The adapter must still construct a message sequence the provider accepts.

Persist oversized output first and send a bounded excerpt. The compiler needs to know what was truncated. Mark omissions in the request so the model can tell an excerpt from a complete result.

4.3 Budget for the whole request#

I would count fixed instructions and tool definitions, task state, recent messages, and retrieved evidence separately. Leave room for output, growing tool results, and estimation error. A model can have distinct input, output, and total-window limits. The adapter must check each one.

input budget = available model window − reserved output − safety margin
optional history budget = input budget − fixed instructions − task state − recent content − required evidence

Take a hypothetical 128k window. Reserving 24k for output and headroom leaves at most 104k for input. Allocate 12k to fixed content, 24k to recent history, 8k to a state summary, and 16k to evidence. Only the remaining 44k is available for other history. These are illustrative allocations rather than measured or recommended thresholds.

If fixed content already takes up too much space, reduce the always-loaded tools and instructions. Further shortening the little chat history that remains will have little effect. If a single tool result can overflow the window, the runtime needs control over tool output before it enters the next turn.

4.4 Three visibility states for tool results#

StateIncluded in this turnWhen to use it
FULLOriginal content or the complete contents of a bounded rangeActive reasoning or an exact comparison
REFERENCEFactual summary, source ID, version, and retrieval pointerEvidence remains useful but the full text need not stay resident.
OMITTEDExcluded from this input; retained in history according to policyRepeated output or a completed line of inquiry

I would start with rules a developer can explain. Protect unresolved errors, the latest verification, and unfinished tool exchanges. Reduce repeated large-file reads to references. Once there is evaluation data, consider letting a model help choose the eviction order.

Protecting the last ten tool calls is one possible rule. Ten large logs can still exceed the window, while a much older user constraint can matter more than all ten.

4.5 Validate the version before adopting a background summary#

Suppose the background summary covers events through E100. While it runs, the session produces E101 through E108. Adopting the summary must preserve those new events. If the user switched branches, changed the goal, or selected another model, the old summary itself may no longer apply.

snapshot = capture(branch, prefix_end, instructions_hash, model_key)
candidate = summarize(snapshot.events)

at_next_safe_boundary:
  if prefix_still_matches(snapshot) and policy_still_matches(snapshot):
    atomically_append_checkpoint(candidate, base=snapshot.prefix_end)
    keep_all_events_after(snapshot.prefix_end)
  else:
    discard_or_recompute(candidate)

Define a safe boundary explicitly. In this design the runtime waits for the current batch of tools to settle and checks the candidate before compiling a request. If summarization fails or returns incomplete output, keep the previous checkpoint. Switch views only after persistence succeeds. Use versioning or compare-and-swap to coordinate concurrent updates to the messages.

4.6 Bound recovery attempts#

If the next turn still exceeds the window after compaction, first identify what grew: fixed instructions, an attachment, or a tool result. Cap recovery attempts and check the actual budget before and after each reduction. Repeatedly compacting and resending the same oversized input turns one failure into an expensive loop.

If the summary is unusable but the raw history survives, return to the last valid checkpoint and choose a new retention range. When switching models, rebuild a portable textual projection. An opaque provider checkpoint cannot serve as a universal session format.

5. How would we test whether it works?#

This is a proposed evaluation, with no measured ranking of products. I would prepare replayable tasks and compare full history, budget-based truncation, a summary plus recent content, evidence references, and state checkpoints. Use the same model, tool environment, and task inputs for each strategy.

Test caseWhat to check
The user changes a requirement midwayDoes the new constraint supersede the old decision? Does the agent keep pursuing an obsolete goal?
At least three consecutive compactionsDo unresolved issues, rejected options, or source references drift across rounds?
Long logs and parallel tool callsAre calls paired with results, failures retained, and overflow recovery bounded?
Branch changes, model switches, and restartsDo the session view, workspace state, and checkpoint still correspond?
A tool result contains instructionsDoes the agent promote external text to a user requirement or permission?
Work has already been submitted or publishedDoes the agent repeat an external action after forgetting that it completed?

Record task success, retention of critical constraints, evidence retrieval success, repeated tool calls, time spent waiting for compaction, and tokens and cost across the whole task. Cache-hit and compression ratios are secondary. More aggressive compaction can cost more overall if it sends the agent on a ten-turn detour.

I would save four artifacts: the input before compaction, the candidate summary, the actual request after adoption, and the next action. Together they help distinguish summary omissions, retrieval failures, malformed messages, and a model choosing poorly despite having the necessary evidence.

6. What I would build first#

Claude Code drew my attention to layering and isolation before information enters the main context. Pi shows how to make a session projection a data structure in its own right. OpenCode V2 brings caches, background precomputation, provider differences, and safe adoption into the same lifecycle.

Starting from scratch, I would build the event record, evidence references, task state, and request compiler first, then add verifiable summarization and recovery. The system should always be able to answer three questions: What did the model see this turn? Where did each conclusion come from? Why is the proposed next step still valid?

A larger window postpones compaction. Long tasks also need a way to preserve the goal, boundaries, and evidence as information accumulates.
