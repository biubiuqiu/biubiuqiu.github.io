Imagine 300 people each give their agent a personal computer. In the morning it uses Python to turn orders into a report. A user spends ten minutes checking the numbers, then asks for a chart by region. The report must survive that wait. Is it worth keeping the Python interpreter alive? What if all 300 users come back in the same minute?

Keeping a file, a process, or an entire machine can feel alike to a user. The platform pays very different prices for them. Start with a workspace that already runs Bash, writes code, and delivers files. Previously: Why does an agent need a sandbox?

One Lester computer across multiple conversations#

One Lester user who opens three conversations still owns one logical Computer. The sandbox table has a unique constraint on user_id . Each conversation starts its commands from /workspace/conversations/<id> . File tools check paths against the conversation's directory; the terminal, Python, Git, and the preinstalled browser share an environment. A new conversation can use prepared tools, and the prior task's report has its own home.[1]

I like one particular trade-off here. The Docker backend mounts a named volume at /workspace, calls docker stop when idle, and calls start on wake. The user returns to find that orders.csv still opens from disk, while the old interpreter's df is gone. Rerun the script to draw another chart. This preserves files across container stops and starts. But a default local volume remains on its original host. A replacement machine needs a way to retrieve it.[1]

I would split “one per user” into three decisions. File ownership determines who can return to a workspace. Which tasks may run together determines whether two sessions may edit the same file or claim the same port. Where compute runs determines who pays for idle gaps. Directories organize files, but shared processes can still clash over ports. Trusted personal tasks can share a toolchain; tasks with conflicting requirements or different permissions can get separate environments. These choices can evolve independently.

Identify waits during which compute can be reclaimed#

A GitHub Copilot production trace study gives an indication of scale. Researchers analyzed roughly 13 million sessions sampled in June 2026. Across multi-turn sessions the median share of elapsed time spent waiting for the user was 80.1%. This describes intervals between interactions. Estimating reclaimable sandbox minutes also requires knowing whether background jobs were running.[2]

Back to the report. Once the script has exited and written its result, the wait for human confirmation is easy to reclaim. If inference and orchestration live outside the sandbox, waiting for a model to write the next command can also free compute. But while the user reads the report, the sandbox browser might be exporting a PDF. Stopping it interrupts the export even if CPU use has been close to zero for several seconds.

I'd track foreground commands, background jobs, and previews that must stay available. The orchestrator can mark known pauses such as awaiting human approval. Keep the sandbox warm between short commands and reclaim early during known long waits. Lester documents a default idle threshold of 30 minutes. Google's Agent Substrate lets applications choose when to call suspend. Measure inter-call intervals on your own platform before deciding how much resume latency to impose on a short pause.[1] [3]

How Google places multiple sandboxes in one Pod#

Google has two similarly named designs. Agent Sandbox on GKE assigns a dedicated Pod to each Sandbox. The design discussed here, Agent Substrate , adds a layer. Kubernetes deploys Worker Pods. Each Worker can host several Actors concurrently. Actors have stable identities and are isolated using gVisor or microVMs. In the gVisor configuration, a Worker invokes runsc to manage sandboxes. Kubernetes schedules the Worker Pods; Substrate places Actors based on sandbox specifications and remaining capacity.[4] [5] [6]

Combine the designs: give the report user a durable workspace ID and map it to an Actor for execution. The first chart runs on Worker A; further commands route to A by Actor ID. Suspending frees space on A for someone else. When the user requests another chart, a compatible Worker B with available capacity can take over. The client retains only the workspace ID. Substrate records Actor–Worker mappings in PostgreSQL. Connecting Lester's personal workspaces to such a pool is my proposed design.[4]

Pooling changes failure and authorization boundaries. Lose a Worker with 20 active Actors and up to 20 restores arrive together. Density on a single machine determines the headroom needed for one failure. Network identity must follow the Actor. Google assigns Actors separate identities and can inject credentials by identity at an egress gateway. Two users sharing a Pod can then reach external services with their respective permissions.[6]

How many machines for 300 workspaces?#

Assume each user runs a tool for exactly one minute every ten minutes, with one more minute kept warm. A slot is enough capacity to meet one sandbox's resource guarantee. Each cycle consumes 300 × 2 = 600 slot-minutes, averaging 60 slots. Buying machines for that average ignores the timing of arrivals.

The chart models continuous work as repeating ten-minute cycles. Warm tasks can spill into the next cycle. Assume each sandbox receives a dedicated 1 vCPU and 2 GiB, and a node has 12 vCPUs and 24 GiB available after system and runtime overhead. One Worker then fits twelve sandboxes. Staggered and simultaneous starts require peaks of five and 25 nodes respectively. This assumes no queuing and excludes control plane resources, failure reserves, and node startup time. Actual prices and machine performance must be measured separately.

Google's model published November 16 also identifies when the savings fade. It compares 100 coding agents at us-central1 on-demand prices against a baseline of one always-on Pod per session. At equal CPU guarantees and working hours, suspension saves nearly 40% of node cost at two prompts per person per hour. At four prompts per hour, savings shrink to about 4%. The model scales the worker pool to zero outside working hours. Match CPU guarantees in your own comparison, or savings from overcommit may be misattributed to suspension.[3]

I'd keep two separate accounts. First, slot-minutes released, valuable when another task takes them. Second, billable node-hours avoided. Those appear on the bill only when an entire node can stop accruing charges. If every machine has one long-running task, the numbers can diverge sharply. Favor packing new work into existing space and drain Workers slated for removal to consolidate idle fragments. Compare the reclaimable value of each gap with incremental snapshot write, storage, and read costs. Even a positive balance must fit the user's tolerance for restore latency.

What should the report take to a replacement Worker?#

My test for a stateless execution tier is a host replacement. Lose Worker A, send the same user to B, and check what they can recover. A running sandbox has memory and processes. What the platform can do is remove the only important copy of state from the Worker and make the host replaceable.

What the user wants to continueWhat must persistHow to continue on B
Edit a saved reportWorkspace files and committed artifact versionsRemount the user's persistent volume or open the committed version
Draw another chart with the same librariesBase image version, dependency lockfile, and private changesReuse read-only layers, install missing dependencies from the lockfile, and rebuild caches
Keep working with df in memoryCompatible process and memory snapshot with matching file versionsRestore the interpreter when compatible; otherwise restart and recompute from the files
Check whether the report has been publishedTask record, operation ID, and remote service receiptReconcile the remote result and link the artifact back to the original conversation

File durability depends on when you tell the user “saved.” If the only copy is local and uploaded to S3 on exit, losing a node just after acknowledgment can prevent the write from ever reaching a snapshot. To survive loss of one node, persist the write before reporting success. EFS Regional, for example, documents cross-AZ durability after synchronous writes or closing a file. A file tool can acknowledge once the chosen storage's commit conditions are satisfied. Bytes still buffered in userspace by an arbitrary Bash program must first be flushed.[7]

If most tasks edit a few scripts and publish a few artifacts, a lighter path uploads versioned artifacts to object storage, then commits a manifest pointing at the successful upload. Interactive terminals, renames, and edits during execution are a better fit for a persistent filesystem. Use both: keep live edits on an attached working volume and published versions and backups in object storage. Hundreds of MiB of reference data need not move on each suspension.

Price process continuity separately. Subject to compatibility, Agent Substrate can restore memory, root filesystem modifications, and persistent directories. Incompatible hardware or runtimes may still allow files to be retained with a fresh process. After template image changes only persistent directories may survive. External CSI volumes remount from the original storage. Synchronous suspension waits for remote upload; asynchronous mode allows the remote copy to remain temporarily PENDING. Base the decision to remove a machine on the latest version actually restorable on another host.[6] [5] [8]

There is a subtler consistency problem. If the interpreter snapshot's df came from Monday but another task has updated the remounted workspace to Tuesday's data, even a successful resume can give a wrong answer. I'd record the input or workspace commit version in the snapshot manifest. On a mismatch, restart the interpreter and show the user why a recomputation was necessary. Durable files and restorable processes are separate contracts; joining them requires a consistent point in time.

A late write from the old Worker#

A is writing the report when a network interruption stops its heartbeats reaching the control plane. B takes over the workspace. Ten seconds later A reconnects with its old file handle still open. When both machines can write, new routing cannot stop A from overwriting B's edits.

Lester uses per-user PostgreSQL transaction locks to stop two API replicas creating a Computer concurrently. A handoff must also handle an old owner that remains alive. Give each takeover an increasing generation: A gets 41, B gets 42. At commit the publication service checks the current generation and rejects A's late 41. This is a fencing token. Bash writing directly to writable NFS bypasses that service. Revoke the old node's write access first, or write separate copies per generation and check the generation at publication. Updating a lease row cannot govern an already-open file handle.[1] [9]

An external receipt can also arrive late. The publication endpoint may have accepted the report before A lost the response. If B replays publication from a snapshot, readers may get two copies. Assign each publication a stable operation ID in the durable task record. Reuse it for deduplication if supported by the external API, then record the receipt. If the API offers neither idempotency nor lookup, keep the result pending reconciliation. Lester persists GitHub publication receipts and checks uncertain writes before retrying. For a user deciding whether to click Continue, this matters more than a surviving terminal process.[1] [10]

When scaling out, how long until the first useful command finishes?#

At 9 a.m., 100 workspaces wake at once. If each reads a 128 MiB compressed snapshot from remote storage and all must finish in ten seconds, the network alone must deliver 1.25 GiB/s of effective throughput, before decompression and random reads. More Workers with idle CPUs won't fix that shared bandwidth bottleneck. Simultaneous scale-in can likewise cause a burst of snapshot writes. Google's capacity guide sizes snapshot bandwidth, node disks, and upload concurrency separately.[5]

E2B's open-source runtime makes another trade-off. Templates are snapshots of prebooted Firecracker microVMs. Memory pages load on first access, and the root filesystem uses copy-on-write over a read-only image. A task running only ls can start quickly, while importing large libraries and actually drawing the chart may trigger more page faults and remote reads. Measure P95 both from restore request to ready and from restore request to completion of the first useful command. Run the real reporting script on cold nodes.[11]

Different observations call for different scaling actions. If slots run out and jobs queue, add Workers; expand the node pool when new Worker Pods no longer fit. If slots remain but snapshot reads stall, inspect remote bandwidth and node cache hit rates. When scaling in, stop assigning fresh tasks to the targeted Worker, then let in-flight jobs finish or wait until required snapshots are recoverable remotely before removing the node.

For Lester's next version I'd keep one workspace per user and make acknowledged files and publication receipts verifiable after a host change. Collect a week of tool start and stop times, background activity, and restore latency. Size for the busiest minutes; calculate cost from the entire week's node-hours. Restart cheaply for reports reproducible from files, and snapshot notebooks that need live memory separately. Introduce multi-sandbox Workers once the recovered idle capacity justifies maintaining another scheduler.

My acceptance test is the opening report. Let the user check the data and return. Give a different worker node the same input, produce the right chart, and publish it exactly once. If the bill also reflects those ten minutes of released capacity, there is a reason to roll it out to more users.
