A model can write a script to analyze data. Where does the script run? Where does its output go, and can the next step find it? Moving from answering questions to completing tasks takes more than a longer context window. An agent needs a workspace where it can compute, retain results, and test its assumptions.

Scope · 2026-11-14

This article starts with a task and uses official documentation to explain the operating-system mechanisms behind a sandbox. Diagrams, filenames, and interfaces are teaching examples. The implementation sketches are design proposals. I did not benchmark or compare the security of the isolation technologies discussed here.

1. A model can propose a procedure. Something has to execute it.#

Consider a routine request. A user uploads a CSV of orders and asks for a total, a report, and a check of the results. The model can interpret the columns, decide what to count, and write Python. Getting a number from the actual data still requires someone to run that code.

Model inference consumes compute too. Here, a compute environment means the external environment a model uses through tools. A CPU executes the program, memory holds data in flight, a filesystem stores inputs and outputs, and an operating system manages processes. The model requests this work through a tool call. Python runs as a separate process.

Think of giving the agent a computer it can operate. It can put a script there, run it, inspect an error, fix it, rerun it, and deliver a file that actually exists. Artifacts, logs, and exit status give it evidence for the next decision.

1.1 Why not send all the data to the model?#

For well-defined iteration, sorting, aggregation, or format conversion, a program is usually a better fit. The model specifies the rule and the code applies it to every record. A large file needn't pass through the context window one row at a time just to calculate a total.

Anthropic's article on code execution illustrates this pattern. Data is filtered and transformed in the execution environment, and only the necessary results return to the model. Files hold intermediate state between operations.[1] In other words, the workspace extends beyond the context window. The model can see summaries, samples, and failures while complete inputs and outputs live elsewhere.

Execution alone cannot guarantee correctness. Whether amounts are concatenated as strings or added as numbers, whether refunds are deducted, and which units apply all depend on the task definition and the code. Set the rules, run the program, then verify the result.

1.2 Why not just offer a hundred predefined tools?#

Fixed tools work well for narrowly defined business actions such as looking up an order or creating a calendar event. A workspace lets an agent compose a new sequence on demand: parse a new format, write a filter, convert a document with an existing library, then pass the output to another tool. Each new combination can run without waiting for a bespoke API.

Not every agent needs a dedicated sandbox. If the job consists of selecting and orchestrating authorized business APIs, tool servers may handle all the execution. A dedicated workspace becomes valuable with dynamically written code, large files, artifacts passed between steps, or long-running processes. Protocols such as MCP define how tools connect and are called. Execution capacity must come from somewhere else.

2. Following a task from request to deliverable#

Here the model can delegate arithmetic but still needs to understand the data, propose an appropriate program, and adapt to its output. Errors become new observations. After a successful exit it must still verify that the file exists, the row count is plausible, and the aggregation used the agreed rules.

# orders.csv is in the current directory; amounts are whole yuan
import csv
from pathlib import Path

with open("orders.csv", newline="", encoding="utf-8") as f:
    rows = list(csv.DictReader(f))

total = sum(int(row["amount"]) for row in rows)
Path("summary.csv").write_text(
    f"order_count,total_amount\n{len(rows)},{total}\n",
    encoding="utf-8",
)
print({"order_count": len(rows), "total_amount": total})

The expected result is three orders totaling 500 yuan. Real data may include fractional amounts, missing values, duplicate orders, or multiple currencies. Those require additional rules and validation. The generated file still resides in the workspace. A download or artifact endpoint must deliver it to the user.

3. What does this computer provide?#

A directory holds files but cannot explain where processes run, where dependencies come from, which networks are reachable, or who enforces limits. Look at the workspace in terms of five capabilities.

3.1 Filesystems move intermediate state out of the conversation#

An input CSV, analysis script, chart, and test log can each have a path. A later tool call reads the relevant files to continue without embedding everything in the next prompt. Files also let programs exchange data: one writes a CSV and another plots it.

A stable path does not imply stable contents. A conversation summary may mention a file that has since been deleted, overwritten, or moved. Inspect the real state after a restore.

3.2 Processes give an action a trackable identity#

Running Python, starting a browser, compiling, and waiting for tests all involve processes. A process has a PID, exit status, standard output and error, children, and elapsed time. The model may start another reasoning step before a command finishes. The runtime needs a task ID to track ongoing work.

The model and process can run on different machines. The runtime dispatches commands over a controlled connection, collects output, and returns it. Browsers, GPUs, or large computations can use separate execution services. One sandbox needn't contain every capability.

3.3 Dependencies and resources make execution predictable#

Scripts need Python and libraries, pages need a browser, and video processing needs codecs. A base image supplies reusable software. Project files and configuration turn it into a task workspace. Pin versions, consider download sources and caches, and account for network installations failing.

CPU, memory, disk, process count, and execution time determine the size of a feasible job. An infinite loop should not occupy the entire host indefinitely. A program may start successfully and still run out of memory loading the data.

4. Why the workspace needs a sandbox boundary#

So far we have seen why a workspace is useful. Now ask how far the damage can spread if a generated program uses the wrong path, consumes unbounded resources, or reads untrusted content.

A dedicated compute environment and a security boundary are distinct properties. A directory and a shell can form a workspace with little isolation. A sandbox adds runtime and OS controls over which resources a process can see, what it can do, and what it can affect.

Each protection needs explicit configuration and verification. Drawing a boundary does not enforce it.

4.1 Each mechanism addresses a different problem#

MechanismWhat it constrainsWhat you cannot infer
NamespacesViews and naming scopes for processes, mounts, networks, and other resourcesThat entering a namespace makes arbitrary code safe
CgroupsAccounting and limits for CPU, memory, processes, and other resourcesThat limiting memory also restricts file reads and network access
Capabilities / Seccomp / LSMNarrow privileges, allowable system calls, and access scopeThat a syscall filter alone constitutes a complete sandbox
File and network policiesMount scope, read/write permissions, outbound destinations, and egressThat filesystem isolation implies network isolation

Docker's documentation describes the separate roles of namespaces and resource controls. The Linux documentation explicitly warns that seccomp syscall filtering alone does not make a complete sandbox.[2][3] Whichever technology you choose, configure mounts, permissions, and network policies as well.

A prompt asking a model to stay in one directory is behavioral guidance. An OS denying access enforces a boundary. Lower layers can reject an action the model approved, and permission to send a network request does not authorize changes to remote business data.

4.2 Containers, gVisor, and microVMs put the boundary in different places#

Ordinary Linux container processes share the host kernel. gVisor implements a Linux-style application kernel in userspace and provides runsc for integration with container tooling.[4] Firecracker runs microVMs through KVM, giving each workload a guest kernel.[5]

The diagram compares logical layers, rather than tracing every syscall. Consider compatibility, workload characteristics, startup and maintenance costs, and trust between tenants. It gives no universal performance ranking. A microVM also needs egress controls: Firecracker explicitly delegates network filtering to the host.[5]

Distinguish two use cases. A local coding assistant can constrain commands in an existing development directory. A cloud agent can receive a fresh remote environment. Claude Code's sandboxed Bash documentation describes filesystem and network controls. It does not imply that every call creates a VM.[6]

5. Specify which state survives#

Conversations, files, and processes are three kinds of state. A saved conversation proves nothing about its files. Even if the files survived, a running Python process, an in-memory variable, or a browser connection may be gone.

Kubernetes distinguishes ephemeral volumes tied to a Pod's lifetime from persistent volumes that outlive an individual Pod.[7] Design workspace reclamation and storage policy together.

A common approach persists important files, releases compute when idle, then remounts storage and starts fresh processes. Another saves execution state with supported checkpoint/restore mechanisms. gVisor offers this, but restore still depends on filesystem consistency, network connections, and environment compatibility. It cannot promise unchanged behavior on any arbitrary machine.[8]

My interpretation. Pausing, process snapshots, file persistence, object storage archives, and backups solve different problems. An upload on exit creates an archive but leaves writes before an abrupt crash unprotected. A durability promise must specify when writes are acknowledged, where they persist, what failures it covers, and the recovery objective. An exit hook alone cannot make that promise.

6. One workspace per user or per session?#

This is a product and resource-management decision. The model does not dictate it. Sandboxes, containers, Pods, and working directories need not map one-to-one. A scheduling unit can contain multiple isolated instances. Whether it should depends on the isolation mechanism and platform design.

AllocationBenefitsTrade-offs
Ephemeral environment per callSimple cleanup; suits small, independent computationsState must be transferred explicitly across steps; dependency setup can repeat
Workspace per sessionClear task state and easier separation between sessionsMore instances; dependencies and file sharing need a design
Workspace per userReuse personal files and dependenciesConcurrent sessions compete over files, ports, dependency versions, and background processes

Implementation sketch. Separate long-lived file ownership from short-lived execution instances. A user owns durable storage, while each task receives a restricted working directory or an isolated instance. A subdirectory per session organizes files; it cannot prevent access across directories without runtime and OS enforcement.

7. Connecting tool calls to the workspace#

In my implementation I'd expose stable tool semantics to the model and have the runtime locate the physical machine. For example:

{
  "workspace_id": "ws-demo",
  "operation": "exec",
  "command": ["python", "analyze.py"],
  "cwd": "/workspace",
  "timeout_ms": 30000,
  "request_id": "run-demo-1"
}

This is a proposed interface, not a particular product's API. Bind the authenticated identity to the workspaces it can access. A client-supplied workspace ID does not establish authorization. request_id is a correlation ID. It provides idempotency only when the server defines deduplication and records side effects.

The execution service must report readiness, whether a command is running, its exit status, output truncation, artifact locations, and whether cancellation cleaned up child processes. Routing must send subsequent operations to the right workspace. If several executors might take over, use leases or another concurrency control to prevent duplicate execution.

The sandbox and the agent have distinct responsibilities. The external runtime can interpret goals, request inference, select context, and orchestrate tasks. The sandbox holds the dispatched computation and its state. A clear interface allows them to scale independently and helps locate failures in model inference, dispatch, or execution.

How I'd test the design. Take a task through reading input, writing a script, running it, fixing it, and delivery. Stop the compute instance mid-task and verify the promised files survive. Exercise oversized output, out-of-memory conditions, timeouts, and concurrent writes. Check that the service reports what actually happened. These tests say more about whether an agent has a usable workspace than a successful container startup does.

When I say an agent needs a sandbox, this is what I mean: it needs an environment it can operate to turn proposed steps into computations, files, and verifiable results, with explicit boundaries around those operations. Compute extends what it can do. Saved state connects the steps. Observations let it correct errors. Isolation makes it possible to offer these capabilities within defined limits.
