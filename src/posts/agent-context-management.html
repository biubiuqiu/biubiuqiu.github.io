同一个模型，为什么换一个 Agent 产品，长任务的表现就不一样？我更关心的差异，是它每一轮究竟让模型看见什么，以及它如何保证：省掉一段历史之后，任务仍然能接得住。

研究范围 · 2026-11-13

Claude Code 依据官方公开文档讨论行为，不推断其未公开实现。Pi 与 OpenCode 同时阅读了固定提交的源码；OpenCode 以 V2 为准。下文分别标注“已证实”“分析”和“实现推演”。本文没有运行三款产品的统一性能测试，预算数字与伪代码是设计示例。

阅读路径先分清四种状态三款产品的实现差异值得借鉴的设计判断一个可以落地的上下文层如何验证它真的有效研究来源与源码快照

一、先分清：历史、上下文、记忆与运行环境

我的分析：“Agent 记住了什么”至少包含四个不同问题。把它们合并成一个 messages 数组，很容易在恢复、切换模型和压缩时产生混乱。

层次负责保存什么不能据此认定什么
会话历史用户消息、模型响应、工具调用与结果等事件保存过，就意味着下一轮全部发送
当前上下文本次模型请求实际包含的输入没发送，就意味着原始内容被删除
长期记忆跨会话有价值的偏好、事实与定位线索所有历史都应被提升成长期事实
运行环境文件、进程、工作目录及外部副作用恢复聊天，就等于恢复文件和进程

例如，一次测试日志可以完整保存在历史里，当前请求只带失败结论和可定位引用；“这个项目用什么命令测试”可能适合项目指令；测试时生成的文件则属于工作区。它们的保存周期与恢复方法并不相同。

因此，我把本轮输入理解为一个计算结果：当前输入 = 指令 + 任务状态 + 被选中的历史 + 必要证据。Anthropic 对 context engineering 的描述，同样强调每一轮都要整理有限窗口中的有效信息。[12]

二、三款产品分别把复杂度放在哪里？

先给出对照。这里比较的是可核实的机制，不能据此排出整体能力高低。

产品与证据范围压缩与续接值得注意的边界
Claude Code · 官方文档自动或手动 compact；项目指令、按需加载与独立子任务上下文协作公开行为不等于完整内部算法
Pi · 固定源码快照结构化摘要、保留边界、会话树和上下文投影原始记录与模型可见消息分开处理
OpenCode V2 · 固定源码快照摘要加近期内容；可选后台预计算；区分自身摘要与 provider 原生压缩V1 的 pruning 解释不能直接套到 V2

2.1 Claude Code：先减少进入主上下文的信息

已证实：官方文档明确描述了自动压缩和带重点的 /compact。它也从入口控制上下文：Skills 的完整内容按需加载，MCP 工具定义可经工具搜索延迟加载；子 Agent 的工具过程留在自己的上下文中，主会话接收结果摘要。[1]

这意味着，压缩并非唯一调节手段。对大量搜索、日志分析这样的侧任务，把过程留在独立上下文，可以减少主任务反复携带的噪声。不过，子任务仍会花费自己的 token；fork 还会继承父上下文，不能把它理解成一个零成本的空白窗口。[4]

已证实：项目指令与 Auto memory 是另一条跨会话通道。官方文档描述了简短的 MEMORY.md 入口和按需读取的主题文件；在研究时点，入口加载上限是前 200 行或 25KB，以先到者为准。这是索引入口的边界，不是整个记忆目录的容量。[2]

我的分析：这里最值得借鉴的是分层：常驻规则负责约束，按需知识负责补充，当前摘要负责续接。若把三者全写进一份越来越长的“永久提示词”，只是把会话膨胀转移到了启动阶段。

Claude Code 的精确摘要选择算法、每项内部阈值和所有回退分支，不能仅凭这些文档还原。更不能因为 Claude API 有某种 context management 能力，就认定 Claude Code 在所有路径都使用同一种实现。

2.2 Pi：把“下一轮能看见什么”做成可重建的投影

已证实：Pi 的摘要记录包含 summary、firstKeptEntryId、tokensBefore 等字段。在所读快照中，默认预留量是 16,384 tokens，近期保留目标是 20,000 tokens；它们分别控制触发与保留，不是同一个“摘要长度”。切分时还要考虑工具调用与结果的完整性。[5]

比默认数字更有意思的是结构。session-manager.ts 用 id 与 parentId 表达会话路径，由 buildContextEntries() 选择当前摘要与保留区间，再由 buildSessionProjection() 应用上下文编辑，最后形成模型消息。上下文编辑可以改变内容或省略某条记录，而原始条目仍可存在。[7]

我的分析：这给了上层产品一个清楚的设计方向：历史是事实记录，模型输入是基于事实记录生成的视图。分支、回放、压缩就不必都通过破坏性地改写一个数组完成。但能重建“当时发过什么”，仍不代表能重现模型的随机输出或撤销已发生的工具副作用。

已证实：Pi 的默认摘要围绕目标、约束、进度、决策、下一步与关键上下文组织。token 估计会利用最近可用的 usage，再估算其后的新增消息。摘要生成则先把对话序列化，构造专门的摘要请求；对不完整摘要和试图调用工具的摘要响应有校验。[6]

我的分析：“下一步做什么、为什么不能做另一个选择”，往往比“刚才调用了哪些工具”更接近任务的最小续接状态。摘要应该优化接手者的决策，而非聊天记录的覆盖率。

2.3 OpenCode V2：连压缩本身也进入调度

已证实：当前 V2 文档描述的是摘要与近期内容共同续接，近期保留目标默认为约 15,000 tokens；buffer 管理预留空间。文档明确区分 V1 的 tail-turn / pruning 行为。保留的近期内容也不是所有数据逐字不动：长工具输出会被缩短，附件数据会变为简短描述。[8] 配置定义也已使用 auto、keep.tokens、buffer 这些字段。[11]

已证实：源码让正常摘要请求尽可能沿用现有对话前缀，再附加摘要要求，以尝试复用 provider 的 prompt cache。实验性的后台路径会提前生成并暂存摘要，到真正需要压缩时再决定是否切入；若模型、指令或历史前缀等条件不再匹配，就不能简单复用。[9]

此外，它区分自己生成的文本摘要与 provider 原生压缩。后者可能产生不透明检查点，其可迁移性受 provider 和模型限制。不能假设“压缩后切换模型”只需换一个 model 字段。[8]

我的分析：后台摘要真正难的部分，不是多开一次 LLM 请求，而是证明它在切入时仍然对应当前会话。它更像一个有版本条件的状态更新，而不是生成完一段文字就结束。

三、我认为最重要的四个判断

3.1 压缩目标应该是“能继续做对”，不是“摘要读起来完整”

设想用户要求修改支付回调，同时明确“不要改数据库结构”。随后 Agent 连续读文件、运行测试，积累了大量日志。一份摘要即使详细描述了测试过程，只要丢掉这条限制，就可能在下一轮把任务方向带偏。

我的推论：摘要至少应保住目标、用户限制、已验证事实、尚未证实的假设、已完成的外部动作、当前阻塞和下一步。文件中可以重新读取的细节适合缩成引用；用户已经排除的方案则未必能靠重新读代码找回来。

3.2 能再次读取的证据，应该有稳定地址和版本

“详细日志已省略”不足以支持续接。更有用的是：哪次运行、哪个工具调用、日志哪一段、对应哪个代码版本。否则，模型想补证据时，只能再跑一遍命令，而命令可能很贵、不可重复，或者会产生新的副作用。

工作区文件也会变化。一个文件路径定位的是当前内容；原始工具输出或带哈希的快照，才能定位当时观察到的内容。两者都需要，并应明确区分。

3.3 Prompt cache 是成本机制，不是语义记忆

已证实：Claude Code 文档将压缩后的对话层缓存变化，与系统提示和项目上下文层分开说明。压缩会改变历史前缀，但其他稳定层仍可能复用缓存。[3] OpenCode 的上下文组装代码也刻意把更共享、更稳定的指令放到前面。[10]

我的推论：每轮少发一点，并不必然更便宜。频繁改写早期内容，可能让后续大段前缀重新计算。反过来，缓存命中高也不代表模型“记住得好”：被缓存的输入照样占窗口，也可能带来无关信息。应分别看输入规模、缓存成本与任务质量。

3.4 压缩不能制造新的授权

研究日志、网页和仓库文件时，工具结果可能包含指令式文字。如果摘要把“某网页声称可以执行”改写成“用户已允许执行”，信息就跨越了信任边界。

我的设计判断：用户指令、工具观察、模型假设应带不同来源。授权必须由原始用户事件或产品权限状态证明，不能靠摘要中的一句话成立。把内容压短，不应把它的身份也压没。

四、实现推演：为自己的 Agent 做一个上下文层

以下是我的方案推演，不是对三款产品内部实现的描述。我会先建立可回放的数据结构，再加摘要能力。

4.1 保留事件，单独编译本轮输入

会话事件只追加，较大的工具输出放在持久化工件里，事件保存引用。单独的上下文编译器，根据当前分支、任务状态、证据与预算生成请求。它可以省略内容，却不应偷偷销毁原始记录。

// 设计示例，不对应任何产品的现有接口
SessionEvent {
  event_id, session_id, branch_id, parent_id,
  role, kind, content_ref, tool_call_id,
  provenance, created_at
}

ContextCheckpoint {
  checkpoint_id, base_event_id, source_event_ids,
  summary_ref, retained_from_event_id,
  model_key, instructions_hash, projection_version
}

这里的 checkpoint 只描述会话上下文。文件系统检查点、进程恢复与外部 API 的执行记录需要各自的机制，不能由这张表替代。原始事件的保留也应遵守产品的数据删除和租户隔离规则，而不是无限制永久保存。

4.2 工具交换按完整单元处理

不能只按消息条数粗暴截断。一次 assistant tool call 和对应的结果需要共同参与边界判断；并行工具还可能有多个结果。若必须缩短结果，要保留工具 ID、状态、关键证据与取回方式，并让适配器保证 provider 所要求的消息结构合法。

超大输出可以先持久化，再发送有范围的片段。编译器必须知道“截断了什么”；模型也应看到省略标记，而不是把不完整片段误认为全量结果。

4.3 预算由整次请求决定

我会分别计入固定指令与工具定义、任务状态、近期消息、检索证据，并为输出、工具增长和估算误差留空间。具体模型可能同时限制输入、输出和总窗口，适配层必须分别检查。

输入预算 = 模型可用窗口 - 本次输出预留 - 安全余量
可裁剪历史预算 = 输入预算 - 固定指令 - 任务状态 - 近期内容 - 必要证据

例如在一个假设的 128k 总窗口里，先为输出与余量留 24k，输入目标不超过 104k。再给固定内容 12k、近期内容 24k、状态摘要 8k、证据 16k，剩余约 44k 才可分配给其他历史。这只是预算演示，不是推荐阈值或实测结果。

若固定内容已经过大，应减少常驻工具和指令；继续摘要剩下的一小段聊天，不会解决根因。若一次工具返回就足以越界，控制点还必须前移到工具输出进入下一轮之前。

4.4 工具结果可以有三种可见状态

状态本轮携带适合场景
FULL原始或有范围的完整内容当前正在推理、需要精确比对
REFERENCE事实摘要、来源 ID、版本与取回入口信息仍有价值，但不必常驻全文
OMITTED不参与本轮输入，历史仍按保留策略存储重复输出、已结束的探索支线

我更愿意先实现可解释的规则：保护未解决错误、最近一次验证、仍未完成的工具交换；重复的大文件读取降为引用。等有了评测数据，再考虑让模型参与决定淘汰顺序。

“最近十次工具调用”可以作为保护规则之一，却不能作为全部策略。十次大日志可能仍然超窗，而更早的一条用户限制反而最重要。

4.5 后台摘要用版本校验切入

假设后台摘要只覆盖到事件 E100，它运行期间会话又产生了 E101 到 E108。正确的切入结果应保留这些新增事件；如果用户已经切换分支、修改目标或换了模型，原来的摘要还未必可以用。

snapshot = capture(branch, prefix_end, instructions_hash, model_key)
candidate = summarize(snapshot.events)

at_next_safe_boundary:
  if prefix_still_matches(snapshot) and policy_still_matches(snapshot):
    atomically_append_checkpoint(candidate, base=snapshot.prefix_end)
    keep_all_events_after(snapshot.prefix_end)
  else:
    discard_or_recompute(candidate)

“安全边界”也要有定义：本设计会等待当前工具批次结算，并在请求编译前检查。候选摘要失败或不完整时，不覆盖旧检查点；持久化完成后再切换视图。这里需要版本号或比较并交换，而不是让两个异步任务同时改 messages。

4.6 提供有上限的失败恢复

如果压缩后下一轮仍超窗，我会先判断增长来自哪里：固定指令、单个附件，还是工具结果。恢复尝试必须有上限，并校验缩减前后的实际预算。不断“压缩—重发同一个超大输入”，只是把失败变成昂贵的循环。

如果摘要不可用，但原始历史还在，可以回到上一个有效检查点，重新选择保留区间。跨模型时则重建可移植的文本投影；provider 不透明检查点不能被当作通用会话格式。

五、如何验证它真的有效？

以下是待执行的评测方案，本文没有宣称测出了产品排名。我会准备一组能反复回放的任务，分别比较全量历史、按预算截断、摘要加近期内容、引用化证据与状态检查点几种策略。模型、工具环境和任务输入保持一致。

测试场景重点检查
用户中途改变要求新约束是否覆盖旧决策，旧目标是否继续被执行
连续三次以上压缩未解决问题、被排除方案、来源引用是否逐轮漂移
长日志与并行工具调用结果配对、失败信息保留、超窗恢复是否有界
切分支、换模型、重启会话视图、工作区状态与检查点是否明确对应
工具结果夹带指令是否把外部文字升级成用户要求或授权
已提交或已发布的任务是否遗忘动作状态而重复执行有副作用的操作

记录任务成功率、关键约束保留率、证据取回成功率、重复工具调用、压缩等待时长，以及整个任务的 token 与费用。缓存命中率和摘要压缩比只是辅助指标；如果压缩更狠，却让 Agent 多绕了十轮，整体收益可能为负。

我还会保存“压缩前输入、摘要候选、切入后的实际请求、下一步动作”这四份产物。只有这样，才能分清一次失败究竟来自摘要遗漏、检索失败、消息结构错误，还是模型在已有证据下做错了判断。

六、最后的判断

Claude Code 让我更关注进入上下文之前的分层与隔离；Pi 让我看到会话投影如何成为独立的数据结构；OpenCode V2 则把缓存、后台预计算、provider 差异与安全切入放进同一套生命周期里。

如果从零做一个 Agent，我会优先把事件记录、证据引用、任务状态和请求编译器做好，再加可验证的摘要与恢复。让系统始终能回答三个问题：这轮模型看到了什么？哪些结论来自哪里？下一步为什么还成立？

长上下文能延后压缩，但更可靠的长任务，需要的是在信息越来越多时，仍能保住目标、边界和证据的能力。
