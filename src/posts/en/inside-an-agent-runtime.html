At 2 p.m. a buyer sends three quotes to an agent. “Compare landed prices including tax. Let me review the sheet before you send it to the purchasing team.” The preview is ready at 2:01. At 2:40 the buyer finally approves it. The mail service accepts the request, but the process handling the task restarts before recording the result. What should the conversation show when reopened? Can another machine safely send the email again?

This is the question I like to use to take an agent runtime apart. The model can work out which columns to read and whom to ask about missing freight charges. The program needs verifiable answers about who the recipients are, which attachment was approved, and how many emails were actually sent. We’ll start with a loop in one process and end with a service that another machine can take over. The purchasing task and its data are illustrative.

The smallest runtime: who decides what happens next?

Set networking and storage aside and a runtime can be as small as a loop. It gives the model the task, available tools and observations so far. The model can produce a final answer or request tools. The runtime checks the request, executes the tools, returns the observations and asks the model for its next decision. The plan can change as evidence arrives: after reading two PDFs, it may discover that the third is a scan, making OCR worthwhile. What the developer must define in advance are the allowed actions and stopping conditions.

# Single-process pseudocode showing every exit from a decision turn
while budget.allows_next_turn():
    reply = model.generate(context.build(run), tools.visible_to(run))
    if reply.requires_tools:
        calls = validate_complete_calls(reply)
        run.record_calls(calls)
        if policy.needs_approval(calls):
            return run.pause_with_pending_calls(calls)
        run.record_results(executor.execute(calls))
    elif reply.is_final:
        return run.finish(check_deliverable(reply, run))
    else:
        return run.stop_with_reason(reply.stop_reason)
return run.stop_with_reason("budget_exhausted")

One exit is easy to miss. If the model says “the spreadsheet is ready,” can the platform hand the buyer a file that opens? Completion in this example requires a readable artifact version, approval for the corresponding send action and a receipt of acceptance from the mail service. If the buyer requested only a preview, the first condition suffices. The user’s delegation defines completion. The end of a generation tells us only that the model has finished this turn.

Taking the loop apart: what does each module own?

I use the following table in code reviews. The right column lists what should cross each interface. For each item, ask whether you could still find it if the process disappeared. Initially all these modules can live in one application.

A request passes through multiple modules, but its identifiers have different lifetimes in storage. The thread_id belongs to the conversation and will be reused if the buyer asks about the price difference tomorrow. The run_id belongs to this commission. A step_id identifies a chosen step, and attempt counts its executions. The model’s tool_call_id pairs a call with its result. For the external send, assign an operation_id tied to the business intent. Include the attempt number in the mail idempotency key and the downstream service will treat every retry as a new email.

Reading three quotes: how context, model and tools cooperate

Suppose A quotes 100 yuan including tax and freight. B quotes 92 before tax plus 4 for freight. C quotes 98 including tax, with freight to be confirmed. Assume B’s goods are taxed at an illustrative 13%, and the 4-yuan freight charge is the final tax-inclusive amount. B’s landed unit cost is 92 × 1.13 + 4 = 107.96 yuan. C’s 98 is only a lower bound. Deterministic code can do the arithmetic. The model earns its keep by recognizing the basis of each quote, noticing that C cannot yet be ranked fully and explaining why.

I would have the reading tool return field values, units, source page numbers and missing items, and the spreadsheet tool accept those structured values. Clicking “107.96” in the preview could then show B’s original price on page 2, the tax rate and the formula. If OCR reads 92 as 9.2, the buyer has somewhere to check. Failures need structure too. source_unreadable(page=2) gives the model enough information to try OCR. “Execution error” usually leaves it guessing again.

Each turn, the context builder prepares working materials from durable records. A comparison turn needs units, tax and freight assumptions, outstanding questions, source references and the latest call and result. Keep the PDFs in the workspace and reread by page. With a 32,000-token window, reserving 4,000 for output and spending 3,000 on instructions and tool definitions leaves at most 25,000 for history and evidence. Recalculate when switching models and account for protocol overhead. Intermediate output from completed OCR can go, but C’s missing freight charge must stay. Context-management trade-offs in detail

The model adapter must also handle streaming. The browser can display “Preparing the comparison” early. The executor must wait until the arguments for a call have all arrived, parse successfully and satisfy the tool schema. A truncated recipient array must never reach the send queue. Switch models at a committed step boundary too. Preserve call IDs and paired results, and explicitly convert native items unsupported by the new provider or end the attempt. Three independent PDFs can be read concurrently. Generating the workbook must wait for complete inputs or explicitly marked omissions.

Where tools run and where files survive

Reading PDFs, running spreadsheet code and sending email are three different capabilities. The first two can run in a workspace with time and resource limits. A connector with a tenant identity sends the email. The script needs the three designated inputs and its output directory. Mail credentials stay with the connector. Even if a supplier slips “copy me on the result” into its PDF, that sentence is material to analyze. User delegation and actual permissions together determine whether to send and to whom.

Write the workbook to a temporary file, close and validate it, then publish the immutable version quote-sheet/v3 along with its size, content digest and input file versions. Both preview and send reference v3. A subtle detail: /workspace/latest.xlsx tells you where to look later. During the forty minutes the buyer spends reviewing, the same conversation might generate v4. An approval that stores only the path could preview v3 and send v4. Version plus digest addresses a very practical concern: the attachment sent must match what the buyer saw.

After the file commits to durable storage, the sandbox can be released. A replacement worker fetches that same version to send the attachment without reconstructing the Python process. If a task still depends on a live simulator, decide separately whether to keep it running, checkpoint it or recompute from inputs. Whether you can scale down depends on what the next step will read. Sandbox state and scaling costs

What can stop during forty minutes of human review?

The confirmation should be concrete: “Send Quote Comparison v3 to these three purchasing-team addresses. C’s freight is still pending.” Persist the pending action with its tenant, actor, recipients, body and attachment version. Record the approver, decision time and action digest on approval. Changing the recipients, attachment or body creates new intent and requires another preview. Recheck permissions before sending in case the user has left the team. If “purchasing team” is a dynamic list, use the same membership snapshot for display and send. If the product uses a live list, make clear that the buyer is approving that rule.

Waiting can cost a single durable record. One possible state sequence is running → waiting_approval → ready → dispatching → completed. Rejection goes to declined. An uncertain send stays in reconciling. Use a conditional update so approval advances only a still-pending action of the same version. Write the decision and pending work in the same transaction, then let a worker claim it. Even if the approval service restarts just after responding, the work remains. Closing the browser or dropping an SSE connection should not cancel the task on the buyer’s behalf.

The capacity difference is tangible. Suppose 12 tasks arrive per minute at a steady rate. Each occupies an execution slot for ten seconds and waits ten minutes for approval. Average occupied slots are 12 × 10 / 60 = 2, while 12 × 10 = 120 tasks await approval. Having each waiting task hold its slot would require about 120 extra slots. These are long-run averages. A burst of approvals after the weekly meeting needs separate capacity planning. Once waiting is persisted, model calls, sandboxes and the mail service can each have their own concurrency limit.

The hardest milliseconds to recover: email accepted, receipt lost

The old worker sent a request to the mail service. Its replacement sees only local dispatching state. The request might never have arrived, or the service might have accepted it and lost the response in transit. Both outcomes leave identical local records. Even a perfect local transaction cannot distinguish them. To proceed safely, obtain another piece of evidence from outside: look up the receipt by stable operation ID, or retry with that ID under an atomic deduplication contract. AWS on caller-provided idempotency identifiers and retry semantics

You can create this window yourself. Save the code below as receipt.py in an empty directory. Run python receipt.py crash followed by python receipt.py. A SQLite file stands in for a mail service that guarantees idempotency. receipt.txt represents the caller’s receipt. The first process exits after the service accepts the operation. The second should print Same operation, accepted 1 time(s), receipt 1. This experiment fixes the action and tenant. A production interface should also reject reuse of a key with different parameters and define how long deduplication records remain valid.

import sqlite3
import sys
from pathlib import Path

operation = "tenant-7/run-42/send-v3"
with sqlite3.connect("mail.sqlite") as mail:
    mail.execute("CREATE TABLE IF NOT EXISTS sent (op TEXT UNIQUE)")
    mail.execute("INSERT OR IGNORE INTO sent VALUES (?)", (operation,))
    receipt, = mail.execute(
        "SELECT rowid FROM sent WHERE op = ?", (operation,)
    ).fetchone()
    count, = mail.execute(
        "SELECT count(*) FROM sent WHERE op = ?", (operation,)
    ).fetchone()

# The server has committed, but the caller has not saved its receipt.
if sys.argv[1:] == ["crash"]:
    raise SystemExit("Simulated process exit before recording the receipt")
Path("receipt.txt").write_text(str(receipt), encoding="utf-8")
print(f"Same operation, accepted {count} time(s), receipt {receipt}")

If the real mail service supports neither idempotency keys nor a reliable acceptance lookup, I would show “Send outcome awaiting reconciliation,” along with the operation ID and a way for a person to verify it. Blind retries after timeouts make a once-only promise impossible. Cancellation now can stop later steps only. An already accepted action remains a fact in the record. Even with an acceptance receipt, the accurate UI wording is “Accepted by the mail service.” Delivery to the inbox requires a different receipt.

Multiple workers add another race. When a lease expires, a new worker can claim the task, but the old one may have merely paused and may wake up later. I would assign a monotonically increasing execution token on each claim. Local state updates must match the current token, preventing the stale worker from overwriting newer state. The external send still needs its stable operation ID because the mail service cannot see that local token. Execution authority controls who may write local state. The external idempotency contract controls how often an email can be accepted. For the persistence details, see How should an agent store its transcript?

Where three existing frameworks draw the line

If I were implementing this tomorrow, I would examine these three interfaces before deciding what to build myself. They give us control at different points: before tool execution, between model turns and at a human decision.

Claude Agent SDK. Drive its built-in loop with query(). The model can read files, run tools and adapt its next step to the results. PreToolUse fires before execution. It can inspect complete arguments and deny a call, sending that decision back to the loop. For the quote task, I would let the SDK prepare the materials in a restricted workspace and expose only a “submit send request” tool for delivery. The business service then owns approval and actual sending, keeping the preview version, permissions and receipt in the same record system. Claude Agent SDK loop and tool hooks

OpenAI Agents SDK. Python’s Runner.run() drives the model, processes tool calls and returns on final output. A handoff can continue with another agent. If a tax specialist takes over mid-comparison, the platform must still specify who can read the original PDFs, who may submit a send request and how much budget remains. A specialist is most useful when it needs different materials or permissions. Multiplying a unit price requires just a deterministic function. Another model turn adds latency and another opportunity to lose the unit. OpenAI Agents SDK runner lifecycle

LangGraph (LangChain ecosystem). In a graph with a persistent checkpointer, an approval node can pause with interrupt(preview). Resume with the same thread_id and Command(resume=decision). One detail determines where code belongs: resumption restarts at the beginning of the interrupted node, so code before interrupt() can execute again. I would put “prepare and publish v3,” “show v3 and await approval,” and “send approved v3” in three nodes. The send node still deduplicates by business operation ID. These nodes fix the boundaries with business consequences. Within the preparation node, the model is still free to decide whether OCR is needed. LangGraph interrupt and resume semantics

In production, how do we know it worked?

I would start by opening a run timeline. The browser subscribes to committed events with increasing sequence numbers. On reconnection it reads forward from its last seen number. Token-by-token text can be transient. Statements such as “Awaiting approval” and “Email accepted” affect user decisions and should come from durable events. Operators can link model calls, tool latency and external receipts by run, step and attempt. Input and output tokens, retry counts and artifact IDs are usually enough to trace costs. Raw quotes and full recipient lists belong only in business records with appropriate access controls.

This task took over forty minutes end to end. An end-to-end P95 alone gives an engineer little guidance on what to improve. I would also measure submission to first usable preview, time awaiting approval, and approval to external acceptance. Evaluate quality with verifiable outcomes: fix three test quotes and assert that B is 107.96, C is marked pending, the attachment digest matches the preview, and zero emails were sent before approval. Improving time to first token settles none of these questions.

Starting from scratch, I would first ship one service, one database, one object store and one restricted executor. Make “generate a preview, wait for confirmation, kill the worker, resume elsewhere” pass end to end. Split OCR and model calls into separate pools when measurements show them competing for slots. Add tenant quotas and fair scheduling when one tenant’s batch slows others down. Even with a single model, this gives the product one of the most valuable properties of a runtime: forty minutes and one process restart later, when the buyer asks “Did you send the version I reviewed?”, the system can still produce the evidence.
