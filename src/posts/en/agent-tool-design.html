If Bash already reads files, writes files and runs programs, why give an agent separate Read, Edit and Write tools? The interesting question is how these apparently overlapping tools reduce what the model has to guess.

Scope of this study · 2026-11-13

For Pi and OpenCode I read the source at the commits listed below. “Analysis” explains design trade-offs. “Implementation sketch” describes my own proposal. I did not benchmark the three products against one another. The files, logs and runtime states in the figures are teaching examples.

1. One task, four contracts

Suppose the task is to change the retry count from 3 to 5, then verify it. Read answers “what is there now?” Edit says “change this occurrence.” Write specifies the complete desired file. Bash invokes programs in the real environment. Each defines a different action boundary. A task need not execute all four in sequence.

01 / Observe

Read

Read the relevant part of the configuration file.

path + offset + limitThe result is one observation of the file.
02 / Local change

Edit

Find the old code and replace it with new code.

old text → new textIf the old text no longer matches, reassess.
03 / Complete contents

Write

Create a configuration or rewrite a whole file.

path + full contentAnything omitted can be lost.
04 / Run and verify

Bash / Shell

Run tests, compilers and existing CLIs.

command + execution contextA successful launch tells you only that it started.

Analysis. Dedicated tools turn frequent operations into calls that are easy to generate, validate and explain. A shell lets the model compose existing software without a new tool for every command. The right boundary depends on the workload, model and environment. Counting APIs tells us little on its own.

Across products. Pi uses path rather than file_path. Its current Read schema lists only path / offset / limit. In OpenCode V2, path also accepts directories, and offset / limit apply to directory entries. Identical field names can accept different objects.[4][8]

Analysis. old_string both locates the change and checks its precondition. replace_all expands a single-target operation to the whole set of matches. It changes scope, not matching quality. An empty new_string can delete the matched passage. Matching and authorization requirements still apply.

Across products. Pi's current primary schema is {path, edits: [{oldText, newText}]}. This is more than a change in capitalization. Multiple edits to one file are matched against the same original contents. OpenCode V2 uses path / oldString / newString / replaceAll. Non-overlapping ranges, unique matching and formatting tolerance are runtime rules. Field types alone do not tell you how these work.[6][9]

How to read a parameter list. Identify the target, establish the scope, check defaults and units, then determine whether a return means “finished” or “still in progress.” The following sections explain why these design choices matter.

2. Read returns an observation of a file

2.1 Line numbers, ranges and what remains guide the next step

Documented behavior. Claude Code's Read supports line numbering and range reads. It can also present images and other content in a form the model can perceive. Large-file handling distinguishes full contents from partial views. Exact limits vary by model and version.[1]

Pi's implementation is particularly clear. Read takes a one-based offset and a line count, limit. It caps text by both line and byte count. In this revision the default is 2,000 lines or 50 KiB, whichever comes first. A truncated result gives the next position to read.[4][5]

Analysis. A 2,000-line limit alone tells the model too little. It needs to distinguish a complete file, a requested range and a view cut off by the output budget. Otherwise absence from this view can be mistaken for absence from the file. Line limits bound ordinary long files. Byte limits catch minified single-line JSON and huge strings. Neither counts tokens exactly.

2.2 Read adapts an execution environment for the model

Raw binary is a poor representation of an image. A directory needs different handling from a text file, and a missing path deserves more than an opaque exception. OpenCode V2 Read handles files and directories on the model side. Its description warns that display line numbers are not part of the file and must not be copied into Edit. For some invalid paths it suggests alternatives. After a successful read it can discover relevant AGENTS.md. [8]

Analysis. Read produces content, location and an account of completeness. If reading also discovers project instructions, a runtime offering shell reads must decide whether to preserve this behavior. Two tools can return the same text yet leave the model with different instructions. Equivalent stdout alone cannot establish interchangeability.

3. Edit makes a write conditional

3.1 Why not ask the model to change line 42?

Line numbers help people find things, but inserting a few lines earlier moves the target. Old text establishes both the location and a precondition: change the passage that still looks like this. A local edit also saves the model from regenerating a large amount of unchanged code.

Documented behavior. Claude Code Edit uses old_string and new_string for exact replacement. If there are several matches, supply more context or explicitly use replace_all. Read-before-edit requirements in the current documentation vary by model and version. A prior Read call is not universally mandatory.[1]

Analysis. Matching the old text puts a condition on a local change. It is not a version lock on the whole file. Someone else can change code outside the matched passage and Edit can still succeed. Matching catches some stale assumptions without proving that the file's semantics are unchanged. It does not implement cross-process compare-and-swap.

3.2 Tolerate formatting differences, reject ambiguous targets

Documented behavior. Pi describes Edit as exact text replacement. Its helpers first try an exact match, then apply limited normalization for trailing whitespace, certain Unicode quotation marks and space characters. The current version can submit multiple edits for one file. Each target is matched against the same original contents, and overlapping ranges are rejected.[6]

OpenCode V2 also has constrained fallbacks for line endings, typographic quotes and some whitespace differences. Ambiguous matches still require explicit handling. If the old contents are absent, it may report that the new contents already exist or suggest similar lines nearby. These hints expose file data, so they require read permission.[9]

Analysis. Dropping a typographic detail and losing track of the intended target are different failures. The first admits understandable normalization rules. The second calls for rejection. An editor should not guess more aggressively when evidence is weak. A fallback should identify its matching rule so reviewers know whether the bytes actually matched.

3.3 The tool protocol and the review interface serve different readers

A model can submit old/new text while the runtime shows a diff to a human reviewer. An early Anthropic engineering article explains that unified diffs may require a model to count lines before it finishes generating the edit, whereas JSON imposes escaping overhead. Formats that ordinary programs can convert between may place different demands on a model. The article also describes using absolute paths to reduce confusion about relative directories.[3]

Analysis. Let the model express intent in a protocol it handles well. Let the tool match text and calculate a diff, and give reviewers a format suited to review. Old/new text, patches and whole files each suit different situations. Evaluate them against the density of changes, model training and multi-file tasks. Tool arguments are an interface for a model. They need not mirror a human editor's gestures.

4. Write has fewer parameters and takes responsibility for more content

Write typically takes a path and complete contents, then creates or overwrites the file. Pi also creates missing parent directories. OpenCode V2 explicitly recommends Edit for local changes.[7][10]

Analysis. Write fits new files, short complete configurations and artifacts intended to be regenerated. Using it for a one-line change in a long file requires the model to reproduce every unchanged line correctly. Wanting to change just one line does not constrain the tool. Both generation cost and the surface for accidental omission grow.

NeedNatural expressionWhat to check
Create a configuration fileWrite with complete contentsDoes the target exist? Is overwriting authorized?

A small interface can authorize a large change. Write can replace every byte, whereas Edit authorizes a local intent. Atomicity and durability of the filesystem writes are separate contracts underneath both tools.

5. Bash connects a single tool to an ecosystem of software

5.1 Why keep a general-purpose channel?

Compilers, test runners, package managers, Git and data-processing tools already have mature command-line interfaces. Defining a tool for every subcommand produces a growing catalogue with overlapping parameters. A shell connects existing programs with familiar composition rules, making new capabilities easy to add.

Analysis. The price is that a command can include redirections, pipelines, child processes and network access. Its name alone reveals little about its effects. An Edit call exposes the intended change directly. The same change inside a script gives the runtime more behavior to analyze and constrain. Tool descriptions guide the model. Systems outside the model must enforce permissions and isolation.[2]

5.2 Why keep a file's beginning and a command log's end?

Documented behavior. Pi's text Read retains the head when truncating. Bash retains the tail of its text output. It saves large outputs to temporary files and returns a path for later reads. Bash also distinguishes nonzero exit, cancellation and timeout. The source examined here produces separate results or errors for those paths.[4][5][11]

Analysis. The beginning of a file often contains structure, imports and definitions. The end of a log often contains final status. Either heuristic can fail, and the relevant error may be in the middle. Keeping the tail and a searchable full log makes the immediate observation smaller while preserving a way back to the evidence.

5.3 Execution also needs time, state and identity

Documented behavior. In the OpenCode V2 snapshot, the general-purpose execution tool is called shell. Its parameters distinguish workdir, timeout and background execution, and its results distinguish running and completed. Background jobs have identifiers and notify the session on completion. The source documentation discourages repeatedly polling a job to await completion.[12]

Analysis. A Bash tool does not imply a permanently open terminal. Files, working directories, environment variables and processes each have their own lifetimes. Products differ. Without an explicit contract, do not assume a previous command's export, background job or directory change survives into the next call.

A timeout may arrive after an effect has taken place. A cancellation response may arrive while child processes are still running. A reliable runtime reports what it actually knows. If a publish command loses its connection, retrying blindly can publish twice. Check the external state before replaying the call.

6. Design choices that emerge between tools

6.1 Errors are an interface for the next action

“Failed” gives the model little to act on. “Two matches: add surrounding text,” “showing through line 120: continue at 121,” and “process still running: do not start it again” each reduce uncertainty. Errors can teach a model how to repair its call. Anthropic's tool-design article also emphasizes meaningful responses, bounded output and refining descriptions through evaluations on real tasks.[13]

Analysis. A useful error identifies the unmet condition, states whether effects have occurred, and suggests how to verify the outcome. This matters especially for writes and commands. A model receiving an error does not imply an unchanged world.

6.2 Parameter descriptions communicate constraints before execution

Pi's descriptions specify that every edit in a batch matches the original file. OpenCode Edit warns against copying line numbers. Both address concrete mistakes before the model generates its arguments.[6][9]

Analysis. A usable tool explains when to use it and when to choose another. Write must explain overwriting, Edit must describe ambiguous targets, and Read must identify the returned range. JSON Schema restricts types. It cannot ensure that the model chose the right file or understood an overwrite.

6.3 Share state across tools and specify what it guarantees

Documented behavior. Pi routes Edit and Write through the same file-mutation queue. Operations on one file are serialized. Different files can proceed concurrently. Cancellation logic waits for the file operation to finish before checking the signal, avoiding an early release. OpenCode's mutation layer likewise notes that its in-process lock coordinates cooperating calls only. External writers can race.[14][15]

Analysis. A queue cannot lock other processes. Serialization cannot establish disk durability, and a successful file write cannot establish a multi-file transaction. Shared state reduces some mistakes. Concurrency control must also account for IDEs, formatters, shells and other agents. Locking only Edit leaves a Bash script free to change the same file.

6.4 Tool lists evolve faster than design principles

The Claude Code documentation now describes platform-specific defaults for search. On macOS, Linux and WSL some searches run through Bash. Glob/Grep return under particular configurations.[1] An agent should not be defined by one version's list of tools.

Analysis. As models become more capable shell users, some specialized tools may offer less benefit. Permissions, observability or multimodal input can still justify a dedicated interface. Evaluate task quality, recovery cost and control over effects. The number of tools is a poor substitute for those measures.

7. Contracts I would guarantee first

Implementation sketch. For a deployable agent workspace, I would separately record the model's intent, runtime validation and observed effects. This proposal does not reproduce the implementations above.

LayerRecord or checkProblem addressed
InputTool version, explicit workspace and path semantics, call IDPrevent the same string from pointing to different workspaces
ObservationRead range, truncation, content version or hashDistinguish unseen, absent and changed
WriteOld-content condition, expected version, authorization scope, actual diffReject stale assumptions and enable review
ExecutionTask ID, state, exit code, cancellation outcome and log referenceDistinguish a successful launch from completed work
RecoveryWhether effects committed, whether the result was delivered, whether retry is safeAvoid blindly repeating a write or command after a timeout

For example, a local edit could include an expected_version field that a single write service verifies and commits. This only provides concurrency control if the version check and the write share a constrained commit mechanism. Computing a hash and writing later still leaves a race. A temporary file followed by rename can address some visibility issues. Symlinks, permissions, filesystem boundaries and crash durability each need separate consideration.

The result could have two layers: concise text sufficient for the model's next decision and structured fields for the runtime and UI, for example status, changed_paths, truncated, artifact_ref. Retaining structure does not require feeding every field into the model's next turn. Define expiry and access permissions for large artifacts as well.

How to test whether the design helps

Using one model and one task set, I would compare strict Edit, constrained formatting tolerance, patches and whole-file rewrites. Before merging tools, I would test at least the following cases.

  • Target selection. Does it modify the wrong location when code repeats, old text goes stale or lines are inserted above the target?
  • Format and scope. Can CRLF, Unicode quotation marks, huge single-line JSON or partial reads lead to incorrect assumptions about completeness?
  • Concurrency and interruption. Can the tool explain what actually happened after an external write, overlapping batch edits or cancellation midway through a write?
  • Execution recovery. With oversized logs, exit code 1, an unfinished background job or a lost connection before the result arrives, does it report false success or execute twice?

Besides success rate, I would measure unintended edits, extra retries, input volume, wait time and recovery after failure. I did not run these controlled experiments and cannot report a percentage improvement for any protocol.

My conclusion. Tool design gives the model a world it can observe, act on and correct.Read specifies the scope of an observation. Edit makes a change conditional. Write makes responsibility for a whole-file overwrite explicit. Bash connects open-ended capabilities to a stateful environment. The model proposes the next step and the runtime enforces the contract. Reliable work on real files and processes depends on both.
