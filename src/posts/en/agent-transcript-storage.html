A user asks an agent to investigate last night’s failed orders. A tool returns 2 MB of records. The agent identifies three affected batches and opens a ticket. Ten minutes later, the user asks, “Did the second batch fail for the same reason as the first?” Sending the entire dataset to the model again means paying to read it on every follow-up. Keeping only “three batches affected” leaves too little evidence to answer. And if the process crashes just after the ticket is created, how does the next machine know whether to keep investigating or open another ticket?

These three questions shape how I store a transcript: the interactions that have already taken place between the user, model, tools and agent. For a multi-user service that must recover on another machine, I would start by appending logical items, keeping small payloads inline and leaving retrievable references to large results. Choosing which items the model sees on its next turn is a separate decision. Let’s follow that ticket through the system.

What belongs in a row? Start with a tool call

Suppose the order query has call ID q7 and ticket creation has ID t8. The platform could record the run in six items. The sequence number belongs to the session, while the call ID belongs to a single tool interaction. Each serves a different purpose.

Seq    Kind                Content
41     user.message        Find last night's failed orders and open one ticket for the affected batches
42     tool.call     q7    query_orders, time range and query criteria
43     tool.result   q7    3 affected batches, detail object A, version and checksum
44     tool.call     t8    create_ticket, based on #43, stable idempotency key K
45     tool.result   t8    Success, external ticket O-318
46     assistant.message   The three batches are listed in ticket O-318

Fetching just items 44 through 46 lets the UI show which ticket was opened. If two queries run in parallel and their results arrive in reverse order, their call IDs still match them correctly. A partial word or an incomplete JSON argument can stream to the frontend. I would usually commit a history item once its message or call is complete. If reconnecting clients need to replay the stream, give the deltas a short-lived buffer and cursor. Its retention period can be much shorter than the session’s.

A single JSON field for the whole conversation is convenient for a prototype with one writer, bounded length and whole-conversation reads. Its cost depends on how you write it. If the client uploads the entire array on each append, 100 equally sized messages transfer the equivalent of 5,050 messages. Appending individual items transfers 100. This example measures client traffic. Actual disk writes depend on the database implementation. A local JSONL file is another practical starting point: it uses the same JSON encoding and appends one record at the end. You can choose the encoding and the unit of update independently.

Where do three SDKs look when the user says “continue”?

Claude Agent SDK: return the native session to the runtime

When calling query() in TypeScript, save the returned session_id and pass it to options.resume on the next call. By default the transcript lives in a JSONL file under ~/.claude/projects/ on the local machine. Routing the next request to a different machine requires the data that ID points to as well.

The SDK’s SessionStore adapter supports append(key, entries) and load(key). Its backend contract is specific: loaded entries must be deeply equal to the values written and retain their order. Changing JSON serialization is fine. Substituting a one-sentence summary for a tool result breaks that contract. The key includes a project identifier and an optional subpath, which can identify a subagent’s records. I would persist native entries in batches and build a lightweight index for the UI. If the storage layer separates out the 2 MB payload, load must reconstruct it losslessly. If the model should receive only a summary, design the tool’s original return value that way. Session resumption · External storage contract and examples

LangChain / LangGraph: recover whose turn it is

LangChain’s create_agent(..., checkpointer=saver) can use LangGraph persistence. The same thread_id retrieves the thread’s graph state. messages is one field, and the application can extend the state. Development can use InMemorySaver. The official database example uses PostgresSaver. A separate Store holds information such as user preferences shared across threads. LangChain short-term memory · LangGraph persistence

For our ticket, a checkpoint can carry the reference to query artifact A, the pending request to open a ticket, and the current graph state. If the approver returns tomorrow, the runtime needs to know which step to resume. Reconstructing that reliably from the six lines in the chat window is hard. Conversely, storing all the raw records in frequently saved state means the checkpoint reader and serializer must handle a large field. I would put only what the node needs for its next step into state, then measure incremental writes for the actual saver.

OpenAI Agents SDK: persist history and choose what the model reads

In the Python SDK, SQLiteSession("orders-17", "sessions.db") preserves history across multiple calls to Runner.run for the same conversation. Specify a file path: the default in-memory database disappears when the process ends. The Session interface has methods such as get_items and add_items. Before the model call, RunConfig.session_input_callback can combine retrieved history with the current input. Filtering out some older items does not cause the remaining old items to be appended again as new history. Sessions and input merging · SQLiteSession persistence parameters

For example, these calls can run in two processes. Both must have the same agent configured and access to the same database file. The second call retrieves the history using the same session ID.

from agents import Runner, SQLiteSession

# Turn one: the query tool returns a summary, batch IDs and a reference to the records.
session = SQLiteSession("orders-17", "orders.db")
await Runner.run(agent, "Find last night's failed orders", session=session)

# On the next turn, reopen the session. The client need not resend the conversation.
resumed = SQLiteSession("orders-17", "orders.db")
answer = await Runner.run(agent, "Did the second batch fail for the same reason as the first?", session=resumed)

Two costs are involved. Keeping ten items in the callback saves model tokens, but if the SDK has already fetched 10,000 items, the database still served all 10,000. SessionSettings(limit=N) also limits retrieval. However, N counts individual items: the boundary might fall between a tool call and its result. The platform needs to fetch the missing partner or remove the entire completed interaction from the model input.

Where PostgreSQL ends and object storage begins

Back on the enterprise platform, here is the logical table I would implement first. The platform generates a stable event ID and reuses it when retrying the same write. Tool call IDs can be interpreted within a run. Auditing and troubleshooting also require the tenant, session and run that own the event.

transcript_item
  tenant_id, session_id, seq         committed order within the session
  event_id, run_id, kind, call_id    deduplication, ownership and tool pairing
  payload_jsonb                     message body, or a small preview and artifact metadata
  artifact_key, digest, byte_size   immutable version, checksum and size of a large result
  schema_version, created_at        decoding and retention policies

  PRIMARY KEY (tenant_id, session_id, seq)
  UNIQUE      (tenant_id, session_id, event_id)

In one append transaction, lock the session head, check whether the event has already been written, allocate consecutive sequence numbers to the batch, insert its items, update the head and commit. The frontend can then paginate using seq > cursor without missing a record whose number was allocated earlier but committed later. Other sessions write independently. If a large parallel task stalls on one lock, measure per-session lock wait before splitting work across subagents. The platform-wide concurrent user count tells you little about contention on that lock.

First write detail object A as an immutable object under the current tenant and confirm that the upload succeeded. Then commit item 43 and its reference in the database transaction. A successful upload followed by a failed transaction leaves an orphan, which a sweeper can reclaim after a grace period. Reversing the order can expose a “successful” item whose details do not exist. Recheck the current user’s authorization on artifact access. Store a stable object identifier in the event and generate temporary download URLs on read.

A smaller database: which bytes are still there?

Suppose there are 10,000 runs per day, each with 20 records averaging 1 KB and one 2 MB tool result. Use decimal units and a 30-day month. The calculation covers uncompressed logical content only. Measure indexes, WAL, replicas, backups, object request charges and network costs separately.

Small records   10,000 × 20 × 1 KB × 30  =   6 GB/month
Large results   10,000 ×  1 × 2 MB × 30  = 600 GB/month
Item count      10,000 × 20 × 30         =   6 million items/month

With large results inline, the database takes about 606 GB per month. Externalizing them puts about 6 GB plus references in the database and 600 GB in object storage. Roughly the same total bytes remain. The gain is that opening a recent conversation requires only a lightweight index and the current page. Backups of the hot database stop carrying large results over and over. A product that promises to retain the details forever still pays for another 600 GB accumulating each month.

There are two independent decisions here. Externalizing a large result happens in a live session and depends on item size and access patterns. Archiving the history happens once a session goes cold and depends on revisit frequency, retention requirements and acceptable restore latency. Closed ranges of sequence numbers can be compressed into JSONL segments. Record their first and last sequence numbers, object versions and checksums in the database. Verify the archive, switch the read index, then reclaim the hot copies. If the user returns unexpectedly, append new items at the tail. Fetch an archived segment only when an older page is requested.

Choose the externalization threshold using real traffic. For one week’s sample, measure tool result sizes at P50, P95 and P99, and the proportion reread in full within seven days. Simulate cutoffs of 32 KB, 128 KB and 512 KB. How much less does the hot database write? How many extra object GETs occur each day? What happens to P95 time to first response after resumption? An occasional 10 MB report and a 40 KB configuration read on every turn may warrant different policies. Tenant deletion also needs an expiry path for archives, summaries, caches and backups still in retention.

“What about the second batch?” Which items do we actually read?

Opening the chat: read the most recent page by cursor and show the ticket receipt and query summary. Fetch A only when the user expands the details. Following up on the cause: fetch a summary marked with the last sequence number it covers, the complete interactions after it and the current question. The summary should at least preserve the three batch IDs, the original query time range and the artifact reference. If the difference between batches one and two lies in their error codes, retrieve the relevant rows from A and fit them into the context budget. If access is denied or A has expired, tell the user the evidence is unavailable. Rerunning the query produces new data and needs a new query timestamp.

Investigating why the ticket was opened: follow item 44 back to the original evidence in item 43 and the tool version in use. If the product also needs to answer “What exactly did the model see?”, record the selected item ranges, summary version, system prompt version, tool definition version and final request digest for that model call. A hash can verify content but cannot reconstruct it. For verbatim inspection, retain the actual request or immutable inputs sufficient to reconstruct it, subject to authorization and retention policies. Even with identical input, a new model request need not produce the same answer.

I would give each summary a through_seq and a policy version. When trying a shorter summary in production, rebuild it from authorized history and compare answers to follow-ups such as “How did the first and second batches differ?” That makes compression testable. Overwriting the only original with the new summary forfeits the chance to check what it omitted. For more on fitting messages into a finite model window, see Managing an agent’s context.

The most revealing acceptance test: cut the power after item 44

Suppose the ticket system created O-318, but the runtime exited before writing item 45. The transcript proves a creation request was initiated, but it cannot tell us whether the remote operation succeeded. The new worker should query or retry with the previously persisted idempotency key K. A downstream service that supports idempotency returns the same ticket, and the worker can record the missing result. If the API supports neither ticket lookup nor an idempotency key, record “outcome awaiting reconciliation” and have a person check. A database uniqueness constraint can prevent two local records while the remote system still creates two tickets.

Starting from scratch, I would first ship three acceptance tests: the session paginates in order, a different worker can answer a follow-up and retrieve the specified batch, and killing the process before it records the ticket receipt still leaves exactly one external ticket after recovery. Once those pass, tune externalization and archive thresholds using tool result sizes and cold-session revisit rates. A good storage design shows up in an ordinary moment. The user returns tomorrow and asks, “What about the second batch?” The system can find yesterday’s evidence and remembers the ticket it already opened.
