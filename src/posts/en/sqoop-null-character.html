Most tables exported successfully with the same command. Only a handful kept producing type conversion errors. The clue turned out to be a character that was normally invisible.

The same configuration, but values landed in the wrong fields

We were running Sqoop 1.4.7 and Hive 2.1.1. When exporting from Hive to MySQL, values in a few tables shifted into the wrong columns and triggered type conversion errors. Other tables exported with the same settings, so I turned to the input data.

Narrowing the failure down to a single record

It took two days to isolate the problem row. I used a manual binary search. For a set of 10,000 records, for example, I would try exporting 5,000, then keep narrowing the failing subset until I had a record that reproduced the error.

I retrieved the Hive data file from HDFS. It looked normal in cat, but vim displayed a ^@ within the data. Further comparison showed that rows containing this character failed, while rows without it exported successfully.

The ^@ represents NUL, Unicode U+0000. An empty string has zero characters. This value actually contains a character, even though it is usually invisible.

Why did the parser treat NUL as special?

I had already specified a field separator with --fields-terminated-by. Why would NUL affect parsing instead of passing through as ordinary text?

I read the Sqoop 1.4.7 source to find out. Its record parser uses a state machine that distinguishes four kinds of characters.

OptionRole in the parser
--enclosed-byField enclosure character
--escaped-byEscape character
--fields-terminated-byField terminator
--lines-terminated-byRecord terminator

The clue was in the comment on the method that returns the enclosure character. When no enclosure was specified, it used \000 to mean “none.” The NUL character in the input can be written in Java as \u0000. The two spellings have exactly the same value.

char a = '\u0000';
char b = '\000';
System.out.println(a == b); // true

I read the failing file, inspected the character values in a debugger, and followed the state machine’s checks for the enclosure and escape characters. That traced the shifted fields to a collision between an actual input character and the parser’s defaults.

The fix we used

We set both --enclosed-by and --escaped-by explicitly to avoid the defaults that collided with the input. The choice of values depends on the input format and needs to be verified against the data. An arbitrary replacement character can introduce another collision.

What I took away from the investigation

The most useful part was reducing the scope at each step. Compare a successful row with a failing one, use the difference between two displays to identify the invisible character, and then follow the parser’s state transitions. The error surfaced during type conversion, but the fields had already shifted during parsing.
