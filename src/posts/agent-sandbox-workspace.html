模型可以写出一段分析代码，但代码要在哪里运行？生成的文件放在哪里？下一步还能找到吗？当 Agent 从回答问题走向实际完成任务，它需要的不只是更长的上下文，还需要一个能计算、能保存结果、能验证假设的工作空间。

阅读范围 · 2026-11-14

一、模型能提出做法，还需要一个地方把做法执行出来

先想一个普通任务：用户上传一份订单 CSV，希望统计金额、生成报表，再检查结果。模型可以理解字段、决定统计口径、写出 Python，但“生成了一段代码”和“已经用真实数据算出了结果”之间，隔着一次真正的执行。

模型推理本身当然也消耗计算资源。这里说的计算空间，特指它通过工具使用的外部执行环境：CPU 运行生成的程序，内存承载处理中的数据，文件系统保存输入和产物，操作系统管理进程。模型通常通过工具请求使用它，而不是自己变成一个 Python 进程。

这像把一台可操作的电脑交给 Agent。它不仅能说“可以这样处理”，还可以把脚本放进去、运行它、看到报错、修改后重跑，最后交付一个真实存在的文件。沙盒里的产物、日志和退出状态，会成为下一轮判断的证据。

1.1 为什么不把所有数据都交给模型算

对于结构明确的遍历、排序、聚合、格式转换，让程序处理通常更合适：模型描述规则，代码逐条应用规则。没有必要为了统计一个大文件，让每一行都先穿过模型上下文。

Anthropic 的代码执行文章也展示了这种做法：数据在执行环境中筛选、转换，再把必要结果返回给模型；文件可用于保存跨操作的中间状态。[1] 这说明上下文不是工作空间的全部。模型可以只看到汇总、样本和失败信息，完整输入与产物另有承载位置。

但这不自动保证结果正确。金额按字符串拼接还是数值相加、退款是否扣除、单位是什么，仍取决于任务定义和代码。需要先明确口径，再运行、检查，不能把“程序算的”当作正确性的证明。

1.2 为什么不只提供一百个固定工具

固定工具非常适合边界清楚的业务动作，例如查询订单、创建日程。计算空间则允许 Agent 临时组合步骤：解析一种新格式、写一个过滤脚本、用现有库转换文档，再把结果交给另一个工具。它扩展的是可组合能力，不是让每一种新需求都等一个新接口。

并非所有 Agent 都需要独立沙盒。如果任务只是在已授权的业务 API 之间选择和编排，工具服务器可能已经承担全部执行。遇到动态代码、大文件、多步产物或持续进程时，独立工作空间的价值才明显。MCP 等协议负责工具连接与调用约定，本身并不等于一台执行机器。

二、跟着一个任务走：从请求到可交付文件

这个例子里，模型不需要亲自逐行心算，但需要理解数据、提出合适程序，并根据实际执行结果调整。代码出错时，错误信息成为新的观察；程序成功结束后，还要检查文件存在、行数符合预期、统计口径一致。

# 假设当前目录中已有 orders.csv，金额单位为整数元
import csv
from pathlib import Path

with open("orders.csv", newline="", encoding="utf-8") as f:
    rows = list(csv.DictReader(f))

total = sum(int(row["amount"]) for row in rows)
Path("summary.csv").write_text(
    f"order_count,total_amount\n{len(rows)},{total}\n",
    encoding="utf-8",
)
print({"order_count": len(rows), "total_amount": total})

在这个玩具数据集里，结果应为 3 笔、500 元。真实任务如果有小数金额、缺失值、重复订单或币种混用，就需要改用相应的数据规则；示例不具备这些生产校验。生成文件也只是工作区内的结果，还需要通过下载或产物接口交付给用户。

三、拆开这台“电脑”：它究竟提供了什么

工作空间不只是一个目录。目录能保存文件，却不能单独解释进程在哪里运行、依赖来自哪里、可以连接哪些网络、资源由谁限制。可以从下面五个部分理解。

3.1 文件系统：把中间状态从对话里拿出来

输入 CSV、分析脚本、图表、测试日志都可以有自己的路径。下一次工具调用读取这些文件，就能继续处理，而不必把全部内容重新嵌进提示词。文件系统也使不同程序能交换数据：一个程序输出 CSV，另一个程序把它画成图。

但“路径相同”不等于“内容版本相同”。会话摘要写着文件存在，文件也可能已经被清理、覆盖或移动。恢复后要检查真实状态，而不是相信聊天里上一次的描述。

3.2 进程：让动作真正发生，并有一个可追踪的身份

运行 Python、启动浏览器、执行编译、等待测试，都涉及进程。进程有 PID、退出码、标准输出、标准错误、子进程与运行时间。一个长命令可能还没结束，模型却已开始下一轮推理，所以运行时需要用任务 ID 追踪它。

模型通常不需要和执行进程在同一台机器。运行时可以通过受控连接派发命令，收集输出并回传。浏览器、GPU 或大型计算也可以由单独的执行服务承担；不必把所有能力都装在一个沙盒里。

3.3 依赖与资源：让“可以运行”变成可预期

脚本需要 Python 和库，网页需要浏览器，视频需要编解码工具。基础镜像提供可复用的软件环境，项目文件和必要配置再组成具体任务的工作区。安装过程还需要考虑版本、下载来源和缓存，不能假设依赖永远能从网络装成功。

CPU、内存、磁盘容量、进程数与执行时长则决定它能做多大的工作。一个无限循环不能无限占用整台宿主机；同样，一段程序能启动，不代表给定内存足够把整个数据集读进来。

四、为什么还需要“沙盒”这道边界

到这里，我们已经解释了工作空间为什么有用。还需要再问：动态生成的程序如果路径写错、消耗失控，或读取了不可信内容，它能够影响到哪里？

“专属计算空间”和“安全隔离边界”相关，但不是同义词。一个普通目录加一个 shell 可以作为工作区，却未必具备可靠隔离。沙盒是在提供执行能力的同时，由运行时和操作系统约束可见资源、可执行操作和影响范围。

受约束的执行环境 · 概念示意

Agent 生成的程序读写授权工作目录使用受限计算资源访问允许的外部服务
操作系统 / 执行服务按策略检查边界
其他用户数据宿主机敏感目录未授权网络与凭证
这些保护需要明确配置与验证；框里画了一条线，不代表所有访问天然被阻断。

4.1 几种机制各自解决一个问题

机制主要约束不能据此认定
Namespaces进程、挂载、网络等资源的视图与命名范围进入 namespace 就能任意安全运行所有代码
CgroupsCPU、内存、进程等资源的计量与限制限制内存就限制了文件读取和网络访问
Capabilities / Seccomp / LSM缩小权限、系统调用与访问面一个 syscall 过滤器就是完整沙盒
文件与网络策略挂载范围、读写权限、外连目标与出口文件隔离自动带来网络隔离

Docker 文档分别说明了 namespaces 与资源控制的角色；Linux 文档也明确提醒 seccomp 系统调用过滤本身不是完整沙盒。[2][3] 因而不能只选一个技术名词，就忽略文件挂载、权限和网络策略。

提示词里写“不要访问其他目录”是行为指引；操作系统拒绝访问才是执行边界。即使模型已经批准一个动作，底层仍可以拒绝越权；反过来，沙盒允许发出请求，也不等于业务层授权它修改远程数据。

4.2 容器、gVisor、microVM：执行边界可以放在不同位置

普通 Linux 容器中的进程共享宿主机内核。gVisor 在用户态实现 Linux 风格的应用内核接口，提供 runsc 与容器工具集成。[4] Firecracker 则通过 KVM 运行 microVM，让工作负载使用客体内核。[5]

这张图只比较逻辑层次，不是完整的系统调用路径。选型还要看兼容性、工作负载、启动与维护成本，以及租户之间的信任关系。不能把它画成一个普适的性能排名，也不能假设用了 microVM 就自动有出口控制；Firecracker 文档明确把网络过滤交给宿主侧方案。[5]

还要分清两个常见场景：本地编程助手可能约束现有开发目录里的命令；云端 Agent 则可能获得一套新建的远程工作环境。Claude Code 的 sandboxed Bash 文档讨论的是文件与网络约束，不能据此推断每次调用都新建了一台虚拟机。[6]

五、有状态的计算空间，必须说明“什么会留下来”

对话、文件与进程是三种不同的状态。聊天历史还在，不能证明文件还在；文件还在，也不能证明正在运行的 Python 进程、内存里的变量、浏览器连接还在。

Kubernetes 的 volume 文档区分了跟随 Pod 生命周期的临时卷与超出单个 Pod 生命周期的持久卷。[7] 因此工作区回收策略必须和存储策略一起设计。

一种常见做法是持久保存重要文件，空闲时释放计算资源，下次重建进程并重新挂载。另一种做法是使用支持的 checkpoint/restore 保存执行状态。gVisor 提供相关机制，但恢复还要考虑文件系统一致性、网络连接和环境兼容条件，不能理解为“在任意机器上恢复就一切不变”。[8]

我的分析：暂停、进程快照、文件持久化、对象存储归档、数据备份分别处理不同问题。“退出时上传到对象存储”可以归档，却不能保护上传之前突然宕机的所有写入。需要承诺什么级别的数据不丢，就要明确写入确认、持久化路径、故障范围与恢复目标，不能只加一个退出钩子。

六、一个用户一个，还是一个会话一个

这是产品与资源管理上的选择，不是模型要求的固定结构。沙盒、容器、Pod 和工作目录也不天然一一对应。一个调度单元可以承载多个隔离实例；是否应该这么做，取决于隔离实现与平台设计。

分配方式得到什么要处理什么
每次调用一个临时环境清理简单、适合独立小计算多步状态需要显式带入带出，依赖准备可能重复
每个会话一个工作空间任务状态清晰，不同会话较易分开更多实例、依赖与文件共享方式要设计
每个用户一个工作空间个人文件与依赖可复用并发会话会竞争文件、端口、依赖版本与后台进程

实现推演：可以把长期文件归属与短期执行实例分开：用户拥有可持续的文件空间，任务获得受约束的工作目录或独立执行实例。但“每个会话一个子目录”只解决组织问题，不自动解决跨目录访问；真正隔离仍需运行时和操作系统执行。

七、把工具调用接到这个空间，需要什么

如果自己实现，我会先让模型面对稳定的工具语义，让运行时负责定位真实机器。例如：

{
  "workspace_id": "ws-demo",
  "operation": "exec",
  "command": ["python", "analyze.py"],
  "cwd": "/workspace",
  "timeout_ms": 30000,
  "request_id": "run-demo-1"
}

这是自定义接口示意，不是现有产品的调用格式。身份必须由认证上下文绑定到可访问的 workspace，不能因为客户端传了一个 ID 就信任它。request_id 也只是关联标识；只有服务端建立了去重与副作用记录规则，它才有幂等意义。

执行服务需要回答：环境准备好了吗、命令是否仍在运行、退出码是什么、输出有没有截断、产物在哪里、取消后子进程是否清理。路由还要保证后续操作找到正确工作区；多个执行者同时接手时，需要租约或其他并发控制，避免重复执行。

这也说明沙盒不等于 Agent 本身。目标理解、模型请求、上下文选择与任务编排可以在外部运行时；沙盒负责承载被派发的计算和状态。二者通过明确的接口连接，既能分别扩缩容，也更容易解释故障发生在模型、派发还是执行层。

我会这样检验这个设计：让一个任务完成“读输入、写脚本、运行、修错、交付”全流程；中途停止计算资源，确认承诺保留的文件仍在；模拟超长输出、内存不足、命令超时和并发写入，检查是否返回真实状态。这些验证比仅仅看到一个容器启动更接近“Agent 有了可用的工作空间”。

所以，当我说 Agent 需要一个沙盒，想强调的是：它需要一个可以实际操作的环境，把提出的步骤变成计算、文件和可核验的结果，再由明确的边界约束这些操作。能计算让它做更多事，能保存状态让它把多步任务接起来，能观察结果让它纠错，隔离则让这些能力可以被有边界地交付。
