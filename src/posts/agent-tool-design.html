既然 Bash 已经能读文件、写文件、跑程序，为什么 Agent 还要单独设计 Read、Edit 和 Write？最值得研究的，是这些看似重复的工具，如何减少模型需要猜测的东西。

研究范围 · 2026-11-13

Claude Code 依据当前官方工具参考讨论公开行为；Pi 与 OpenCode 依据文末固定提交阅读源码。文中的“我的分析”解释设计取舍，“实现推演”是我提出的方案，不代表产品内部实现。没有运行三款产品的统一效果评测。图中的文件、日志与运行状态均为教学示例。

一、先看图：同一个任务，四种不同的契约

假设任务是“把重试次数从 3 改为 5，再验证”。Read 回答“现在是什么”，Edit 表达“只改这一处”，Write 表达“这个文件的完整内容应当是什么”，Bash 则让模型调用真实环境里的程序。它们不是必须依次执行的四个步骤，而是不同的动作边界。

01 / 观察

Read

读取配置文件的相关范围。

path + offset + limit输出是观察，不是完整世界。
02 / 局部变更

Edit

找到旧代码，再替换为新代码。

old text → new text旧内容不匹配，就要重新判断。
03 / 完整内容

Write

创建新配置，或重写整个文件。

path + full content没有提供的部分，不会自动保留。
04 / 执行与验证

Bash / Shell

运行测试、编译器与已有 CLI。

command + execution context启动成功，不等于任务完成。

我的分析：专用工具的价值，是把常见操作变成容易生成、容易校验、容易解释的调用；Shell 的价值，是让模型组合已有软件，而不必为每个命令重新造一个工具。边界应由任务分布、模型能力与运行环境决定，不能只按 API 数量判断好坏。

参数图谱：把一次调用拆开看

先把四个工具的参数摊开。下面以 Claude Code 官方 SDK 公开输入类型为主，Pi 与 OpenCode 沿用本文固定源码快照做对照。JSON 示例只展示工具的 input，不是直接发送给模型 API 的完整请求。标注“可选”表示输入字段可省略；不代表省略后不受运行时限制。[16]

① Read 范围② Edit 匹配③ Write 覆盖④ Bash 时间与目录

Read 参数：对象、起点、数量，分别回答一个问题

参数类型 / 是否必填含义与设计原因常见误用
file_pathstring / 必填读哪个文件。路径定位与读取范围分开。把目录、错误的工作区路径当成文件。
offsetnumber / 可选文本从哪一行开始；按 1 开始理解。省略时从开头读。把它当字节偏移，或用数组下标 0。
limitnumber / 可选最多读取多少行；省略仍受输出预算约束。以为 limit=20 表示“读到第 20 行”。
pagesstring / 可选PDF 页码范围，如 "1-5"。与文本行范围混用。
allow_largeboolean / 可选符合版本条件时允许更大文本读取，仍受会话剩余窗口约束。当成无限输出或绕过访问权限的开关。

看一个算式：offset=3, limit=2 表示从第 3 行开始，最多取 2 行，也就是第 3–4 行；预期结束行是 offset + limit − 1。文件末尾或输出上限可能让实际返回更少。allow_large 需要 SDK v0.3.296 / Claude Code v2.1.296 或更新版本。[16]

产品差异：Pi 使用 path，不是 file_path；其当前 Read schema 只列出 path / offset / limit。OpenCode V2 的 path 还支持目录，offset / limit 对目录条目也有意义；不要因为字段同名就假设接受相同对象。[4][8]

Edit 参数：旧文本是条件，新文本是意图

参数类型 / 是否必填含义与设计原因常见误用
file_pathstring / 必填限定在哪一个文件里匹配。以为旧代码会自动在整个项目里搜索。
old_stringstring / 必填当前文件中要找到的旧文本；包含必要上下文。复制了 Read 的显示行号，或只写一个到处出现的词。
new_stringstring / 必填替换后的文本；不是补充说明。以为工具会自动合并省略掉的旧代码。
replace_allboolean / 可选显式选择替换所有匹配；默认不是全部替换。遇到多处匹配就设 true，顺手改了不该改的地方。

我的分析：old_string 同时承担定位和前提校验。replace_all 则把“选中一个目标”变成“处理整个匹配集合”，它改变的是作用范围，并不是让匹配更智能。new_string 为空字符串可表达删除匹配片段；仍要满足匹配与授权条件。

产品差异：Pi 的当前主 schema 是 {path, edits: [{oldText, newText}]}，不是把 Claude Code 参数改个大小写；一个文件的多个 edits 对同一份原始内容匹配。OpenCode V2 则用 path / oldString / newString / replaceAll。批量区间不重叠、唯一匹配与格式容错属于运行时规则，不能只看字段类型就推断出来。[6][9]

Write 参数：两项就够了，也因此没有隐含的保留区

参数类型 / 是否必填含义与设计原因常见误用
file_pathstring / 必填要创建或覆盖的目标路径。没确认目标已存在，就把它当新文件写。
contentstring / 必填写入后的完整内容。不存在追加或局部保留参数。只给改动的一行，期待其他行自动保留。

我的分析：JSON 中的 \n 表示解析后的换行；\\n 则可能写成字面量“反斜杠+n”。不要把 Markdown 代码围栏也当作代码正文传进去。content 是要落盘的文本，不是“告诉工具怎样修改”的自然语言指令。Pi 与 OpenCode V2 的对应名称是 path / content。[7][10]

Bash 参数：命令、时间和返回方式，不是一回事

参数类型 / 是否必填含义与设计原因常见误用
commandstring / 必填真正交给 shell 执行的命令。把说明文字放这里，或忘记转义路径中的空格。
timeoutnumber / 可选Claude Code 中单位为毫秒；前台等待与后台运行有不同的期限规则。照抄 Pi 的秒数，导致时长差 1,000 倍。
descriptionstring / 可选对本次操作的简短用途说明。以为这句话会自动改变命令或授予权限。
run_in_backgroundboolean / 可选请求后台运行，让控制流先返回。将“已在后台启动”当成运行成功。
dangerouslyDisableSandboxboolean / 可选 · 高级请求不经沙盒执行；仍受权限与运行时策略控制。把它当作延长时间或提升成功率的通用参数。

版本边界：后台期限、超时后是否转后台、可用开关均取决于 Claude Code 版本与配置。下面只演示参数单位和执行上下文，不模拟具体进程调度。通常没有必要修改沙盒开关；普通的参数说明也不能代替执行授权。[1][16]

产品 / 快照30 秒工作目录后台字段
Claude Code Bashtimeout: 30000，毫秒该公开 input 类型没有 workdir；由会话语义管理run_in_background
Pi bashtimeout: 30，秒当前会话 / 创建工具时的 cwd，不是 input 字段所读基本 schema 无此字段
OpenCode V2 shelltimeout: 30000，毫秒可传 workdirbackground

Pi 的可选 timeout 省略时没有默认超时；填入时要求有限正数。OpenCode V2 在该快照中 timeout=0 表示禁用超时，前台省略默认 2 分钟，后台默认无超时。同名字段的单位、零值和默认值都要单独核对。这些差异来自本文固定快照，不代表扩展、远程执行后端或未来版本不可能改变规则。[11][12]

读参数的顺序：先确认调用对象，再看作用范围，然后检查默认值与单位，最后弄清楚返回表示“已经完成”还是“仍在进行”。后面的章节继续解释这些参数为什么值得这样设计。

二、Read：它返回的不是文件本身，而是一次观察

2.1 行号、范围和“还有多少”，共同决定下一步

已证实：Claude Code 的 Read 支持行号与范围读取，也能把图片等内容以模型可感知的形式返回。大文件处理会区分完整内容与部分视图；具体限制与模型、版本有关。[1]

更容易看清实现的是 Pi。其 Read 接受从 1 开始的 offset 和行数 limit；文本结果同时受到行数与字节数限制。所读快照中的默认上限为 2,000 行或 50 KiB，先达到哪个就按哪个截断；返回结果会给出继续读取的位置。[4][5]

我的分析：“只给 2,000 行”还不够。模型需要知道这是全文、指定范围，还是被容量上限截断。否则，“当前没看到”就容易被误读成“文件里没有”。行数限制防止普通长文件占满输入，字节限制处理压缩成一行的 JSON、长字符串等情况；两者都不是精确的 token 计量。

2.2 Read 也是运行环境到模型的适配层

图片不能只回传一串二进制；目录不能冒充普通文本；查不到路径也不能只扔一个没有方向的异常。OpenCode V2 的 Read 在模型侧同时处理文件与目录，并明确提醒：显示出来的行号不是文件内容的一部分，不能复制进 Edit 参数。它还会在部分路径错误场景给出候选路径，在成功读取后发现相关的 AGENTS.md。[8]

我的分析：Read 的真正产物，是“内容 + 定位信息 + 完整性说明”。如果读取还会触发项目指令发现，那么改用 Shell 读取时，运行时也必须考虑是否保持这一语义；否则同样读到一段文本，后续行为可能受不同指令影响。工具替代不能只比较 stdout 是否一样。

三、Edit：把一次写入，变成带前提的变更

3.1 为什么不直接让模型指定“改第 42 行”

行号是方便人定位的坐标，但文件前面多插入几行，坐标就变了。旧文本则同时表达了位置和前提：我想修改的，是仍然长成这个样子的那一段。相比整文件重写，模型也不必重新生成大量没有变化的代码。

已证实：Claude Code 的 Edit 用 old_string 与 new_string 做精确替换；多处匹配时，需要扩大上下文或明确使用 replace_all。当前文档中的先读后改限制存在模型和版本差异，不能写成所有模型都无例外地必须先调用 Read。[1]

我的分析：旧文本匹配有点像给局部修改加一个条件，但不是完整的版本锁。只要其他人改的是不在匹配片段里的代码，这次 Edit 仍可能成功。它能挡住一部分过期假设，不能证明整份文件的语义都没变，更不等于跨进程的 compare-and-swap。

3.2 对格式宽容，对目标歧义严格

已证实：Pi 的 Edit 虽然描述为精确文本替换，辅助实现却先尝试精确匹配，再进行有限的规范化匹配，处理行尾空白、部分 Unicode 引号、空格等表示差异。当前版本支持一次对单个文件提交多个 edits，所有目标对同一个原始内容匹配，拒绝重叠区间。[6]

OpenCode V2 同样对换行、排版引号及部分空白差异做限定的回退；匹配不唯一仍然要明确处理。找不到旧内容时，还可能提示新内容已经存在，或返回附近相似行；这些包含文件内容的提示会先检查读取许可。[9]

我的分析：这是两种错误的区别：模型丢了一个排版符号，和模型不知道要改哪一处。前者可通过可解释的规则容错，后者应该拒绝。所谓“智能编辑”，不应该是在证据不足时更积极地猜测。回退还应暴露用了什么规则，避免用户以为发生的是逐字节替换。

3.3 工具协议和展示界面，解决不同问题

让模型提交 old/new，并不妨碍运行时给人展示 diff。Anthropic 早期的工具设计文章指出，生成 unified diff 可能要求模型在写完内容前算对行数，而 JSON 还有转义开销；这些格式对普通程序等价，对模型却不一定一样容易。该文章还记录过用绝对路径降低相对目录混淆的实践。[3]

我的分析：可以让模型用它更擅长的协议表达意图，让工具负责匹配、计算 diff，再让人看适合审阅的形式。old/new、patch 和整文件都不是通用赢家；对代码改动密度、模型训练偏好和多文件任务，应通过评测选择。工具参数是模型交互界面，不必直接照搬人类编辑器的操作方式。

四、Write：参数更简单，承担的内容却更多

Write 的契约通常很直接：路径加完整内容，创建或覆盖。Pi 的实现还会创建缺失的父目录；OpenCode V2 的描述明确建议局部变更使用 Edit。[7][10]

我的分析：Write 适合新文件、短小的完整配置，或者本来就要重新生成的产物。修改大文件的一行却用 Write，意味着模型必须再次正确输出其他所有内容；“我只想改这里”不会自动成为工具约束。生成量和意外遗漏面都会扩大。

需求更自然的表达仍要检查的事
新建一个配置文件Write：完整内容目标是否已存在，是否允许覆盖
现有函数改几行Edit：带上下文的局部替换是否匹配唯一位置，是否符合最新代码
大量规律性变更经过验证的脚本或专用重构工具作用范围、预览、失败与回滚策略
重构跨多个文件分组修改，加完整的验证流程部分成功时怎么办；多文件不天然具备事务性

小接口并不自动意味着小风险。同样写一次文件，Write 可以替换全部字节，Edit 只授权一个局部意图；但两者背后的文件系统写入是否原子、是否持久化，是另外一层契约。

五、Bash：名字像一个工具，实际接入了一整个软件生态

5.1 为什么始终需要这条通用通道

编译、测试、包管理、Git、数据处理，都已经有成熟的命令行接口。若为每个子命令建立专用工具，工具定义会不断增长，而且参数边界容易重叠。Shell 用一套组合规则连接已有程序，是能力扩展最直接的方式之一。

我的分析：代价也很明确：一段命令可能包含重定向、管道、子进程与网络访问，副作用不能只从“Bash”这个名字判断。专用 Edit 的变更意图可直接呈现；同样的修改藏在脚本里，运行时需要分析和约束更多东西。工具描述负责引导，权限和隔离必须由模型之外的系统执行。[2]

5.2 读文件留开头，执行日志留结尾：不是随便截一段

已证实：Pi 的文本 Read 使用头部截断，而 Bash 的文本输出保留尾部；大输出会保存到临时文件，并给出可继续读取的路径。Bash 还区分非零退出、取消与超时等状态。所读源码为这些路径分别生成结果或错误。[4][5][11]

我的分析：文件开头通常给出结构、导入与定义，日志结尾经常包含最终状态；这是有用的默认启发式，绝不是保证。错误也可能在日志中间。因此“保留尾部 + 可检索的全文”比“只保留尾部”重要：缩短观察，仍留下追溯证据的路。

5.3 执行工具还需要时间、状态和身份

已证实：OpenCode V2 这一快照中的通用执行工具名为 shell。其参数明确区分 workdir、超时和后台运行，结果区分 running 与 completed；后台任务带标识并在结束后通知会话。源码中的说明要求避免为等待完成而反复轮询。[12]

我的分析：“一个 Bash 工具”不能被理解为“一个永远活着的终端”。文件、当前目录、环境变量与进程各有生命周期，产品之间也不同。没有明确约定，就不该假设上一条命令的 export、后台任务或目录切换能在下一次调用中沿用。

更关键的是：超时不一定意味着副作用没发生，取消返回也不一定证明所有子进程已停止。可靠运行时必须说明自己知道什么。如果一次发布命令失联，盲目重试可能重复发布；恢复前应先核对外部状态，而不是只重放上一次参数。

六、真正的巧思，往往藏在工具之间

6.1 错误结果也是下一步的操作界面

“失败”几乎没有信息。“匹配了两处，请增加周围上下文”“已展示到第 120 行，请从 121 行继续”“进程仍在运行，不要重复启动”，则直接减少下一步的不确定性。错误不只是让程序抛异常，还在教模型怎样修复调用。Anthropic 的工具设计文章也强调返回有意义的信息、控制响应量，并通过实际任务评测迭代描述。[13]

我的分析：好的错误应回答三件事：什么条件没满足、是否已产生副作用、接下来可以怎样确认。尤其对写入与执行，不能把“模型收到错误”直接等价为“世界没有改变”。

6.2 参数描述不是注释，而是模型执行前的约束说明

Pi 的参数说明强调批量 edits 都匹配原始文件；OpenCode 的 Edit 明确要求不要复制行号。它们都针对真实的误用方式，在模型生成参数之前解释正确边界。[6][9]

我的分析：一个可用的工具应同时说明“什么时候用”和“什么时候不用”。例如 Write 必须说明覆盖，Edit 必须说明目标歧义，Read 必须说明返回范围。JSON Schema 能限制类型，却不能单独保证模型选择了正确文件、理解了覆盖语义。

6.3 工具之间要共享状态，但别夸大共享状态的保证

已证实：Pi 的 Edit 与 Write 经过同一份文件变更队列，同文件串行、不同文件可并行。取消逻辑在等待文件操作结束之后检查信号，避免过早释放队列。OpenCode 的文件变更层同样明确指出：进程内的锁只约束协作调用，外部写入仍可能竞争。[14][15]

我的分析：队列不是跨进程锁，串行不是磁盘持久化，写入一次也不是跨文件事务。共享读写状态有助于减少误用，但真正的并发控制应把 IDE、格式化器、Shell 和其他 Agent 都纳入考虑。只给专用 Edit 加锁，挡不住 Bash 里另一个脚本写同一文件。

6.4 工具集合会演进，设计原则比固定名单更耐用

当前 Claude Code 文档已按平台调整搜索工具的默认提供方式；macOS、Linux 与 WSL 的部分搜索通过 Bash 执行，特定配置下才恢复 Glob/Grep。[1] 这提醒我：不能把某个版本的工具名单当成 Agent 的本质。

我的分析：模型更擅长 Shell 后，部分专用工具可能收益下降；权限、观测或多模态能力仍可能要求保留独立接口。该评测的是完成质量、恢复成本和副作用可控性，而不是“越少越优雅”或“越多越专业”。

七、如果自己实现，我会先保证哪些契约

实现推演：下面是一种面向可部署 Agent Workspace 的设计，不是上面产品源码的复刻。核心思路是把“模型意图”“运行时校验”和“实际副作用”分开记录。

层次建议记录或检查解决的问题
输入工具版本、明确的工作区与路径语义、调用 ID同样的字符串不要指向不同工作区
观察读取范围、是否截断、内容版本或 hash区分没看到、没有、已经变化
写入旧内容条件、预期版本、授权范围、实际 diff拒绝过期假设，并让修改可审阅
执行任务 ID、状态、退出码、取消结果、日志引用区分启动成功与工作完成
恢复副作用是否已提交、结果是否已送达、可否安全重试避免超时后盲目重复写入或执行

例如局部修改请求可以额外带上 expected_version，由单一写入服务校验并提交。只有版本检查和写入在同一个受约束的提交机制里，这个字段才有并发意义；“先算 hash，过一会儿再写”仍存在竞争窗口。临时文件加 rename 可帮助解决部分可见性问题，但还要分别考虑符号链接、权限、跨文件系统与崩溃持久化。

返回结果也可以分两层：给模型一小段足够做决定的文本，给运行时与界面结构化字段，例如 status、changed_paths、truncated、artifact_ref。保留结构化数据不意味着把所有字段都塞进下一轮模型输入；大工件的有效期和访问权限也必须明确。

怎样证明这些巧思真的有用

我会用同一个模型、同一批任务，对照 strict Edit、限定格式容错、patch、整文件重写等协议。至少覆盖以下情形，再决定工具该不该合并：

  • 目标定位：重复代码、旧文本过期、文件前面插入新行，是否误改？
  • 格式与范围：CRLF、Unicode 引号、一行超大 JSON、部分读取，是否误判完整性？
  • 并发与中断：外部写入、批量编辑区间重叠、取消发生在写入中途，能否解释真实结果？
  • 执行恢复：日志超长、命令退出 1、后台任务尚未完成、工具返回前连接断开，会不会误报成功或重复执行？

除任务成功率，我还会看误改率、额外重试次数、传给模型的输入量、等待时间，以及失败之后能否恢复。本文没有执行这些对照实验，因此不能宣称某个协议带来具体百分比提升。

我的判断是：工具是在为模型设计一个可观察、可操作、可纠错的世界。Read 把观察范围讲清楚，Edit 把修改前提写出来，Write 让完整覆盖的责任显式化，Bash 把开放能力接入有状态的执行环境。模型负责提出下一步，运行时负责兑现契约；两者配合，才可能在真实文件和进程上稳定地工作。
