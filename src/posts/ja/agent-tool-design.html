Bash でファイルを読み書きし、プログラムも実行できるのに、なぜエージェントに Read、Edit、Write という個別のツールを持たせるのか。注目したいのは、一見重複するツールが、モデルに推測させる事柄をどう減らすかだ。

調査範囲 · 2026-11-13

Claude Code は公式ツールリファレンスに記載された公開仕様を、Pi と OpenCode は末尾に示したコミットのソースを調べた。「考察」は設計上の判断についての私の解釈、「実装案」は私自身の提案である。3 製品を同じ条件で比較する評価は行っていない。図中のファイル、ログ、実行状態はいずれも説明用の例だ。

1. ひとつのタスク、4 つの契約

「リトライ回数を 3 から 5 に変えて確認する」タスクを考えよう。Read は「現在どうなっているか」を返し、Edit は「この箇所を変える」と伝え、Write は「ファイル全体はこうあるべきだ」と指定する。Bash は実環境のプログラムを呼び出す。それぞれが操作できる範囲を定めており、常にこの順番で実行するわけではない。

01 / 観察

Read

設定ファイルの該当範囲を読む。

path + offset + limit結果が示すのは観察できた範囲だけ。
02 / 局所的な変更

Edit

元のコードを見つけ、新しいコードに置き換える。

old text → new text元のテキストが一致しなければ再検討する。
03 / 内容全体

Write

設定を新規作成するか、ファイル全体を書き直す。

path + full content指定しなかった部分は引き継がれない。
04 / 実行と検証

Bash / Shell

テスト、コンパイラー、既存の CLI を実行する。

command + execution context起動成功だけではタスクの完了は分からない。

考察。専用ツールは、よくある操作を生成しやすく、検証しやすく、説明しやすい呼び出しに変える。シェルを使えば、コマンドごとにツールを作らなくても既存のソフトウェアを組み合わせられる。適切な境界はタスクの分布、モデルの能力、実行環境に依存する。API の個数だけでは判断できない。

ツール呼び出しをパラメーターから読む

以下では主に Claude Code 公式 SDK の公開入力型を用い、Pi と OpenCode は固定したコミットと比較する。JSON の例に示すのはツールの inputのみで、モデル API に送るリクエスト全体ではない。「任意」は入力を省略できるという意味であり、ランタイムの制限は引き続き適用される。[16]

Read のパラメーター：対象、開始位置、取得量

パラメーター型 / 必須か意味と設計意図よくある誤用
file_pathstring / 必須対象ファイルを指定する。パスと読み取る範囲は別に扱う。ディレクトリや別のワークスペースのパスを渡す。
offsetnumber / 任意テキストの読み取り開始行。1 行目から数え、省略時は先頭から読む。バイトオフセットや 0 始まりの添字と解釈する。
limitnumber / 任意最大行数。省略しても出力上限は残る。limit=20 を「20 行目まで」と考える。
pagesstring / 任意PDF のページ範囲。例： "1-5"。テキストの行範囲と混同する。
allow_largeboolean / 任意対応バージョンで、セッションの残りコンテキストの範囲内でより大きなテキストを読める。出力を無制限にしたり、アクセス権限を変更できたりすると考える。

計算例。offset=3, limit=2 は 3 行目から最大 2 行、つまり 3～4 行目を読む。想定される最終行は offset + limit − 1。ファイル末尾や出力制限に達すると実際の行数は減る。allow_large には SDK v0.3.296 / Claude Code v2.1.296 以降が必要だ。[16]

製品ごとの違い。Pi が使うのは path であり、 file_path ではない。現在の Read スキーマで指定できるのは path / offset / limit のみだ。OpenCode V2 の path はディレクトリも扱え、offset / limit はディレクトリエントリーにも適用できる。同名のフィールドでも受け付ける対象は異なりうる。[4][8]

Edit のパラメーター：旧テキストは条件、新テキストは意図

パラメーター型 / 必須か意味と設計意図よくある誤用
file_pathstring / 必須照合対象をひとつのファイルに限定する。プロジェクト全体から元のコードが自動で検索されると思う。
old_stringstring / 必須現在のファイル内で探すテキスト。必要な前後の文脈も含める。Read の表示用行番号をコピーする、あるいはどこにでも出る単語だけを指定する。
new_stringstring / 必須置換後のテキストそのもの。省略したコードをツールが自動でマージすると思う。
replace_allboolean / 任意一致箇所をすべて置換する明示的な指定。既定では全置換しない。複数箇所に一致したからと true にして、無関係な箇所まで変更する。

考察。old_string は変更場所の特定と前提条件の検証を兼ねる。replace_all は対象をひとつの箇所から一致集合全体へと広げる。変わるのは範囲であって、照合精度ではない。new_string に空文字列を指定すれば一致部分を削除できる。その場合も照合と権限の条件を満たす必要がある。

製品ごとの違い。Pi の現在の主要スキーマは {path, edits: [{oldText, newText}]}。Claude Code と大文字・小文字が違うだけではない。ひとつのファイルへの複数の edits は同一の元データに照合される。OpenCode V2 では path / oldString / newString / replaceAll を使う。範囲の重複禁止、一意性、表記ゆれの扱いはランタイムの規則で、型だけからは判断できない。[6][9]

Write のパラメーター：2 項目で書き込み後の全体を指定する

パラメーター型 / 必須か意味と設計意図よくある誤用
file_pathstring / 必須作成または上書きするパス。既存ファイルかを確認せず、新規ファイルとして書き込む。
contentstring / 必須書き込み後の完全な内容。追記や一部を残すためのパラメーターはない。変更した 1 行だけを渡し、残りが維持されると思う。

考察。JSON 中の \n はデコード後の改行を表す。一方\\n はバックスラッシュと n という 2 文字を書き込むことがある。Markdown のコードフェンスまで本文に含めないようにしたい。content は保存するテキストで、編集手順の自然言語指示ではない。Pi と OpenCode V2 の対応する名前は path / content だ。[7][10]

Bash のパラメーター：コマンド、時間、制御の戻り方

パラメーター型 / 必須か意味と設計意図よくある誤用
commandstring / 必須シェルに実行させるコマンド。説明文を渡す、あるいはパス中の空白をエスケープし忘れる。
timeoutnumber / 任意Claude Code ではミリ秒。フォアグラウンド待機とバックグラウンド実行では期限の規則が異なる。Pi の秒数をそのままコピーして、時間が 1,000 倍ずれる。
descriptionstring / 任意今回の操作の短い用途説明。説明文によってコマンドが変わったり権限が付いたりすると考える。
run_in_backgroundboolean / 任意制御を先に返すようバックグラウンド実行を要求する。「バックグラウンドで起動済み」を処理の成功と取り違える。
dangerouslyDisableSandboxboolean / 任意 · 上級者向けサンドボックス外での実行を要求する。権限とランタイムポリシーには引き続き従う。時間を延ばしたり成功率を高めたりする一般的なスイッチとして使う。

バージョンによる違い。バックグラウンドの期限、タイムアウト後にバックグラウンドへ移るか、利用できるスイッチは Claude Code のバージョンと設定に依存する。以下は単位と実行コンテキストの例で、スケジューリングの再現ではない。通常はサンドボックスのスイッチを変える必要はない。説明文で実行権限を与えることもできない。[1][16]

Claude Code Bashtimeout: 30000、ミリ秒この公開入力型に workdir はない。ディレクトリはセッションが管理する。run_in_background

Pi の任意の timeout は、省略すれば既定のタイムアウトなし、指定すれば有限の正数を必要とする。今回の OpenCode V2 のスナップショットでは timeout=0 でタイムアウトを無効にできる。省略するとフォアグラウンドでは既定 2 分、バックグラウンドでは期限なしとなる。同名のフィールドでも、単位、ゼロの意味、既定値を個別に確かめたい。ここでの違いは固定したリビジョンに限る。拡張機能、リモート実行基盤、将来のバージョンでは規則が変わりうる。[11][12]

パラメーターを読む順序。まず操作対象、次に作用範囲を確かめ、既定値と単位を確認する。最後に戻り値が「完了」か「進行中」かを見分ける。以降では、なぜこのように設計する価値があるのかを考える。

2. Read が返すのはファイルを観察した結果

2.1 行番号、範囲、残量が次の一手を決める

確認できた挙動。Claude Code の Read は行番号と範囲読み取りに対応し、画像などもモデルが認識できる形で返す。大きなファイルでは全体と部分表示を区別する。具体的な上限はモデルやバージョンに依存する。[1]

実装を追いやすいのが Pi だ。Read は 1 始まりの offset と、行数を表す limit を取る。テキスト出力には行数とバイト数の両方に上限がある。この版の既定値は 2,000 行または 50 KiB で、先に達した方で打ち切り、続きの開始位置を返す。[4][5]

考察。2,000 行という制限だけでは足りない。全文なのか、指定した範囲なのか、出力上限で切れたのかを知らせる必要がある。そうでなければ「ここには見えない」を「ファイルに存在しない」と誤解する。行数上限は通常の長いファイルに、バイト上限は 1 行に圧縮した JSON や長大な文字列に効く。どちらも厳密なトークン数ではない。

2.2 Read は実行環境とモデルをつなぐ変換層でもある

画像をバイナリ列だけで返しても扱いにくい。ディレクトリには通常のテキストと異なる扱いが必要で、パスが見つからない場合にも手がかりが欲しい。OpenCode V2 の Read はファイルとディレクトリの両方を扱い、表示用の行番号はファイルの一部ではなく Edit にコピーしてはいけないと明記する。一部のパスエラーでは候補を提示し、読み取り成功後には関連する AGENTS.md を検出する。[8]

考察。Read が返すのは、内容、位置、そしてどこまで読めたかという情報だ。読み取りによってプロジェクトの指示も発見するなら、シェルで読んだ場合にもその挙動を保つのかを決める必要がある。同じテキストを読んでも、その後に適用される指示が異なりうる。stdout が同じだけでは代替可能とは言えない。

3. Edit は書き込みに前提条件を持たせる

3.1 なぜモデルに「42 行目を変える」と指示させないのか

行番号は人が位置を探すには便利だが、前に数行挿入すると対象がずれる。旧テキストは位置と前提を同時に表す。「今もこの形をしている箇所を変える」という指定だ。局所的な編集なら、変わらない大量のコードをモデルに再生成させずに済む。

確認できた挙動。Claude Code の Edit は old_string と new_string で正確な置換を行う。複数に一致したら文脈を増やすか、明示的に replace_all を使う。編集前の読み取りに関する現行の制限はモデルとバージョンによって異なり、常に Read が必須とは言えない。[1]

考察。旧テキストの一致は局所変更の条件になるが、ファイル全体のバージョンロックにはならない。別の人が一致範囲の外を書き換えた場合でも Edit は成功しうる。古くなった想定の一部は検出できるが、ファイル全体の意味が変わっていないことは証明できず、プロセス間の compare-and-swap にもならない。

3.2 表記ゆれには寛容に、対象の曖昧さには厳密に

確認できた挙動。Pi は Edit を正確なテキスト置換と説明する。補助実装ではまず完全一致を試し、次に行末の空白、一部の Unicode 引用符やスペースなどを限定的に正規化して照合する。現行版ではひとつのファイルに対し複数の edits を一度に指定できる。すべてを同じ元データと照合し、重なる範囲は拒否する。[6]

OpenCode V2 も改行、組版用引用符、一部の空白差に限定して照合をやり直す。一意に決まらない場合は明示的な対処が必要だ。旧テキストが見つからないと、新しい内容が既に存在する旨や近くの類似行を提示することがある。これらのヒントにはファイル内容が含まれるため、読み取り権限を先に確認する。[9]

考察。モデルが記号の表記を落とした場合と、どこを変えるつもりなのか分からない場合は、別の失敗だ。前者には説明可能な正規化が使える。後者は拒否すべきだ。根拠が足りないほど積極的に推測するのは賢い編集とは言えない。フォールバックで使った規則も示せば、利用者はバイト単位で一致したのかを判断できる。

3.3 ツールのプロトコルとレビュー画面では読み手が違う

モデルに old/new を渡させても、ランタイムは人に diff を表示できる。Anthropic の初期の設計記事は、unified diff の生成では内容を書き終える前にモデルが行数を正しく数える必要があり、JSON にはエスケープの負担があると述べている。通常のプログラムには等価な形式でも、モデルにとっての難易度は異なる。相対ディレクトリの取り違えを減らすため絶対パスを採用した例も記録されている。[3]

考察。モデルには得意なプロトコルで意図を表させ、照合と diff の計算はツールに任せ、人にはレビューに適した形式を示せばよい。old/new、パッチ、ファイル全体のどれが向くかは状況による。変更密度、モデルの学習傾向、複数ファイルのタスクを踏まえて評価したい。ツール引数はモデルとのインターフェースであり、人間のエディター操作をそのまま写す必要はない。

4. Write は引数が少ない分、より多くの内容を引き受ける

Write の一般的な契約は、パスと完全な内容を渡してファイルを作成または上書きすることだ。Pi は存在しない親ディレクトリも作る。OpenCode V2 は局所的な変更には Edit を推奨している。[7][10]

考察。Write は新規ファイル、短い設定ファイル、もともと全体を再生成する成果物に向く。長いファイルの 1 行だけを Write で変えるには、他のすべての行もモデルが正しく再出力する必要がある。「ここだけ変えたい」という気持ちはツールの制約にならない。生成量が増え、偶発的に欠落する箇所も広がる。

目的自然な指定確認事項
設定ファイルを新規作成Write で全内容を指定対象は存在するか。上書きは許可されているか。
既存関数の数行を変更前後の文脈を含む Edit一意の場所に一致するか。最新のコードに合っているか。
規則的な変更を多数適用検証済みスクリプトまたは専用リファクタリングツール作用範囲、プレビュー、失敗時の処理と巻き戻し
複数ファイルをまたぐリファクタリング変更をまとめて適用し、全体を検証一部だけ成功したらどうするか。複数ファイルの変更にトランザクション性が自動で付くわけではない。

小さなインターフェースでも大きな変更はできる。Write は全バイトを置き換えられ、Edit が表明するのは局所変更の意図だ。その下でファイルシステムへの書き込みが原子的か、永続化されたかは別の契約になる。

5. Bash はひとつのツールからソフトウェアの生態系につながる

5.1 汎用の実行経路を残す理由

コンパイル、テスト、パッケージ管理、Git、データ処理には成熟した CLI がある。サブコマンドごとにツールを定義すると一覧は膨らみ、引数の役割も重複する。シェルなら一定の組み合わせ規則で既存のプログラムを接続でき、機能を追加しやすい。

考察。その代わり、コマンドにはリダイレクト、パイプ、子プロセス、ネットワークアクセスが含まれうる。「Bash」という名前だけでは副作用を判断できない。Edit の変更意図は直接表示できるが、同じ処理をスクリプトに入れると、ランタイムが解析し制約すべき挙動が増える。説明文はモデルを導ける。権限と隔離の強制はモデルの外で行う必要がある。[2]

5.2 ファイルは先頭、実行ログは末尾を残す理由

確認できた挙動。Pi のテキスト Read は切り詰める際に先頭を残し、Bash のテキスト出力は末尾を残す。大きな出力は一時ファイルに保存し、後で読めるパスを返す。また Bash は非ゼロ終了、キャンセル、タイムアウトを区別する。調べたソースでは、これらの経路ごとに結果またはエラーを生成している。[4][5][11]

考察。ファイルの先頭には構造、インポート、定義が現れやすく、ログの末尾には最終状態が出やすい。これは目安にすぎず、エラーは途中にも現れる。「末尾と検索可能な全文」を残せば、一度に観察する量を抑えつつ根拠に戻れる。

5.3 実行には時間、状態、識別子も必要になる

確認できた挙動。この OpenCode V2 のスナップショットでは汎用実行ツールは shell と呼ばれる。引数で workdir、タイムアウト、バックグラウンド実行を区別し、結果では running と completed を区別する。バックグラウンドタスクには識別子が付き、完了するとセッションに通知する。ソース内の説明でも完了待ちの反復ポーリングを避けるよう求めている。[12]

考察。Bash ツールがあるからといって、端末が永続するとは限らない。ファイル、作業ディレクトリ、環境変数、プロセスにはそれぞれ寿命があり、製品ごとにも異なる。明示された契約がなければ、前回のコマンドの export、バックグラウンドタスク、ディレクトリ移動が次の呼び出しに引き継がれると想定してはいけない。

タイムアウト時点で副作用が既に起きていることも、キャンセル応答後も子プロセスが動いていることもある。信頼できるランタイムは、どこまで確認できたかを伝える。公開コマンドで接続を失ったとき、無条件の再実行は二重公開を招く。引数を再送する前に外部の状態を確認したい。

6. ツールとツールの間にある工夫

6.1 エラーは次の操作を助けるインターフェース

「失敗」だけでは手がかりが乏しい。「2 箇所に一致。前後のテキストを追加」「120 行目まで表示。121 行目から再開」「プロセスは実行中。再起動不要」なら、次の判断がしやすい。エラーは呼び出しの直し方をモデルに教えられる。Anthropic の設計記事も、有用な情報の返却、応答量の制御、実タスクでの評価を通じた説明文の改善を重視している。[13]

考察。良いエラーは、満たせなかった条件、副作用の有無、次に確認する方法を伝える。特に書き込みやコマンド実行では、モデルがエラーを受け取っただけで外の状態が変わっていないとは言えない。

6.2 引数の説明は実行前に制約を伝える

Pi はバッチ内のすべての edits が元ファイルと照合されると説明する。OpenCode の Edit は行番号をコピーしないよう明記する。どちらも、モデルが引数を生成する前に具体的な誤用を防ごうとしている。[6][9]

考察。使いやすいツールは、使うべき場面と他を選ぶべき場面の両方を示す。Write は上書き、Edit は対象が曖昧な場合、Read は返却範囲を説明する必要がある。JSON Schema は型を制限できるが、正しいファイルを選んだか、上書きの意味を理解したかまでは保証しない。

6.3 ツール間で状態を共有し、その保証範囲を明示する

確認できた挙動。Pi の Edit と Write は共通のファイル変更キューを通る。同一ファイルは直列化し、別ファイルは並行処理できる。キャンセル処理ではファイル操作の終了を待ってからシグナルを確認し、キューを早く解放しすぎる事態を防ぐ。OpenCode の変更層にも、プロセス内ロックが調整するのは協調する呼び出しだけであり、外部の書き込みとは競合しうると明記されている。[14][15]

考察。キューはプロセス間ロックではなく、直列化してもディスクへの永続化は保証されず、単一ファイルへの書き込みは複数ファイルをまたぐトランザクションにもならない。状態共有は誤用を減らせるが、並行制御には IDE、フォーマッター、シェル、他のエージェントも含めて考えたい。Edit だけをロックしても、Bash のスクリプトは同じファイルを変更できる。

6.4 ツール一覧は変わっても設計原則は残る

現行の Claude Code の文書では、検索ツールの既定値がプラットフォームによって異なる。macOS、Linux、WSL では一部の検索を Bash で実行し、特定の設定で Glob/Grep が復帰する。[1] あるバージョンのツール一覧だけでエージェントを定義するのは早計だ。

考察。モデルがシェルを使いこなすにつれて、一部の専用ツールの利点は小さくなるかもしれない。一方、権限、可観測性、マルチモーダル入力は専用インターフェースを残す理由になる。評価すべきは成果の品質、復旧コスト、副作用を制御できるかであり、ツールの多寡ではない。

7. 自分で実装するなら最初に何を保証するか

実装案。デプロイ可能なエージェントのワークスペースを設計するなら、モデルの意図、ランタイムの検証、実際に起きた副作用を別々に記録したい。以下は上記製品の実装の再現ではなく、私の案だ。

層記録・確認する事項解決する問題
入力ツールのバージョン、明示的なワークスペースとパスの意味、呼び出し ID同じ文字列が別のワークスペースを指すのを防ぐ
観察読み取り範囲、切り詰めの有無、内容のバージョンまたはハッシュ未確認、存在しない、変更済みを区別する
書き込み元の内容の条件、期待バージョン、認可範囲、実際の diff古い想定を拒否し、変更をレビュー可能にする
実行タスク ID、状態、終了コード、キャンセル結果、ログへの参照起動成功と作業完了を区別する
復旧副作用が確定したか、結果が届いたか、安全に再試行できるかタイムアウト後の無条件の再書き込みや再実行を防ぐ

例えば局所変更のリクエストに expected_version を追加し、単一の書き込みサービスで検証・確定できる。並行制御として意味があるのは、バージョン確認と書き込みが同じ制約下のコミット機構にあるときだけだ。ハッシュを算出してから時間を置いて書く方法には競合区間が残る。一時ファイルと rename は可視性の問題の一部に効くが、シンボリックリンク、権限、ファイルシステムの境界、クラッシュ時の永続性は別途検討する必要がある。

結果も、モデルが次を判断するのに十分な短いテキストと、ランタイムや UI 用の構造化フィールドに分けられる。例えば status、changed_paths、truncated、artifact_ref などだ。構造化データを保存しても、全項目を次のモデル入力に入れる必要はない。大きな成果物の有効期限とアクセス権限も明示したい。

工夫の効果を確かめる方法

同一モデルと同じタスク群で、厳密な Edit、限定的な表記ゆれ許容、パッチ、全体書き換えを比較したい。ツールを統合するか決める前に、少なくとも以下を検証する。

  • 対象の特定。コードの重複、旧テキストの陳腐化、対象より前への行挿入で誤った箇所を変えないか。
  • 形式と範囲。CRLF、Unicode 引用符、1 行に詰めた巨大な JSON、部分読み取りによって完全性を誤認しないか。
  • 並行処理と中断。外部からの書き込み、バッチ内での範囲の重複、書き込み途中のキャンセル後に実際の結果を説明できるか。
  • 実行の復旧。長大なログ、終了コード 1、未完了のバックグラウンド処理、応答前の切断で、成功を誤報したり二重実行したりしないか。

成功率に加え、誤変更率、余分な再試行回数、モデルに渡す入力量、待ち時間、失敗後に復旧できるかも測りたい。本稿ではこれらの比較実験を実施していないため、特定のプロトコルによる改善率を示すことはできない。

私の考え。ツールを設計することは、モデルが観察し、働きかけ、誤りを修正できる世界を設計することだ。Read は観察の範囲を示し、Edit は変更の前提条件を記述し、Write はファイル全体を上書きする責任を明示する。Bash は用途の広い能力を状態のある実行環境へつなぐ。モデルが次の一手を提案し、ランタイムが契約を守る。その両方がそろって初めて、実際のファイルやプロセスを安定して扱える。
