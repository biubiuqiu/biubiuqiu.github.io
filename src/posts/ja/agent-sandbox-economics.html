300人がエージェントに一台ずつ専用のコンピューターを与えたとする。朝、Python で注文を集計し、レポートを作った。ユーザーは10分かけて数字を確認し、「次は地域別のグラフにして」と戻ってくる。その間レポートは残したいが、インタープリターも動かし続ける価値はあるか。全員が同じ1分間に戻ったら何台必要か。

ファイルを残す、プロセスを残す、マシンを丸ごと残す。ユーザーから見た体験は似ていても、プラットフォームの負担は大きく違う。まず、Bash を実行し、コードを書き、ファイルを届けられる環境から考えよう。前の記事：なぜエージェントにサンドボックスが必要なのか

複数の会話で使う Lester の一台の Computer

Lester で一人が三つの会話を開いても、論理上の Computer は一つだ。サンドボックス表には user_id の一意制約があり、各会話のコマンドは /workspace/conversations/<id> から起動する。ファイルツールは会話のディレクトリを基準にパスを検査する。端末、Python、Git、インストール済みのブラウザーは同じ環境を使える。新しい会話は準備済みの道具を再利用でき、前のレポートにも置き場所がある。[1]

具体的な設計で気に入っている点がある。Docker バックエンドは名前付きボリュームを /workspaceにマウントし、アイドル時の回収には docker stopを呼び、再開には startを使う。戻ったとき、ディスク上の orders.csv はまだ開けるが、元の Python プロセスにあった df は消えている。スクリプトを再実行すれば次のグラフを描ける。ファイルはコンテナの停止と起動をまたげるが、標準のローカルボリュームは元のホストに残る。別のマシンが引き継ぐには取得経路が要る。[1]

「一人一つ」を三つの判断に分けたい。ファイルの所有権は、誰がその環境に戻れるかを決める。どのタスクを一緒に実行できるかは、複数の会話が同じファイルを編集し同じポートを占有できるかを決める。計算をどこに配置するかはタスク間の空き時間を誰が負担するかを決める。ディレクトリでファイルを整理しても、共有環境ではポートが競合しうる。信頼できる個人のタスクはツールチェーンを共有し、権限や依存条件が衝突するタスクには別の環境を与えられる。三つは独立に改善できる。

マシンを返せる待ち時間を特定する

GitHub Copilot の本番トレースを使った研究が規模感を示す。2026年6月に抽出した約1,300万セッションを調べたところ、複数ターンのセッションではユーザー待ちが総時間に占める割合の中央値は80.1%だった。これは対話のターン間の時間である。回収できるサンドボックス時間に換算するには、バックグラウンド処理の有無も知る必要がある。[2]

レポートに戻る。集計条件の確認待ちでスクリプトが終了し、結果がディスクにあれば回収しやすい。モデル呼び出しと進行管理がサンドボックス外なら次のコマンドの生成中にも資源を返せるかもしれない。一方、ユーザーがレポートを読んでいても、裏のブラウザーは PDF を出力中かもしれない。CPU が数秒ほぼゼロでも停止すれば出力は途切れる。

前景コマンド、バックグラウンドジョブ、公開を続けるプレビューを実行サービスで記録したい。「人の確認待ち」など理由の分かる停止は進行管理側で示す。短いコマンド間はウォーム状態を維持し、長い待ちが明らかなら早めに回収する。Lester の標準アイドル閾値は30分。Google の Agent Substrate は休止 API をいつ呼ぶかをアプリに委ねる。自分の環境で呼び出し間隔の分布を測り、短い休止に許す再開待ちを決めよう。[1] [3]

Google は一つの Pod に複数のサンドボックスをどう収容するか

Google には名前の似た二つの設計がある。Agent Sandbox on GKE は Sandbox ごとに専用 Pod を割り当てる。ここで扱う Agent Substrate はさらに一層を設ける。Kubernetes は Worker Pod を配備し、一つの Worker に複数の Actor が同時に載る。Actor は安定した識別子を持ち、それぞれ gVisor または microVM で隔離する。gVisor 構成では Worker が runsc を呼んでサンドボックスを管理する。Kubernetes が Worker Pod を配置し、Substrate は仕様と残容量に応じて Actor を配置する。[4] [5] [6]

二つの設計を重ねよう。レポートの利用者に長く有効な作業環境 ID を与え、実行時に Actor に対応付ける。初回の作図は Worker A、後続のコマンドは Actor ID で A に戻す。休止後の空きは他の人が使える。次の作図では互換性と空きのある Worker B が引き継げる。クライアントは作業環境 ID だけを保持する。Substrate の制御面は Actor と Worker の対応を PostgreSQL に記録する。Lester の個人作業環境をこのプールにつなぐ部分は私の設計案だ。[4]

プール化は障害と権限の単位も変える。20個の稼働 Actor を載せた Worker が失われれば、同時に最大20件の復元要求が生じる。マシン当たりの密度によって、単一障害用に必要な余力も決まる。ネットワーク上の主体も Actor に追従させる。Google は個別の ID を割り当て、出口ゲートウェイで ID に応じて認証情報を付与できる。同じ Pod にいる二人がそれぞれの権限で外部サービスを利用できる。[6]

300の作業環境にマシンは何台必要か

各ユーザーが10分に一度ちょうど1分間ツールを実行し、その後1分間環境を保持するとする。サンドボックス一つに約束した資源を与えられる容量を「枠」と呼ぶ。1周期の占有は 300 × 2 ＝ 600 枠・分で平均60枠。この平均だけで調達すれば、開始時刻の偏りを見落とす。

連続するタスクを10分周期に単純化し、ウォーム状態は次の周期に持ち越す。各サンドボックスが 1 vCPU と 2 GiB を専有し、システムとランタイムの分を引いて各ノードに 12 vCPU と 24 GiB が残るなら、Worker 一つに12個載る。分散開始と一斉開始のピークはそれぞれ5台と25台。待ち行列なしを仮定し、制御面、障害用予備、ノード起動時間は含めていない。単価と実機性能は別途測定する。

Google が11月16日に公開したモデルは節約効果が薄れる条件も示す。 us-central1 のオンデマンド料金で、100個のコーディングエージェントについて、1セッション1常駐 Pod を基準に比較した。同じ CPU 保証と勤務時間なら、一人毎時2プロンプトで休止によるノード費削減は約40%。毎時4回では約4%に縮む。勤務時間外はプールをゼロにする想定だ。比較では CPU 保証をそろえ、オーバーコミットによる節約を休止の成果に加えないようにしたい。[3]

二つの指標を別々に記録したい。一つ目は解放した枠・分で、ほかのタスクが使える分に価値がある。二つ目は支払わずに済んだノード時間で、ノード一台分の課金を止めたとき初めて請求に現れる。各マシンに長時間タスクが一つずつ散らばると、この二つは大きく乖離する。新規タスクを既存の空きに詰め、撤去予定 Worker はドレインし、分散した空きを一台分にまとめる。個々の空き時間で回収できる価値を、スナップショットの書き込み、保管、読み戻しの増分費用と比べる。利益が出ても、復元がユーザーの待てる時間内に終わらなければならない。

Worker を交換するときレポートは何を持ち出すか

実行層が「ステートレス」かを判断するにはマシン交換を試す。Worker A を失った状態で同じユーザーを B に送り、何を取り戻せるか確かめる。稼働中のサンドボックスにはメモリもプロセスもある。重要な状態の唯一のコピーを Worker の外に出すことで、ホストを交換可能にできる。

ユーザーが続けたい作業永続化するものB での続け方
保存済みレポートを編集作業ファイルとコミット済み成果物の版ユーザーの永続ボリュームを再マウントするか、コミット済みの版を開く
同じライブラリで別のグラフを描くベースイメージの版、依存ロックファイル、個別に加えた変更読み取り専用レイヤーを再利用し、ロックファイルから不足分を補う。キャッシュは再構築可能
メモリ上の df の操作を続ける互換性があるプロセス・メモリのスナップショットと対応するファイルの版条件が合えばインタープリターを復元。不一致なら再起動し、ファイルから再計算
レポートが公開されたか確認タスク記録、操作 ID、外部サービスの受領記録外部サービスと結果を照合し、成果物を元の会話にひも付ける

ファイルの信頼性は「保存した」と伝えるタイミングで決まる。唯一のコピーがノードにあり、終了時に S3 に送る構成では、保存通知の直後に障害が起きると、その書き込みはスナップショットにすら入らない。確認済みファイルがノード喪失に耐えると約束するなら、成功を返す前に永続化する。EFS Regional の文書は、同期書き込みやファイルのクローズ後の AZ 間での永続性を明記している。ファイルツールは所定のコミット条件を満たしてから応答する。Bash から実行されたプログラムのユーザー空間バッファにあるデータは、実際のフラッシュを待つ必要がある。[7]

多くの作業が数本のスクリプトの修正と少数の成果物の公開なら、成果物を版付きでオブジェクトストレージに置き、成功後にその版を指すマニフェストをコミットする方が軽い。端末を開き、名前を変え、実行中にも編集するなら永続ファイルシステムが合う。両立もできる。編集用ファイルは外付けの作業ボリューム、公開版とバックアップはオブジェクトストレージに置けば、数百 MiB の参照データを休止のたびに移さずに済む。

プロセスの継続性は別に費用を見積もる。Agent Substrate は条件に応じてメモリ、ルートファイルシステムの変更、永続ディレクトリを復元できる。ハードウェアやランタイムが非互換ならファイルを残してプロセスを再起動できる場合があり、テンプレート更新時は永続ディレクトリだけを戻す場合もある。外部 CSI ボリュームは元のストレージから再マウントする。同期休止はリモート転送完了を待つが、非同期ではリモートコピーが一時的に PENDINGの状態でもよい。マシンを撤去するかの判断には、別のホストで復元可能な最新の版を使う。[6] [5] [8]

逆向きにも落とし穴がある。スナップショット内の df が月曜日の値で、再マウントした作業環境が別のタスクにより火曜日のデータに更新されていたら、復元に成功しても計算を誤る。入力ファイルか作業環境のコミット版をマニフェストに記録したい。不一致ならインタープリターを起動し直し、再計算の理由を示す。ファイルの永続性とプロセスの復元性は別の契約であり、両者をつなぐには整合した一時点が要る。

旧 Worker から遅れて届いた書き込み

A がレポートを書いている途中で通信が切れ、制御面にハートビートが届かず、B が作業環境を引き継いだとする。10秒後、A は古いファイルハンドルを持ったまま再接続する。両者に書き込み権限があれば、新しいルーティングが有効でも A は B の編集を上書きできる。

Lester はユーザー単位の PostgreSQL トランザクションロックで、複数の API レプリカが同時に Computer を作るのを防いでいる。引き継ぎでは生き残った旧所有者にも対処が要る。交代のたびに単調増加する世代番号を与える。A は41、B は42。公開サービスはコミット時に現在の世代を確認し、遅れてきた41を拒否する。これが fencing token だ。Bash が書き込み可能な NFS に直接書く経路は検査を通らない。旧ノードの書き込みを先に遮断するか、世代別コピーに書いて公開時に世代を照合する。DB のリース更新だけでは開いたままのハンドルを制御できない。[1] [9]

遅れるのは外部の受領通知も同じだ。公開先が受理した後、応答前に A が切断された。B がスナップショットから公開を再生すれば、読者に二通届くかもしれない。公開ごとに永続タスク記録で安定した操作 ID を割り当て、外部 API が対応すれば再利用して重複を防ぎ、受領結果を記録する。冪等性も照会もない操作は「結果の確認待ち」にしておく。Lester は GitHub 公開時の受領記録を永続化し、結果が不明な書き込みは先に照合する。安心して「続ける」を押せるかどうかには、端末を残すこと以上にこの点が効く。[1] [10]

スケールアウト時、最初の有用なコマンドは何秒で終わるか

午前9時に100の作業環境が一斉に起動する。それぞれが遠隔ストレージから 128 MiB の圧縮スナップショットを取得し、全件を10秒で読み終えるにはネットワークだけで 1.25 GiB/s の実効帯域が要る。展開とランダム読み取りはまだ含まない。CPU に空きのある Worker を増やしても共有帯域が復元を制限する。一斉縮退でもスナップショット書き込みが集中する。Google の容量ガイドは帯域、ノードのディスク、同時アップロード数を別々に見積もる。[5]

E2B のオープンソースランタイムは別の設計を選ぶ。テンプレートは起動済み Firecracker microVM のスナップショットで、メモリページは初回アクセス時に読み込み、ルートファイルシステムは読み取り専用イメージ上のコピーオンライトである。 ls だけならすぐ開始できるが、大きなライブラリを初めて読み込んで作図するときにページフォールトや遠隔読み取りが集中することがある。「復元要求から準備完了まで」「最初の有用なコマンドが完了するまで」の P95 を両方測り、コールドノードで実際のレポートスクリプトを試したい。[11]

観測結果で打ち手は変わる。空き枠が尽きて仕事が並べば Worker を増やし、新しい Worker Pod を収容できなくなればノードプールを広げる。枠が余っていても復元が詰まるなら遠隔帯域とノードキャッシュのヒット率を見る。縮退時は対象 Worker への新規割り当てを止め、処理中のジョブが終わるか必要なスナップショットがリモートから復元可能になってから撤去する。

次の Lester ならユーザー単位の作業環境を維持し、確認済みファイルと公開の受領記録をホスト交換後も検証できるようにする。ツールの開始・終了、バックグラウンド処理、復元時間を一週間集め、最も忙しい数分で容量を決め、一週間のノード時間で費用を計算する。ファイルから再計算できるレポートは安価な再起動、メモリを残したい Notebook だけはスナップショットを選ぶ。空きの回収益が第二のスケジューラーを維持する費用に見合う段階で、複数サンドボックス Worker を導入する。

受け入れ試験には冒頭のレポートを使う。ユーザーはデータを確認してから戻り、同じ入力を指定する。別のワーカーノードで正しい図ができ、一度だけ公開される。さらに、明け渡した10分間の容量が請求にも表れれば、より多くのユーザーへ展開する根拠になる。
